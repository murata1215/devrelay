# サイクル SB-2.1.4: 許可先ありで失敗する不具合の修正と、Windows PowerShell 5.1 用テストの新設

## 背景（hp630g9、commit b720ff5）

空集合（許可先なし）では成功するが、`allowDestinations: ["192.168.32.196:2222"]` を設定すると
反映が失敗した。`request.json` は正常（`destinations: [{ip:"192.168.32.196", port:2222}]`）。
`state.json` の `error` は `rule_creation_failed: System.Management.Automation.PSArgumentException
at line 661`。画面には「プロパティ "port" が見つかりません」。失敗時に前の世代（全遮断）が
残ることは確認済み（SB-2.1.3 の修正どおり正常動作）。

SB-2.1.1〜2.1.3 と同じく、`apply-sandbox-allowlist.ps1` は Linux で書かれ、Windows PowerShell
5.1 で一度も実行されないまま実機確認に回っており、1 回に 1 個ずつ 5.1 固有の不具合が見つかって
いた。

## 真因

`$destinations`（522/558 行で作る `@{ ip = $ip; port = $port }` のハッシュテーブル配列）に対して、
658 行 `Group-Object -Property ip` と 661/681 行 `Select-Object -ExpandProperty port` /
`-ExpandProperty ip` を使っていた。**Windows PowerShell 5.1 の `Group-Object -Property` /
`Select-Object -ExpandProperty` は、ハッシュテーブルのキーをプロパティとして解決しない**
（`Group-Object` は例外を出さず全件を1グループ（Name空）にまとめる。`-ExpandProperty` は
`PSArgumentException`「プロパティ "port" が見つかりません」）。`$_.ip` のような直接のメンバー
参照は 5.1 でも動くため、357 行 `Sort-Object @{Expression={ $_.ip }}` や 596 行
`ForEach-Object { ... $_.ip }` は無事だった。空集合では 658〜687 行のブロックが実質何もしない
ため、許可先が1件以上になるまでこの不具合は顕在化しなかった。

なお pwsh (PowerShell 7) ではハッシュテーブルのアダプタの挙動が異なり、`-ExpandProperty` /
`Group-Object` ともに正しく動作する（実機で確認、下記）。この不具合は**5.1 固有**であり、
pwsh での検証だけでは再現・修正確認ができない。

## 修正内容

### `scripts/apply-sandbox-allowlist.ps1`

658〜687 行のルール作成ループを、`Group-Object` / `-ExpandProperty` を一切使わず、素の
`foreach` + 直接メンバー参照（`.ip` / `.port`、5.1 でも動く）で IP ごとのポート集約を作る方式に
書き換えた。あわせて IP の処理順を IPv4 数値の昇順に固定し（`Sort-Object { ConvertTo-Ipv4Value
$_ }`）、`tcp-<N>` がどの IP に対応するかが要求ファイルの並び順に依存しない決定的な割り当てに
なった（従来はたまたま Group-Object の走査順＝だいたい挿入順だったが、保証されていなかった）。
ヘッダーに他3サイクルと同じ体裁で原因と再発防止の注記を追加。ルール名リテラル・`-LocalUser`
/ `-Group` / `-ErrorAction Stop` / `| Out-Null` の形、ロールバック catch のバイト一致アンカー等
既存ガードが見ている部分は一切変更していない。

### 新規: `scripts/tests/test-apply-sandbox-allowlist.ps1`

Windows PowerShell 5.1・**非管理者**で実行できる、apply スクリプト全体（ルール作成・世代切替・
失敗時ロールバック・拒否理由・リンク拒否）を実際に動かすテストハーネス。ASCII のみ、ゼロ引数。

- ケースごとに本番スクリプトの**コピー**を一時フォルダへ作り、そのコピーの中だけ3箇所を
  置き換える: (1) `$ProgramDataDir` を一時フォルダへ、(2) サービス SID 解決を固定値スタブへ、
  (3) `$ErrorActionPreference = "Stop"` の直後に、`New-/Get-/Remove-NetFirewallRule` を
  差し替えるスタブファイルの dot-source を1行挿入。この3つのアンカー文字列は実行前に実在確認し、
  見つからなければテストを即失敗させる（将来 apply 側が変わってテストが無言で無意味化する事故の
  防止）。**本番スクリプトには引数・環境変数・設定による切替を一切追加していない**（タスクが
  引数を取らない設計、開発者が SYSTEM の動作を変えられない前提を維持）。
- ファイアウォールコマンドは呼び出しを JSON ファイル（`rules.json`）に記録する代わりの関数へ
  差し替え、本物のルールには一切触らない。`PowerShell` の「関数 > cmdlet」解決順序を利用して
  いるため、Linux 上の pwsh（NetSecurity モジュール自体が存在しない）でも、Windows 上（モジュール
  が実在する）でも同じに動く。
- 失敗の注入（throw / 非終端エラー / 無言で作らない）は、スタブ生成時に埋め込んだコール数カウンタ
  と環境変数（`DEVRELAY_SBTEST_FAIL_MODE`/`_AT`、テストハーネス自身が生成・設定する値のみ。本番
  スクリプトはこれらを一切読まない）で制御。
- a〜g の全ケースを実装（空集合/1件/同一IP2ポート/2IP順序/世代切替の作成→実在確認→削除の順序/
  throw・無言失敗・非終端エラーの3種別のロールバック/拒否理由8種+おまけ1種/request.json が
  シンボリックリンクの場合の拒否、非管理者でリンクを作れない環境は SKIP 表示）。1行1ケースで
  PASS/FAIL/SKIP、最後に件数、1件でも失敗なら終了コード0以外。

### Linux 側のガード（`agents/linux/tests/sandbox-scripts-guard.test.mjs`）

- 新規ファイルを ASCII ガード（A1）・`List[object]` への `@()` 禁止ガード（E1）の対象リストへ
  登録。
- G1: apply のコード行に `Group-Object` が無いこと（今回の不具合の再発防止）。
- G2: apply の `-ExpandProperty` は本物の CIM オブジェクト相手の `-ExpandProperty Name`（1箇所、
  `Get-ManagedRuleNames` 内）のみであること。
- G3: テストハーネスが置き換える3つのアンカー文字列が apply に実在すること（上記の「見つから
  なければ即失敗」をテスト側だけでなく静的にも二重に保証）。

### 新規: `agents/linux/tests/sandbox-apply-full-script.test.mjs`

pwsh があれば `test-apply-sandbox-allowlist.ps1` を実際に実行し、終了コード0・全ケース PASS を
確認する（`sandbox-ipv4-range-math.test.mjs` と同じ `SANDBOX_TEST_PWSH_PATH` フック）。pwsh が無い
環境（この VPS を含む）では自動スキップ。ファイル冒頭コメントに「この不具合は5.1固有で pwsh では
再現しないため、このテストが緑でも5.1の実機バグが直っている証明にはならない。証明しているのは
許可リスト反映フロー全体（PowerShell バージョンに依存しないロジック）が正しいこと」と明記。

## 検証結果

- pwsh 7.7.0 を `/tmp` に一時展開して実行確認（コミット対象外、作業後に削除済み）。
  - `test-apply-sandbox-allowlist.ps1` を実行し a〜g 全18ケース PASS（0 fail, 0 skip）を確認。
  - ハーネス自身の健全性確認: (1) ケース b の期待値を意図的に誤った値へ書き換えたコピーで実行し、
    該当ケースのみ FAIL・他は PASS になることを確認（アサーション機構が空振りしていないことの
    サニティチェック）。(2) 修正前（git HEAD、`Group-Object` 使用）のスクリプトに対して同じ
    ハーネスを実行し、全18ケース PASS になることを確認（= pwsh では5.1 固有バグを検出できない
    という上記の限界を実機で裏付け）。
  - `node --test tests/sandbox-apply-full-script.test.mjs`（`SANDBOX_TEST_PWSH_PATH` 指定）:
    pass。同テストを pwsh 無しで実行し、スキップとして正しく扱われることも確認。
- `node --test tests/sandbox-scripts-guard.test.mjs`: 69件 pass（新規 G1〜G3 含む）。
- `node --test --test-concurrency=1 tests/`（agents/linux 全体）: 1800件中 1798 pass / 2 skip
  （既存の pre-existing skip）/ 0 fail。
- `.ts` ファイルは無改造のため `pnpm build` 不要・サービス再起動不要。
