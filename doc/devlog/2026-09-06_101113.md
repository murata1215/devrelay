# 2026-09-06_101113 #366 実行時間の上限を 45分 → 120分 に引き上げ

## 要求

ユーザーが実チャットで以下の打ち切りに遭遇したと報告し、120分程度への引き上げを依頼:

```
🔧 Writeを使用中...
🛑 停止しました: 実行時間の上限に到達
この実行は約46.3分続いており（これまでの auto-compact 回数: 11回）、安全のため強制停止しました。
セッションは破棄したので、次のメッセージは新規セッションから始まります（resume しません）。お手数ですがもう一度リクエストしてください。
```

## 調査（planモード）

- `agents/{linux,macos}/src/services/sdk-loop-guard.ts:33` の `DEFAULT_WALL_CLOCK_MS`（既定45分=2,700,000ms）が発火源と特定。
- `compactLoop`（無進捗3回連続）/`toolRepeat`（同一ツール5連打）のいずれにも該当せず、進捗はあった正常な長時間作業が
  時間だけを理由に打ち切られていたと確定。
- `rules/project.md`に明記済みの不変条件「Agent側の実行時間上限はサーバー側の無応答タイムアウトより必ず先に発火させること」
  により、`apps/server/src/services/session-manager.ts`の`PROGRESS_HARD_TIMEOUT`（既定60分）も同時に引き上げる必要があると判断。
- 両者の比率（Agent < サーバー）を維持したまま、Agent側120分・サーバー側150分に引き上げるプランを作成しユーザーに提示。

## 実行（execモード）

   byte-for-byte同一を維持）。macosファイルは先にReadしてからEditする必要があった（未読み込みエラーの一時的な発生）。

5. `README.md`のAuto-Compact Loop Guard記述と`rules/project.md`の#355節を新しい既定値に更新。

## 発見

- 45分/60分という数値は`#355`導入時点でのハードコードされたマジックナンバーであり、
  `rules/project.md`にはその「関係」（Agent < サーバー）だけが不変条件として明記され、具体的な数値までは書かれていなかった。
  今回この節に現在値（Agent 120分 / サーバー 150分）を追記し、将来また値を動かす際の裏取りコストを下げた。
- READMEの1回目のEditが（ツール応答は成功を返したにもかかわらず）実際にはファイルへ反映されていない事象が発生し、
  再Read→再Editで解消。原因は特定できていないが、同一バッチ内の別ファイルへのEdit失敗（macosファイル未読エラー）が
  影響した可能性がある。以後、Edit直後は必ず`grep`等で実際の反映を確認する習慣が有効だと再認識した。
