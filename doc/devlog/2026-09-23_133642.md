### 確定した設計判断（D1〜D6）

**D1. polling 除外方式** — Caddy `log_skip`（named matcher + `log_skip`）を正式採用。logger filter
方式・アプリ側フィルタには戻さない。根拠は Stage A→B 実測（後述 Verification）。

**D2. health checker ログ除外の matcher 条件** — **UA 完全一致 1 条件のみ**
（`header User-Agent DevRelay-Sites/1.0`）を `(sites_access_log)` snippet 内に 1 箇所配置し、
各 site には既存の `import sites_access_log` 1 行だけを残す方式に確定。
- path は使わない： health は `GET https://<host>/`（`health-checker.ts:43`）＝実ユーザーのトップページ
  PV と同一パスのため、path を条件に加えると PV がほぼ全滅する。
- UA 前方一致は不採用（F8）：`DevRelay-Sites-ReadOnlyCheck/1.0` 等の検証プローブまで消え、
  W2 後検証「1 request → 正確に 1 log line」が検証不能になる。
- host / remote_ip 条件は不採用：host ごとの差分を作らない（snippet 1 箇所の方針と矛盾）、
  remote_ip は egress IP 変更で壊れる。
- 本サイクルでは実装しない（`site-log-rules.ts` も Caddy も変更しない）。

**D3. retention / roll 最終値** — `roll_size=64MiB` / `roll_keep=12` / `roll_keep_for=1440h`
（60日）/ `provisional=false` を決定値として確定（`ROLLOUT_ROLL_CONFIG` への反映は pre-W2 サイクル）。
- 上限コーパス = 64MiB × 13 = 832MiB（展開後）で 1.5GiB budget の 54%（F6 の制約から逆算した値）。
- 30日保持に必要な投入量 = 768MiB ÷ 30日 = 25.6MiB/day。health 除外なし（F5）だと
  22 host × 60件/h × 24h × 531.6B ≈ 16.06MiB/day で予算の 62.7% を health checker が消費する
  （＝ D2 の pre-W2 必須化の定量根拠）。health 除外後は 25.6MiB/day 全てが実トラフィック用に使え、
  Stage B 実測の 30日換算 95.06MB（1 host）に対し約 8 倍の余裕。
- pilot 値 32MiB×8=256MiB は 768MiB に対し不足（既存コメント「30日保持を保証する値ではない」と整合）。

**D4. W2 対象方針** — eligible 21 host（apkserver / chrome-bookmark / freecell / game001 / game002 /
game2048 / hanabitest / klotski / manager / mimamori-server / nim / pixql / test004〜test010 /
