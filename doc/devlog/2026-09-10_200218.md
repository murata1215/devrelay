# Lite シェル L3: WS 接続 + メッセージ読み取り（+ L2 手直し）

## Context

L0〜L2（commit `06132a6`）で `/lite` は「開けるが通信しない」空シェルまで到達済み。
本サイクル L3 の目的は **`/lite` で選択中スレッドの会話を読めるようにする**こと（WS 受信 + REST 履歴）。
送信は L4、承認/質問カードの操作は L5。

戦略 B（`ChatPage.tsx` は diff 0、Lite は既存フック + `ThreadList` のみ再利用）を維持した。
参照プラン: `~/.claude/plans/refactored-cooking-thunder.md`。
L2 devlog: `doc/devlog/2026-09-10_092305.md`。

## 実装前に報告し、ユーザーから明示的な承認を得た 5 件の齟齬（プラン本文より）

詳細はプラン本文（S1〜S5）参照。結論のみ記す。

- **S1（最重要）**: サーバーの配信は `sessionParticipants`（`chatId = web:${userId}:${tabId}`）単位。
  スレッド選択時に `POST /api/sessions/:id/switch`（`sessionsApi.switchThread`）を呼ばないと
  Lite には WS メッセージが一切届かない（エラーも出ない）。
- **S2**: 参加登録は「選択時」ではなく「`connected` の立ち上がりエッジ」で発行する
  （依存配列 `[connected, selectedSessionId, tabId]`）。Lite は `//connect` を送れないため。
- **S3（A2）**: classic の絞り込み条件（`GET /api/machines` の `where: userId, deletedAt: null`）は
  共有できるクライアント述語が存在しない。`GET /api/projects` を情報源のまま維持し、
  `GET /api/machines` の id 集合を「生存マシンの許可リスト」として交差させる案を採用。
- **S4（A3）**: 並び順（`lastActiveAt desc`）はサーバー・`ThreadList` 側で解決済み。コード変更なし、
  回帰テストのみ追加。プロジェクト未選択時は横断一覧を維持（指示の「プロジェクト切替で
  スレッド一覧が切り替わり」は仕様と矛盾するため、E2E-3 は「混入しない」の確認に読み替え）。
- **S5**: `readOnly` を解除しない（L2 申し送り #3 からの方針転換）。解除すると `ThreadList` 自身が
  `switchThread` を撃つ第 2 の経路ができ、S2 の `connected` ゲートが効かなくなるため。
  `onLocalSelect` を受けた `LitePage` が switch の唯一の所有者になる。

## 追加調査（人間の承認条件 2/4 に基づく）

### S6: StrictMode 二重実行・再接続時の参加登録レースの調査

E2（参加登録）の effect にはクリーンアップ関数が無いため、React 18 StrictMode（開発時のみ）の
二重マウントで effect 本体が 2 回連続実行され、`switchThread` の POST が同一 `(sessionId, tabId)`
に対して 2 回連続で飛ぶ。実際にレースになり得るか、サーバー側 `addParticipant()`
（`session-manager.ts:330`）を確認した:

```ts
export function addParticipant(sessionId: string, platform: Platform, chatId: string) {
  const participants = sessionParticipants.get(sessionId) || [];
  // Avoid duplicates
  if (!participants.some(p => p.platform === platform && p.chatId === chatId)) {
    participants.push({ platform, chatId });
    sessionParticipants.set(sessionId, participants);
  }
}
```

`(platform, chatId)` の組で重複排除しており冪等。よって StrictMode の二重発火は
「無害な二重 POST」に留まり、参加者リストが壊れることはない。

再接続（`connected` が false→true に反復する）ケースも同じ経路（`addParticipant` の冪等性）で
吸収される。スレッドを跨いだ切替（A→B）のレースは `switchChainRef`（promise チェーン直列化）で
POST の到着順を保証しているため、サーバー側 `currentSessionId` が古いまま残ることもない。

**結論**: 実測・コード読解の範囲で「保証されない順序に起因する実害のあるレース」は見つからなかった。
StrictMode 二重発火は許容し、コード変更（クリーンアップ関数の追加等）は行わない。

### 「switchThread は Session.lastActiveAt を更新するか」（人間の承認条件 4）

`switchChatToThread()`（`command-handler.ts:623-664`、`POST /api/sessions/:id/switch` の実体）の
本文を全文確認したが、`prisma.session.update` は `status: 'active'`（ended からの再活性化時のみ）
の 1 箇所のみで、`lastActiveAt` への言及は無い。

`touchSessionActivity()`（`session-manager.ts:321`、`lastActiveAt` の唯一の更新箇所）の呼び出し元を
全文検索すると:

```
apps/server/src/mcp/tools.ts:632
apps/server/src/services/command-handler.ts:1034
apps/server/src/services/command-handler.ts:1871
```

の 3 箇所のみで、いずれもメッセージ送受信系のコードパス（`switchChatToThread` の呼び出し元とは
別のハンドラ）である。

**結論**: `switchThread` は `lastActiveAt` を更新しない。`lastActiveAt` はメッセージの送受信でのみ
更新される。したがって Lite でスレッドを**閲覧するだけ**（メッセージを送らない）操作は
スレッド一覧の並び順（S4 の `lastActiveAt desc`）に影響しない。L4 以降で送信を実装したときに
初めて並び順が動く。

### LitePage.tsx の設計

- **URL が唯一の状態**（`useSearchParams`）。`?project=<id>&session=<id>`。
- **tabId はマウント時にメモリ生成**（`useRef` + `crypto.randomUUID()`、永続化しない）。
  `useWebSocket` の options と `sessionsApi.switchThread()` の両方に**同一の `tabId` 変数**を渡す
  （絶対規則。食い違うと参加登録 chatId とソケット chatId が別物になり、エラーなしで WS が無音になる）。
- **E1（`[]`）**: `projects.list()` と `machines.list()` を並行取得。`machines.list()` の失敗は
  `liveMachineIds` を `null` のまま維持（fail-open）。`projects.list()` の失敗とは独立に扱う
  （`Promise.all` にしない）。
- **E2（`[connected, selectedSessionId, tabId]`）**: `connected` かつ `selectedSessionId` が
  あるときのみ `switchChainRef`（promise チェーン直列化）経由で `switchThread` を発行し、
  成功後 `historyEpoch` をインクリメントする。`.catch(() => {})` を必ず挟み、1 回の失敗で
  チェーンが永久に詰まらないようにする。
- **E3（`[selectedSessionId, historyEpoch]`）**: `connected` を依存に入れない（瞬断のたびに
  再取得ループになるため）。`historySeqRef` で stale 応答を破棄。直前の `selectedSessionId` との
  比較で `mode: 'replace'`（スレッド切替）/ `'refresh'`（同一スレッドの再取得）を判定し、
  `mergeHistory()` に渡す。
- **受信振り分け**: `decideInboundDisplay()`（fail-open）。承認カードのみ `shouldShowApprovalCard()`
  （fail-closed、R5 の唯一の例外）。
- **`readOnly` を維持**したまま `<ThreadList onLocalSelect={...} onSelect={() => {}} />`。
  行クリックは URL 更新のみを行い、`switchThread` の発行は E2 が一元的に行う
  （switch の所有者を単一化。S5）。
- 破棄した識別子: `useWebSocket()` の戻り値から `connected` のみを分解し、`sendCommand` /
  `sendToolApprovalResponse` を一切destructureしない（静的走査テストで固定）。

## L4 への申し送り

1. **tabId の扱い**（絶対規則）: `LitePage.tsx` がマウント時にメモリ生成し（`crypto.randomUUID()`、
   永続化なし）、`useWebSocket` と `sessionsApi.switchThread()` の**両方に同一値**を渡している。
   L4 で送信（`threads.create()` 等）を実装する際も、必ずこの同一 `tabId` 変数を使うこと。
2. **`POST /api/threads` に必要な引数**: `tabId` 必須（R8）。渡し忘れると `lastProjectId` /
   `currentSessionId` が更新されず、直後の送信が「既存スレッドへの意図しない合流」（F1）に落ちる。
   UI 上は成功に見える。
3. **`session_info` の到着タイミング**: `/switch` の 201 応答**前**に `pushSessionInfoToChat` 済み
   （サーバー実装。L4 で応答待ち処理を書く際に前提として注意）。
4. **A3 の確定キー** = `lastActiveAt desc`（NULL はサーバー側で `startedAt` に解決済み）。
   **今回新たに確認した事実（承認条件 4）**: `lastActiveAt` は `switchThread` では更新されず、
   メッセージ送受信（`touchSessionActivity()`）でのみ更新される。したがって Lite で
   スレッドを閲覧するだけでは並び順は動かない。L4 で送信を実装すると初めて動くようになる。
5. プロジェクト未選択時は横断一覧（仕様どおり。指示 E2E-3 との差異は S4 参照）。
6. S5 により `readOnly` は維持されている。L4 で「＋新規」を有効化する際は switch の所有者が
   `LitePage` 単独であることを壊さないこと。
7. `switchChatToThread` は web では旧セッションから `removeParticipant` しない
   （`command-handler.ts:640`、`platform !== 'web'` のガードで除外）。Lite の chatId は
   閲覧した全スレッドの参加者として蓄積し、表示の正しさは sessionId ゲート
   （`decideInboundDisplay`）が担保している。L4/L5 でここを「修正」しようとしないこと。
8. **S6（StrictMode/再接続の参加登録レース、承認条件 2）**: `addParticipant()` が
   `(platform, chatId)` 冪等のため、StrictMode 二重発火・反復再接続はいずれも無害な二重 POST に
   留まることを実測確認済み。`switchChainRef` による直列化と合わせて、実害のある順序レースは
   見つからなかった。L4 で新たに POST 系の effect を追加する際も、このパターン
   （冪等なサーバー処理 + クライアント側の直列化）を踏襲すること。
