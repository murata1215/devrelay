## 調査結論: 報告された「主バグ」は実際には発生していなかった

指示にあった主バグ:

> 23:30:51 `cmtw5ute200f410yxrqa7cu5m`: その直後の送信「３＋３は？」が上のスレッドに入らず、
> 別スレッドとして作成された（2 件）← 主バグ

`/home/devrelay/.pm2/logs/devrelay-server-out.log` の該当時刻帯を直接 Read してフォレンジックを行い、
これは**成立していない**と確定した。

| 時刻 (UTC) | サーバーログの実際のリクエスト列 | 判定 |

| 23:26:19 | `PUT /api/settings/tab_order` → `PUT /api/settings/chat_servers` → `GET /api/threads?projectId=...` → `server:session:start` → `GET .../messages?limit=10` | **classic タブ**のプロジェクトタブ追加（`//connect`）が `cmtw5ozul` を作成 |

送信は 23:30:51 の**約 2 分半後**であり、その時点で新規スレッド作成 API は一切呼ばれていない。
`decideSendAction` は正しく `send-existing` を返していた。

**空スレッドが 4 件に見えた真因は「一覧が自動更新されないこと」**だった。Lite の左一覧が
`POST /api/threads` 201 の後も更新されないため、人間は作成が失敗したと思って「＋新規」をもう一度
押した。残り 2 件（`cmtw5ozul`/`cmtw5w7zr`）は classic タブ由来。

**自己修正メモ**: 当初、`psql` で引いた `Session.startedAt` を送信時刻と誤読し「送信直後に新規
スレッドが作られた」と結論しかけたが、サーバーログの実際のリクエスト順で突き合わせた結果、
`startedAt` は「＋新規」ボタン押下 2 回それぞれのスレッド作成時刻であり、送信はその後継続して
既存スレッドに入っていたことが判明した。ログの相関を取らずに DB のタイムスタンプだけで
「主バグが発生した」と即断しかけた点は反省点。

→ 「Lite 側に二重 POST の経路は無い。人間操作（Lite 2 回 + classic 2 回）由来」
→ 「一覧が再取得されれば `firstUserMessage` 由来のタイトルは自動で出る」
  （`Session.title` が NULL でも `GET /api/threads` が先頭ユーザーメッセージ 60 文字を返すため。
  server 変更不要）

## ただし実在する潜在レースが 1 件あった（今回これも塞いだ）

`apps/web/src/App.tsx` は `<BrowserRouter>` を素で使っており、react-router-dom v7 は history 更新を
`React.startTransition` でラップする。そのため URL 由来の `selectedSessionId` / `selectedProjectId` は
**低優先度**でコミットされるのに対し、`setThreadProjectConfirmation` / `setCreatingThread(false)` は
**通常優先度**でコミットされる。この隙間（URL がまだ追いついていない瞬間）に送信すると
`decideSendAction` が `create-then-send` を返し、**重複スレッドが実際に作られる**構造的な穴があった。

通常優先度で確実に取れる「URL がまだ追いついていない」シグナルとして
`threadProjectConfirmation.sessionId !== urlSessionId` を `inFlight` の追加条件に採用した。

## 実装

### 1. `apps/web/src/components/lite/lite-shell-rules.ts`（純追加）
- `resolveSendInFlight()`: `sending || creatingThread` に加え、`confirmationSessionId` /
  `requestedProjectId` が非 null かつ URL の値と不一致なら true。情報が無い（null）ときはブロック
  しない（fail-open）。
- `resolveConfirmationOnProjectChange()`: プロジェクト切替時、`confirmation.projectId` が新しい
  projectId と異なれば `threadProjectConfirmation` を `null` に落とす。これが無いとプロジェクト
  切替後に古い confirmation が残り `resolveSendInFlight` が永久に true になり送信不能になる。
- `decideThreadListRefresh()` + `THREAD_REFRESH_MIN_INTERVAL_MS = 1500`: leading + trailing throttle。
  初回・窓外は即時、窓内はタイマー予約、既に予約済みなら skip。

### 2. `apps/web/tests/lite-shell-rules.test.mjs`（26 ケース追加）
- `resolveSendInFlight`: sending/creatingThread 単独、「＋新規」直後（confirmation は新 sessionId・
  URL はまだ旧値）→ true、追いついた後 → false、confirmation=null → false（fail-open）、project 軸の
  未追従、両軸 null → false
- `resolveConfirmationOnProjectChange`: 同一 projectId は保持／異なれば null／null 入力は null
- `decideThreadListRefresh`: 初回 refresh-now／窓内 schedule／窓内 pendingTimer あり skip／窓外
  refresh-now／境界 `elapsed === 1500` → refresh-now
- `decideSendAction` の「＋新規 直後」ケースの固定: 新スレッドの sessionId/projectId が選択済みなら
  `send-existing` を返す（新スレッド ID を維持）ことと、`resolveSendInFlight` が true の窓では
  `blocked/in-flight` になることをペアで固定

### 3. `apps/web/src/pages/LitePage.tsx`（配線）
- `creatingThreadRef` / `requestedProjectIdRef` を追加（`sendingRef` と同じ流儀の同期読み取り用）
- `handleProjectChange` で `requestedProjectIdRef.current = projectId` + 
  `resolveConfirmationOnProjectChange()` で古い confirmation を破棄
- `currentSendAction` と `handleSend` の `inFlight` 計算をどちらも `resolveSendInFlight(...)` に置換
- `<LiteComposer sending={sending || creatingThread} />`（作成中もボタンを `…` にする）
- `threadRefreshToken` state + `requestThreadRefresh()`（`decideThreadListRefresh` 使用、
  `lastThreadRefreshAtRef` / `threadRefreshTimerRef`、アンマウント時 `clearTimeout`）
- `<ThreadList refreshToken={threadRefreshToken} .../>`（`ThreadList.tsx` 自体は無変更、既存の
  `refreshToken?`/`useEffect` を再利用）
- `useWebSocket` に `onSessionInfo` / `onReconnect` を追加。どちらも `requestThreadRefresh()` を
  呼ぶだけで **`setSearchParams` は呼ばない**（`session_info → setSearchParams → E2 → switchThread
  → session_info` の無限ループ防止）
- `handleMessage` 先頭（`decideInboundDisplay` の early-return より前）で `requestThreadRefresh()`
- `handleRequestCreate` の 201 直後、`handleSend` の送信成功直後にも `requestThreadRefresh()`
- `visibilitychange` + `window.focus` で `requestThreadRefresh()` する effect（`setInterval` は
  使わない。classic タブでの操作は Lite の WS には届かないため、タブ復帰時に手動で補う）
