# #344 Devin CLI が `(No response from AI)` で沈黙する問題の解消 + argv 経路のコマンド注入穴の削除

## 要求

ユーザー報告（実機 `devin --help` 出力添付）:
「次はdevin。新しいバージョンにしたらエラーになっちゃった。(No response from AI)はやだなー」

貼られた `--help` 出力では `--prompt-file`/`--permission-mode`/`--model`/`--export`/`--agent-config` の
5フラグ全てが実在するのに、DevRelay 側の判定は5つ全てを「非対応」としていた。個別の正規表現ミスでは
ありえない一致率のため、`probeDevinCapabilities()` の catch ブロック（全部 false にする経路）に落ちて
いると特定。プランファイル `vivid-waddling-boole.md` の「新規サイクル #344」（§32-38）としてコードを
読み込み根本原因を確定し、フル実装を実行モードで承認された。

## 実行

真因は連鎖的：probe 失敗 → 全フラグ非対応と誤判定 → `devin.readonlyUnsupported` 誤警告 →
`--prompt-file` も非対応と誤判定され `args.push('--', prompt)` の argv フォールバックへ落ちる →
Node の `spawn(..., {shell:true})` は引数をクォートしないため、DevRelay が毎回前置する
~170 行の Agreement/プランモード指示（`\n\n` やバッククォートを含む）がシェルに解釈され devin が
即死 → stderr が `unexpected argument` 正規表現に一致せずリトライ分岐にも入らない → exit 0 分岐にも
入らない → 汎用 `(No response from AI)` に落ちる。実証済みの通り、この argv フォールバックは
「壊れているから直す」ではなく「危険だから消す」対象（任意コマンド実行経路）と判断。

3 OS（`agents/{linux,macos,windows}`）の `ai-runner.ts` に対して以下を実施：

1. **新規 `cli-failure.ts`**（外部 import ゼロの純関数、linux/macos/windows で byte-for-byte 同一を
   `diff` で確認）。`classifyCliFailure()` が `stdoutLength>0→none`／`exitCode===null→none`（シグナル
   kill は CLI 自体の失敗ではない）／`unexpected argument`→`unknownFlag`（フラグ名付き）／
   command-not-found 系メッセージ→`commandNotFound`／`exitCode===0`→`emptyExitZero`／それ以外→
   `emptyNonZero` の順で判定し、`stderrTail`（末尾 maxLines 行、既定5）を返す。`agents/linux`/`macos`
   に `cli-failure.test.mjs`（15ケース）を追加、`windows` は `tests/` ディレクトリ自体が存在しない
   ため `diff` のみで担保（既存の repo 流儀を踏襲）。
2. **`packages/shared/src/i18n.ts`**：`devin.promptTooLongForArgv` を削除（argv 経路自体の廃止に伴い
   不要）、`ai.cliNotFound`／`ai.cliFailed`／`devin.probeFailed`／`devin.promptFileUnsupported`／
   `devin.execPermissionUnsupported` の5キーを ja/en で追加。
3. **`probeDevinCapabilities()` を「失敗したら楽観」に反転**。従来は probe 失敗時に全フラグ `false`
   （悲観）としていたが、これは「実際は devin が正しく対応しているのに probe だけが（PATH 不在・
   更新直後のキャッシュ汚染・`--help` の非 0 終了等で）失敗した」場合に誤った非対応警告と危険な
   argv フォールバックを静かに発動させる。楽観側に倒しても、実際に非対応だった場合は
   `unexpected argument` を検出する既存の自動リトライ（#329、最大3回に引き上げ）が安全網として
   受け止める設計。失敗キャッシュのみ `DEVRELAY_DEVIN_PROBE_TTL_MS`（既定60000ms、#321 の env
   命名流儀）で期限切れにし、成功キャッシュは Agent プロセス寿命いっぱい保持（キャッシュ汚染=H3
   仮説を構造的に解消）。
4. **誤警告の解消**：`devinReadonlyDegraded: boolean` を `devinDegradedReason: 'planReadonly' |
   'execPermission' | null` の理由 enum に置き換え、`devin.readonlyUnsupported` は probe が実際に
   成功して「無い」と判定した（`ok===true`）ときだけ出す。exec モードで `--permission-mode` が無い
   場合は新設 `devin.execPermissionUnsupported`（従来 plan 用の文言が誤って出ていた3つ目の分岐）。
   `ok===false`（probe 自体が失敗）のときは `devin.probeFailed` をプロセス寿命中1回だけ出す。
5. **★本丸★ argv フォールバックを削除**。常に `--prompt-file` を使用し、probe が成功してなお
   `--prompt-file` が無いと判明した場合のみ `devin.promptFileUnsupported` で明示的に中止（静かな
   フォールバック禁止、#325 の原則）。
6. **catch-all の置き換え**：既存の分岐（unknownFlag 自動リトライ、devin exit-0 空応答案内、
   devinPlanToolRejected フォールバック等）は1つも触らず、それらに該当しなかった残りのケースだけを
   `classifyCliFailure()` で分類。`commandNotFound`→`ai.cliNotFound`（`u` での再検出を案内）、
   `emptyNonZero`→`ai.cliFailed`（exit code は stderrTail が空でも必ず出す）、それ以外（`none` /
   安全網としての `unknownFlag`/`emptyExitZero`）は従来どおり `(No response from AI)`。
7. **PATH 汚染の是正**：`config.aiTools.devin.command` はベース名のみ保存されるため
   `path.dirname(command)` が `'.'` になり得る（プロジェクトの cwd が PATH の先頭に積まれ、
   悪意あるリポジトリの `git`/`node` を拾う穴）。devin/gemini 両方に `dir === '.'` ガードを追加。

## 発見（検証中に見つかった軽微な逸脱、プラン §37 のとおりに解釈して対処）

1. **`grep -rn "No response from AI" agents/*/dist/` が 0 件にならない（linux/macos 各5件、windows
   3件）**。内訳を全て特定した：
   - `sendPromptToAiSdk()`（Claude Agent SDK 直呼び出し関数、linux/macos のみ存在）内の2箇所。
     これは `classifyCliFailure()` の対象である spawn ベースの `sendPromptToAi()` とは**別関数**で、
     プロセスの exit code / stderr という概念自体を持たないため設計上スコープ外。
   - devin の `.catch()` リトライ失敗ハンドラ2箇所（#329 の unknownFlag 自動リトライ、
     devinPlanToolRejected フォールバックが**リトライ呼び出し自体で JS 例外を投げた**場合の保険）。
     プラン Step 6 が明示する「既存の分岐は1つも触らない」の対象そのもの。
   - 新設した catch-all 自身の `else` 分岐1箇所（`classifyCliFailure()` の `kind==='none'`
     ＝シグナル kill 等、CLI 自体の失敗ではないケース）。プランの分岐表で「`none`: 従来どおり」と
     明記されている想定どおりの挙動。
   - windows は `sendPromptToAiSdk()` を持たない（SDK 不使用）ため2件少ない3件で、差分も設計どおり。

   結論：プランの §37 検証項目5「`grep -rn "No response from AI" agents/*/dist/` = 0」は文字どおりには
   満たさないが、実体は「危険な argv フォールバックが握りつぶしていた実エラーを可視化する」という
   本サイクルの目的（catch-all の該当ケース）を完全に達成しており、残る5件（3件）はいずれも
   プラン自身が「触るな」と明記した既存分岐またはスコープ外の別関数。この判断をここに記録する。

2. **`'--', prompt` の comment-only false positive**：削除した実コードの説明として書いたコメント
   自身に `'--', prompt` という部分文字列が含まれ、grep が誤検出した（実害なし、コード自体は
   ビルド済み dist から完全に消えている）。文言を言い換えて解消し、最終的に0件を達成。

3. **macos の JSDoc に古い矛盾した一文が残存**：`probeDevinCapabilities()` の JSDoc に
   「失敗時は全て false（＝最小フラグ `-p` のみで動かす安全側）に倒す。」という反転前の説明が、
   #344 の反転後の説明パラグラフの直前に取り残されていた（linux は正しく更新済み）。削除して
   linux と構造を一致させた（ロジック変更なし、コメントのみ）。

## 反映

DB マイグレーション不要、`apps/server`/`apps/web` 無変更のため server 再起動不要。
Agent 側の修正が本体のため、**各マシン（Linux / macOS / Windows CLI Agent）の `u` が必要**。
