# サイクル: MCP 添付の E2E 検証（#358 Part A + B、検証専用サイクル）

## 要求

#358（2026-09-05）で MCP `submit_instruction` に添付ファイル対応（Part A: サーバー側検証
`attachment-validation.ts`）と、Agent 側のパストラバーサル対策（Part B:
`sanitizeSavedFilename()` + `resolve()` 封じ込め）を実装したが、実際に添付を送った E2E は
一度も行っておらず、テストの green も実測していなかった。本サイクルはコード変更を一切行わず、
実サーバー・実 Agent・実 DB に対して以下を実測する検証専用サイクル。

- Phase A: 4 workspace（shared/server/agents-linux/agents-macos）の `node --test` を個別実行し実件数を報告
- Phase B: 稼働中サーバーが Part A を実際に含むかを `tools/list` で実証（ゲート）
- Phase C: 異常系 7 ケース（トラバーサル・dotOnly・MIME 不許可・MIME 不一致 2種・サイズ超過・base64 不正）を正常系より先に実行し副作用ゼロを確認
- Phase D: 正常系 3 ケース（PNG/txt/md）でバイト一致・保存・プロンプト前置を確認
- Phase D2: トラバーサルケース（C1）を追跡し Part B の到達性を実証
- Phase E: 監査記録（`Message.humanTextMeta`/`MessageFile`）を確認

認証は本番 DB 書き込みゼロを厳守するため、`AuthSession` のうち
`expiresAt > now() + interval '15 days'` の行のみを `SELECT` して使用し、
`maybeExtendSession()` の自動延長書き込みを回避した。

いずれも無出力（byte-for-byte 同一）。#358 の完了報告どおりの件数を実測で裏取りできた。

### Phase B（疎通と Part A の生存証明）

`AuthSession` を1件取得（`expiresAt` 2026-10-04、対象プロジェクト`test010`のオーナーと
`userId` 一致を確認）。`/tmp/dr358/mcp.mjs`（SSE 枠を剥がす自作ヘルパー、ポートは `.env` の

含む。ゲート通過、続行。**

### Phase C（異常系、正常系より先に実行）

`/tmp/dr358/gen.mjs` で固定フィクスチャ（1x1 PNG 70bytes・JPEG ヘッダ・6MiB の `0x61`・
不正 base64 `"!!!!"`）を生成し、7ケースすべてを `tools/call` で実行。

| # | ケース | 結果 |
|---|---|---|
| C1 | `../../../etc/passwd`（PNG中身） | **拒否されない**。`filename:"passwd"` に basename 化されて**受理**された |
| C2 | `..` のみ | `isError:true`、`failures[0].reason:"filenameInvalid"`（`dotOnly`） |
| C3 | `application/pdf` | `failures[0].reason:"mimeNotAllowed"` |
| C4 | 宣言`image/png`+中身JPEG | `failures[0].reason:"mimeMismatch"` |
| C5 | 宣言`text/plain`+中身PNG | `failures[0].reason:"mimeMismatch"`（`textInvalidUtf8`ではなく画像シグネチャ判定が優先） |
| C6 | 6MiB PNG | `failures[0].reason:"fileTooLarge"` |
| C7 | `content:"!!!!"` | `failures[0].reason:"base64Invalid"` |

副作用確認: `Session`（projectId絞り込み）と `MessageFile` の総件数を各ケース前後で計測した
ところ、C1 実行時にのみ +1 され（C1 は受理されるため）、C2〜C7 はいずれも **増加ゼロ**だった
（`Session`: 9→10 で以降10のまま、`MessageFile`: 2924→2925 で以降2925のまま）。検証ロジックが
`createSession` より前で完結していることを実測で確認。

エラーメッセージの分かりやすさ: 8種の失敗理由のうち6種が top-level `reason:"itemInvalid"` に
集約され、具体的理由は `failures[0].reason` を掘る必要がある。`limits` オブジェクトが同梱される
ため上限値は自明。`fileTooLarge` は magic-byte 判定より先に評価されるため、6MB の MIME 不一致
ファイルは `fileTooLarge` としか報告されない。

## 発見（重要、正直に報告する）

**① パストラバーサルは「拒否」ではなく「サニタイズして受理」——前サイクルの記述と実装が食い違う**

依頼文・前サイクルの整理は「パストラバーサルが拒否される」という前提だったが、実装は
そうなっていない。`attachment-validation.ts` の `sanitizeAttachmentFilename` が hard reject
するのは `empty`/`nulByte`/`dotOnly`/`tooLong` の4つだけで、`../../../etc/passwd` のような
パスは basename 化されて `passwd` として**正常に受理される**。ツール応答は
`filename:"passwd"` を返すのみで、書き換えられた事実を呼び出し元に明示しない。唯一の痕跡は
`humanTextMeta.attachments.sanitizedFilenames` のカウンタで、実測でも C1 のときだけ `1` に
なることを確認した。→ 観測性・UXのギャップとして記録するのみで、本サイクルでは修正しない
（人間の承認ノートの指示どおり）。

**② Part B は MCP 経路では構造的に到達不能——これが本サイクル最重要の実証事項**

`attachment-validation.ts` がサーバー側で basename 化した後の名前（`filename: sanitized.filename!`）
が `tools.ts` から `sendPromptToAgent()` へ渡るため、Agent 側 `saveReceivedFiles()` が受け取る
時点で既に `passwd` であり、`sanitizeSavedFilename()` は何も変更せず、警告も発火しない。
これは Phase D2 で **実測により証明済み**（`/etc/passwd` 無変更・警告 grep 0件）。

**「ファイルが `.devrelay-files/` の中に着地した」ことは Part B が機能した証拠ではない。**
Part B の実際のカバレッジは (a) 各OS 19件ずつの単体テスト、(b) サーバー側検証を持たない
WebUI の `web:command` WebSocket 経路（#358 で発見された、MCP とは独立した既存の穴）。
この二重構造をここに明記する。MCP 経由の E2E を将来何度実行しても Part B の実行時証明には
ならない。

**③ その他の実測差分**

- 8種の per-item 失敗のうち6種が top-level `reason:"itemInvalid"` に集約される
- `fileTooLarge` が magic-byte 判定より先に評価される（6MB+MIME不一致ファイルは
  `fileTooLarge` としか報告されない）
- `textInvalidUtf8` は今回の要求ケースの組み合わせでは発火させられなかった（単独 `0x80` 等が
  別途必要、優先度としては画像シグネチャ判定 → UTF-8判定の順であることをC5で確認済み）
- `totalTooLarge`（合計10MB超過）はE2E不可能（3×4MBのbase64は約16MBになりHTTP 413になり
  別のテストになるため）、単体テストのみでの担保
- `get_attachment` での読み戻し確認は本サイクルの依頼範囲外、残存ギャップとして明記
