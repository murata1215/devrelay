# 2026-09-26 10:09 JST ｜ exec ターンで Write/Edit/Bash が承認待ちのまま失敗する不具合の根治

## 背景

ユーザーから「testflight test010 の exec で実装中に書き込みができなかったみたい。バグかな？」という
報告。添付ログを確認すると、`exec` 承認直後のターンで AI 自身が「Write/Edit/Bash 経由の
python3/pm2/curl/`/bin/true` がすべて `Tool permission request failed: AbortError: Stream closed`
で失敗する。Read/ls/echo/grep/cat は動く」と診断し、DevRelay 側の承認ゲートの不具合を疑って
9 分間リトライした末に 1 ファイルも書けずにターンを終えていた。

Explore サブエージェント3体（`ai-runner.ts`/`connection.ts` のコード調査、plan/exec 遷移とパーミッション
ポリシーの調査、実機ログ・DB・pm2 状態の調査）を並行実行し、実機証拠と SDK バンドル（`sdk.mjs`）の
実装確認を突き合わせて根本原因を特定した。

## 根本原因

`agents/{linux,macos}/src/services/ai-runner.ts` は Claude Agent SDK を
`query({ prompt: <string>, options })` の形（`prompt` が**文字列**）で呼んでいた。SDK
（`@anthropic-ai/claude-agent-sdk` 0.3.282）は文字列 prompt を受け取ると `isSingleUserTurn = true`
を立て、**最初の `result` メッセージを受信した瞬間に CLI サブプロセスへの stdin を閉じる**
（`transport.endInput()`）。この stdin は、CLI がツール承認（`can_use_tool` コントロールリクエスト）を
ホスト（DevRelay の `canUseTool` コールバック）に問い合わせるときの唯一の応答経路でもある。

ところが 2026-09-20 の `840d1e4`（バックグラウンド Agent 対応）以降、DevRelay は「途中 result」
（バックグラウンドタスク稼働中の result や `--resume` 直後に CLI が合成する空 result）を終端とみなさず
`decideResultDeferral()` で延期し、`result` 受信後も for-await ループを読み続ける
（`sdk-background-tasks.ts`）。この「読み続ける」設計と、SDK の「最初の result で stdin を閉じる」
契約が衝突し、**stdin が閉じた状態でターンが続行**されていた。以降 CLI が承認を要するツール
（Write/Edit や許可リスト外の Bash コマンド）を呼ぶたびにホストへの問い合わせが送れず
`Tool permission request failed: AbortError: Stream closed` になる。Read や読み取り専用 Bash
（echo/ls/grep/cat 等）は SDK/CLI 内の安全判定で `canUseTool` 到達前に許可されるため、そこだけ
動いて見えていた。

### 実機証拠（`~/.devrelay/logs/agent.log`）

- 09:33 の**失敗**した exec: `Mode: EXEC` 直後に `🔄 Resuming session` →

- 二重起動・WS 切断・サーバー側承認タイムアウトはすべて実機ログ/DB で否定した

## 修正内容

SDK には「stdin を閉じない」オプションが存在せず、`isSingleUserTurn` は
`typeof prompt === "string"` から機械的に決まるため、**`prompt` を「ターン完了まで完了しない
AsyncIterable」に差し替える**方式で対応した。

- `agents/{linux,macos}/src/services/sdk-prompt-stream.ts`（新規、外部 import ゼロ、byte-identical）:
  `buildSdkPromptStream(promptText)` が `{ stream, release }` を返す。`stream` は SDK が文字列
  prompt から自ら組み立てる JSON と同形の user メッセージを 1 件 yield した後、`release()` が
  呼ばれるまで内部で `await` し続ける（＝完了しない）。SDK の `Query.streamInput()` は渡された
  stream を読み切って初めて `transport.endInput()` を呼ぶため、これで stdin クローズをターン完了まで
  先送りできる。単発 yield して即 return するだけの generator では不十分（`streamInput()` の
  for-await が即完了し、結局早期に stdin が閉じる）ことをコメントに明記した
- `agents/{linux,macos}/src/services/ai-runner.ts`:
  - `query({ prompt, options: sdkOptions })` → `query({ prompt: promptStream.stream, options: sdkOptions })`
  - 既存の `try { for await (...) {...} } catch {...} finally {...}` の `finally` に
    `promptStream.release()` と（二重防御の）`sdkQuery.close()`（例外は握りつぶす）を追加。
    正常終了・catch・abort のいずれの経路でも必ず `finally` を通るため release 漏れは起きない
  - 診断性向上: exec モードの `canUseTool` コールバックにこのターンで初めて到達した瞬間だけ
    ログを出す `canUseToolEnteredOnce` フラグを追加（次回同種の障害が起きた際、
    「呼ばれるべきツールがあるのに一度もこのログが出ない」ことで即座に切り分けられるようにする）
  - 途中 result 延期時のログに `inputStreamHeldOpen=true` を追記（`sdk-background-tasks.ts` の
    判定ロジック自体は無変更）
- `agents/{linux,macos}/tests/sdk-prompt-stream.test.mjs`（新規、byte-identical、8ケース）:
  yield メッセージの形状、`release()` 前は次の `next()` が pending のまま、`release()` 後は速やかに
  完了、`release()` の冪等性、for-await との統合、複数ストリームの独立性を検証

`agents/windows`（Electron GUI 版）は SDK の `query()` 直接呼び出しも `sdk-background-tasks.ts` も
持たないため対象外。`apps/server` は無変更（原因は Agent 側のみ）。

## スコープ外（記録のみ・Phase 2/3 として plan に記載）

- **Phase 2（未実施）**: `pendingToolApprovals` に agent 側タイムアウトがない・WS 切断時に pending
  を reject しない・サーバー再起動時に agent 側の pending が残り続ける、という既存のギャップ。
  今回のバグの原因ではないが独立した堅牢化余地として記録
- **Phase 3（コード変更なし）**: 調査時点で `devrelay-server` が `551f467`
  （Claude Opus 5.5 対応、SDK 0.3.278→0.3.282）より古いプロセスのまま起動しており、
  `running code is stale (rebuild did not take effect)` を繰り返し出力していた。本サイクルの
  原因ではないが `pm2 restart devrelay-server` が別途必要（ユーザーに報告済み）
