# 2026-11-14 07:24 JST ｜ エージェント再接続の3つの不具合修正（linux / macos / windows）

要求: 自宅PC（fwjg2507-FMVD34003）が 2026-11-11 05:29 に pong タイムアウトで切断された後、
DNS エラー（EAI_AGAIN）の再接続を約13回くり返し、05:30:46 の `Connecting...` を最後に3日間沈黙した
事故の根治。プロセスは生きたままで systemd の `Restart=always` も効かなかった。

原因（Plan フェーズの調査で確定）:
- 原因A: `connectToServer()` に接続タイムアウトが無い（`handshakeTimeout` 未指定・自前監視タイマーも
  無い）。CONNECTING のまま止まると、生きたタイマーが1つも残らず沈黙する。
- 原因B: `scheduleReconnect()` の安定判定が「最後に成功した接続から60秒以上たったか」で、長時間
  安定していた接続が切れた後は毎回この判定が真になり `reconnectAttempts` が毎回0にリセットされる
  （常に attempt 1・2秒固定でバックオフが一切効かない）。
- 原因C: `maxAttempts`(30) 到達でログを出して `return` するだけで `process.exit` もせず、プロセスが
  生きたまま永久に沈黙する（crontab `@reboot` の nohup 起動機は戻らない）。

実行: `packages/shared/src/reconnect.ts` を新設し `CONNECT_TIMEOUT_MS`(20s)・`CONNECT_WATCHDOG_MS`(25s)・
`computeReconnectDelay()`（指数バックオフ+jitter、exponent を 30 で clamp して無期限リトライでも
Infinity/NaN にならない）を集約。`DEFAULTS.reconnect.maxAttempts` を削除（撤廃）。
`agents/{linux,macos,windows}/src/services/connection.ts` の3ファイルに同じ変更:
① `wsOptions.handshakeTimeout = CONNECT_TIMEOUT_MS` ＋ 自前の接続監視タイマー（`CONNECTING` のまま
`CONNECT_WATCHDOG_MS` 経過したら `terminate()`。ws v8 は CONNECTING 中でも `abortHandshake()` 経由で
error→close を必ず発火するため既存の close→scheduleReconnect 経路に戻る）。
② 安定判定を「open で即リセット」ではなく「open から `stableConnectionTimer` を張り、60秒 OPEN を
維持できたら `reconnectAttempts = 0`」に変更（判断1）。open 即リセットを採らなかった理由: 本リポジトリに
既知のAgent二重起動事故（サーバーが新接続のたびに旧WSを切断→無限再接続ループ、
`doc/agent_noresponse_20260814.md`）があり、open 即リセットだと2秒間隔のホットループになる
（windows の旧実装はこの型）。`scheduleReconnect()` の旧 `connectionDuration` 判定は削除。
③ `maxAttempts` 打ち切りを撤廃、無期限リトライ＋`computeReconnectDelay()` に委譲。ログは
`(attempt N)` のみに変更（`/30` 表示を削除）。
最後の砦（判断2）として60秒間隔の `startReconnectSupervisor()` を追加: 「ws が生きていない
（OPEN/CONNECTING でない）のに `reconnectTimer` も無い」状態を検出したら `scheduleReconnect()` を
呼ぶ。`disconnect()` で `shuttingDown=true` にして抑止。`connectToServer()` 呼び出しごとに
`startReconnectSupervisor()` を呼ぶが多重起動ガード済み。
windows は構造的に linux/macos と異なる（`thisWs` 捕捉・旧ソケット後片付けが無い）ため、watchdog
用の最小限のローカル参照（`watchedWs`）のみ追加し、旧ソケット後片付け／`thisWs` ガードの既存ギャップ自体は
**範囲外**として残置（別サイクル候補）。

検証: `pnpm build`（6 workspace）green。新規テスト: `packages/shared/tests/reconnect.test.mjs`
（`computeReconnectDelay()` の単体、2s/4s/8s/16s→30s clamp・jitter境界・attempt=1000でもFinite・
attempt<=0 clamp・CONNECT_WATCHDOG_MS>CONNECT_TIMEOUT_MS）、
`agents/{linux,macos,windows}/tests/reconnect-wiring.test.mjs`（byte-for-byte同一、node:fs の静的ガードで
handshakeTimeout・watchdogのCONNECTING判定+terminate・clearConnectWatchdogの4箇所呼び出し・
reconnectAttemptsリセットがopen側にあること・scheduleReconnectにmaxAttempts/Giving upが残っていないこと・
supervisorの多重起動ガードとshuttingDown判定・disconnect()の配線を検証）、
`agents/linux/tests/reconnect-connect-timeout.test.mjs`（live、node:net の「accept するが応答しない
TCPサーバー」で① handshakeTimeout指定時にerror+closeが発火すること ② handshakeTimeout無しでも
CONNECTING中にterminate()するとcloseが来ることを実証。ws v8の前提を裏付け）。
