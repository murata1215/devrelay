## 主要な調査結果（詳細は契約書参照）

- `GET /api/threads` は単一の `label` を返さず、`title`/`labelFromUser`/`labelFromAi`/`firstUserMessage` の
  材料のみ返す。表示名導出はクライアント側の責務
- `GET /api/sessions/:id/messages` の `before` はメッセージ ID カーソルで、存在しない ID を渡すと
  条件が丸ごと無視され最新ページが返る fail-open 仕様。旧 `GET /api/projects/:id/messages` は
  プロジェクト内の全セッション混在のため、スレッド画面では使うべきではない（現行 Flutter の
  「別スレッドの発言が混ざる」症状の直接原因と推定）
- `web:command` に `projectId` ヒントを付けるだけでは送信先スレッドが確定しない
  （直前のタブ current／最新 active／新規作成のいずれかに流れる可能性がある）。
  送信前に必ず `POST /api/sessions/:id/switch` でタブの current を固定する必要がある
- `web:session_info` の配信先は「送信元タブ＋当該セッション参加者」のみで、ユーザーの全ソケットではない
- tabId は `chatId = "web:{userId}:{tabId}"` がキーで、同一 tabId の新規接続は既存ソケットを `terminate()` する
  （chat 用・global 用は別 tabId が必須）
- FCM の `data` には `sessionId` が入っているが、`GET /api/notifications` の `Notification` レスポンスには
  `sessionId` が無い（通知一覧からのスレッド直行には server 側追加対応が必要）
- `Session.status` は `active`/`ended` の2値のみで「処理中」「承認待ち」の中間状態は無く、
  スレッド一覧 REST にもその情報は露出していない
