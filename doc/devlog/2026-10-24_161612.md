# 2026-10-24 16:16 JST ｜ サイクル: インストーラのPAT取得415修正

要求: 会社サーバー（IIS/ARR 配下のサブパス `tsinternal/devrelay`）で、前サイクルの読取PATサーバー
配布（`POST /api/agent/repo-auth`）が 415 になりインストーラが PAT を自動取得できず、原因も無言で
握り潰されている不具合をプランモードで調査し、実装承認を得て修正した。

実行: 真因は IIS がボディ framing ヘッダを付けて転送し、Content-Type 未指定の POST を Fastify が
415（FST_ERR_CTP_INVALID_MEDIA_TYPE）として拒否すること（実測: Content-Type なし→415 /
`-ContentType application/json -Body '{}'`→200）。クライアント側（`install-agent.ps1`/`.sh`）に
`Content-Type: application/json` + `{}` ボディを付与し、失敗時は無言フォールバックをやめて
**ステータスコードのみ** 1 行表示するよう修正（応答本文・例外メッセージ全文は非表示）。サーバー側は
新規 `repo-auth-content-type.ts`（`applyRepoAuthContentTypeParser()`）で `/api/agent/repo-auth` の
プラグインスコープに限り content-type parser を「何でも受けてボディを捨てる」1 本に置き換え、
保険とした（`fastify-plugin` 未ラップのプラグインが親の ContentTypeParser を複製する Fastify 内部
挙動を利用し、他ルートへは一切影響しない設計）。`doc/company-repo-sync.md` に §9.7（IIS 配下の
注意点・切り分けコマンド）を追加。

検証: 新規 `repo-auth-content-type.test.mjs`（実 Fastify + `app.inject()`、9 ケース）で
Content-Type なし/chunked/json空ボディ等が 415/400 にならないこと、別スコープの JSON ルートは
従来どおり 415 のままであること（スコープ漏れ回帰防止）を確認。既存 2 本の静的ガードテストに
10 ケース追加（インストーラの Content-Type/ボディ付与・失敗時メッセージが応答本文を含まないこと・
`removeAllContentTypeParsers` を呼ぶのは本ファイルだけ 等）。server テスト 1343/1343 green
（新規 19）、`pnpm build` 成功、`agents/*`・`apps/web`・`packages/shared`・Prisma は 0 行変更
（`git diff --stat` で確認、各機 `u` 不要・DB マイグレーション不要）。commit `<pending>` push 済み
（本文末尾の最終報告で hash を確定）。

発見: `node --test` がグロブパターン文字列をそのまま展開できず、シェルの `globstar` 有効化
または Node 20（nvm）への切り替えが必要だった（本番用の `pnpm test` スクリプトは動作問題なし、
今回はこのサンドボックスのシェル設定起因）。既存の静的ガードテストで `addContentTypeParser` を
広く検出する設計にすると `src/mcp/oauth.ts` の既存の無害な用途を誤検知することが判明し、
`removeAllContentTypeParsers`（危険な全消去呼び出し）のみに絞った。`text/plain` は Fastify の
既定パーサーに最初から登録済みのため、スコープ漏れ回帰テストの Content-Type には使えない
（`application/octet-stream` 等の未登録タイプを使う必要がある）。
