# core#335: ゲート⑤(ask)/⑥(teamexec) 人間入力テキスト検証 + F3 解消 (2026-08-30)

## 要求
#334 でゲート①②③（note/e,指示/instruction）に入れた「長さ上限・provenance fence・復元可能な監査」を、
未対応のまま残っていたゲート⑤ ask / ⑥ teamexec に同じ形で適用する。併せて #334 の残件 F3（`e,<指示>` が
`lastRemoteProjectId` 経由で teamexec に転送される経路で fence が掛からない）を閉じる。server 側のみ、
Agent（`agents/`）は変更しない。承認ノートで changelog への残件記載2点を追加依頼された:
(1) REST `/api/agent/ask-member` を対象外とした判断根拠、(2) ①②③のインラインと⑤⑥の共通関数実装が
並存する構造・キー順一致はテストで担保している旨・①②③の共通関数への統合が別サイクルの残件である旨。

## 実行
1. `apps/server/src/services/human-text-fence.ts` に `fenceIfHuman(kind, text, origin)` と
   `buildHumanTextMeta(input)` の2純関数を追加（新規ファイルは作らず既存モジュールに追記）。①②③の
   インライン実装（`command-handler.ts` の `handleExec()`、`mcp/tools.ts`）は無変更のまま残した。
2. `command-handler.ts` に `ASK_QUESTION_MAX_LENGTH`/`TEAMEXEC_INSTRUCTION_MAX_LENGTH`（いずれも4000）を
   追加。`handleAskMember()` 先頭に長さ検証を追加（拒否時は `sendMessage`/`session.create` 等いずれの
   状態変更よりも前に return）、`message.create` に `humanTextMeta`（`kind:'ask'`）を追加、
   `executeCrossProjectQuery` への質問を `fenceIfHuman('ask', question, 'human')` に変更。
3. `handleTeamExec()` に `instructionOrigin: string = 'human'`（既定値により直接呼び出しは無変更）を追加。
   `instructionOrigin==='human'` のときのみ長さ検証・`humanTextMeta`（`kind:'teamexec'`）付与。
   `executeCrossProjectExec` への指示を `fenceIfHuman('teamexec', instruction, instructionOrigin)` に変更。
4. `handleExec()` の F3 転送分岐（`:712-734`）で `forwardOrigin = customPrompt !== undefined
   ? (promptOrigin ?? 'human') : 'system'` を計算し `handleTeamExec()` へ渡す。この return は本関数末尾の
   fence 生成（#334 ゲート②）より前にあるため、転送経路で `handleExec` 側の fence が実行されることはない
   （fence は `handleTeamExec` の `fenceIfHuman` 呼び出し1箇所のみ、という構造的根拠をコメントで明記）。
5. `packages/shared/src/i18n.ts` に `humanText.questionTooLong`（ja/en）を1キー追加。
6. `apps/server/tests/human-text-fence.test.mjs` に7ケース追加（`fenceIfHuman` の system/undefined 無変更・
   human時に開始/終了タグ1組・二重fence不成立、`buildHumanTextMeta` のキー順固定・値検証、
   ⑤⑥上限4000でのサロゲートペアケース）。既存16件は無変更。
7. `doc/changelog.md` の #334 の直前に `#335` セクションを新設し、承認ノートで依頼された2点の残件

## 発見
- ⑤⑥は質問/指示が `sendPromptToAgent()`/`execConversation()` にテンプレート加工なしで渡る設計のため、
  fence をハンドラ側1箇所に入れるだけで確実に効くことを事前調査で確認できた（Agent側の変更が一切不要な
  根拠）。
- F3 の「二重fence不成立」は return の実行順序（転送 return が fence 生成コードより前）という静的な
  コード構造のみで保証できるため、ランタイムの分岐条件に依存しない堅い設計にできた。念のため「既に
  fence済みの文字列を渡しても内側は無害化され外側1組だけが生きる」ケースもテストで担保した。
- REST `/api/agent/ask-member` は `handleAskMember()` を経由せず `executeCrossProjectQuery()` を直接呼ぶ
  AI起点の経路であり `origin==='human'` に該当しないため、#334/#335 のスコープ定義上は対象外という判断を
  changelog に明記した。ただし将来この REST に人間が直接叩ける入力口が追加された場合は本判断が無効化される
  ため、再検証が必要な旨も残した。
- ①②③のインラインJSON.stringify実装と⑤⑥の共通関数`buildHumanTextMeta()`が並存する状態になったため、
  5経路のキー順一致は「共通コードによる保証」ではなく「テスト（human-text-fence.test.mjs）による保証」
  であることをコード内コメントと changelog の両方に明記した。①②③を共通関数に寄せる統合は今回見送り
  （「既存の不変条件を壊さない」を優先、#331と同じ判断）、別サイクルの残件として changelog に記録。
