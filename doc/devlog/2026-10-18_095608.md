# WebUI のコマンド応答が消える問題の根治（testflight 完了メッセージが即消える）

日時: 2026-10-18（JST）

## 症状

WebUI（classic ChatPage）で `testflight uso8m` を実行すると、完了メッセージ
（✅ uso8m を作成しました / URL / パス / Port / DB / .env ...）が一度は表示されるが、
数秒で消えてしまう。URL・Port・DB 名という後で必ず必要な情報が失われる。

## 原因（コードと pm2 ログで確定）

3 つが重なっていた。

1. **コマンド応答が DB に保存されていない**: `apps/server/src/platforms/web.ts` は
   `executeCommand()` の戻り値を `web:response` で WS 配信するだけで `Message` テーブルに
   保存しない。ユーザー入力（`testflight uso8m`）も非 AI ターンでは未保存。
   自前で `prisma.message.create` を呼ぶのは AI ターン系ハンドラ（`handleExec` /
   `handleAgreement` / `handleAiPrompt` / `handleAskMember` / `handleTeamExec`）のみ。
   `testflight` を含むそれ以外のコマンドは DB に痕跡を残さない。
2. **クライアントは「DB 履歴が正」で再構成する**: `ChatPage.tsx` の `loadHistory()` は
   `mode='refresh'`（API 最古より古い WS 行を捨てる。API 履歴が空なら WS 由来が全滅）、
   `mode='replace'`（スレッド切替）、マウント復元のいずれも DB 履歴を正として組み立て直す。
   Lite シェルも同じ意味論（`lite-message-log.ts` に明記済み）。
3. **`testflight` 自身が直後に WS を切る**: `testflight-manager.ts` は成功メッセージ返却の
   2 秒後に `sudo systemctl reload caddy` を実行し、これが Agent/WebUI の WS を切断する
   （#258 由来の設計）。切断 → `handleReconnect()` → `loadHistory(..., 'refresh')` が即走るため、
   2 の取りこぼしが毎回・即座に発生していた。

pm2 ログの実トレース（応答送信 → WS 切断 → caddy reload → 再接続 → 履歴 GET）で裏取り済み。
Discord 経路での実行記録はなく、Discord 側にメッセージ削除コードも存在しないため
WebUI 固有の現象と確認。

## 修正方針

コマンドの往復（ユーザー入力＋応答）を AI ターンと同じく `Message` に永続化する。
WS が切れてもリロードしてもスレッドを切り替えても DB から復元されるため、`testflight` だけでなく
`status`/`log`/`model` 等あらゆるコマンド出力の消失を横断的に直す。
`apps/web` と `packages/shared` は無変更（`messageId` を使う仕組みが既に両方の型にあり、
サーバーが保存して id を載せるだけで classic/Lite 両方が直る）。

## 実装

- 新規 `apps/server/src/services/web-command-persistence.ts`（純関数のみ、外部 import は型のみ）
  - `isWebCommandPersistEnabled` — キルスイッチ判定（既定 ON、`'0'` のみ無効）
  - `shouldPersistWebCommandTurn` — 保存すべきか判定。AI ターン系 5 type
    （`exec`/`agreement`/`ai:prompt`/`ask:member`/`teamexec:member`、自前保存済みのため除外）と
    `login`/`login:code`/`login:cancel`/`clear`/`quit`（login 系は認可コードが DB に残らないよう
    構造的に除外、clear/quit は「(無題)」スレッド復活防止のため除外）を型安全なリスト
    （`satisfies readonly UserCommand['type'][]`）で判定
  - `shouldPersistWebResponse` / `buildWebUserMessageRow` / `buildWebResponseMessageRow`
  - `createdAt`: user 行はコマンド受信時刻（送信者タブの楽観表示と ChatPage の 60 秒重複排除窓を
    合わせるため）、応答行は `max(completedAt, receivedAt+1ms)` で必ず user 行より後にする
- `apps/server/src/platforms/web.ts`: `case 'web:command'` 内で上記判定関数を呼び、
  `web:user_message`/`web:response` ブロードキャスト直前に `Message` を作成して
  `messageId` を payload に乗せる。保存失敗（DB エラー）は `console.warn` して握りつぶし、
  WS 配信は巻き込まない

## 副作用の洗い出し（調査済み・許容範囲、修正なし）

- MCP `get_plan`/`get_build_status`/`get_answer`: 最新メッセージ取得は `role:'ai'` か
  `role:'user' AND content:'exec'` 絞りのため無影響
- `auto-updater.ts` の `isMachineBusy` recentActivity 判定: コマンド実行も「最近の活動」と
  見なされる（実際に操作中なので正しい）
- `thread-list-filter.ts` の空スレッド隠し: コマンドだけ打ったスレッドが一覧に出るようになる
  （`clear`/`quit` は除外済み、中身があるので妥当）
- `handleLog` の出力にコマンド往復が混ざる（妥当、気になれば別サイクルで除外）
- ナレッジ化（`processTurnKnowledge`）は `agent-manager` 内の明示呼び出しのみのため無影響

## 検証手順（ユーザー向け、再起動後）

1. WebUI で `status` 実行 → リロード/スレッド切替しても入力・応答が残る
2. `testflight <捨て名>` 実行 → caddy reload 由来の WS 切断・再接続後も完了メッセージが消えない
3. 2 タブで同時に同じコマンドを打っても重複表示されない（`messageId` dedup）
4. 通常の AI ターンで二重保存が起きていないこと
