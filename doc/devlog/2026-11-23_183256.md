## 実行

  CP932 として誤読し ParserError になる既存バグの根治）。実行順を変更: サービス停止・削除を
  ビルドより前に（A6a、SandboxHost.exe の消滅を最大30秒ポーリング）。`sc.exe create` から
  `password=` を削除（A2）。`New-Object ECDsaCng(256)` に変更し直後に blob 長72バイト・magic
  `ECS1` を検査（A5）。秘密鍵の書き込み前に `icacls /grant "*S-1-5-32-544:(F)"` でACLを戻してから
  削除（A6b）。ファイアウォール3本すべて `-LocalUser "D:(A;;CC;;;<SID>)"` に変更（A4）、IPv6は
  `"::/1","8000::/1"`（A3）。完成時にNode経由で公開鍵の読み取りを検証し、実際に動くコマンド
  （node.exe + cli/index.js）を案内（A7/B1）。`uninstall-sandbox-host.ps1` も同様にASCII化+ACL戻し。
- `agents/sandbox-host/SandboxHost.cs`: `HandleSpawn()` の stdin/KILL 読み取りループを背景スレッド化
  （B5の真因）。旧実装はこのループがメインスレッドにあり、Agentが切断するまで
  `process.WaitForExit()` に到達せず EXIT が送れなかった。`SandboxJobObject.Dispose()` に
  一度だけ実行するロックガードを追加（並行呼び出しでの二重 `CloseHandle` 競合を防止）。
- Agent 側: `awaitSandboxProcessResult()` を新設（`sandbox-launcher.ts`。リスナーを同期登録し
  EXIT取りこぼしを防止）、`SandboxSpawnRequest.env` を `Record<string,string|null>` に変更
  （`undefined` は JSON.stringify で消え「キー削除」の意図が伝わらないため）。純関数4本を新設:
  `sandbox-cli-hint.ts`（B1）、`sandbox-console-text.ts`（B2の文字化け修正、UTF-8→Shift_JIS→
  latin1の順でフォールバック）、`sandbox-probe-interpret.ts`（B6/B7/C1の判定）、
  `sandbox-proxy-mode.ts`（B3）。`sandbox-prep-commands.ts` に `decideSandboxPrepPrecheck()` を追加。
- `cli/commands/sandbox.ts` を全面改修: `withSandboxProxy()`（B3、48711への接続試行で既存検出、
  無ければ一時起動）、prepの事前確認（B2）、selftestに `--acl-audit`（C1）・`--claude-roundtrip`
  （B8）・`--bits-probe`（B7、既定で実行せず警告表示）を追加、ネットワーク確認を全てホスト経由
  （B6、`SandboxSpawnedProcess`経由のcurl.exe）に変更、署名検証の表示をECDSA P-256に修正（B4）。

## 発見

- A1の根本原因はBOM無しUTF-8をPowerShell 5.1がANSI(CP932)として読む既知の挙動で、
  `install-agent.ps1`/`uninstall-agent.ps1`も同じ地雷を内在するが `irm | iex` 配布のため
  顕在化しない（今回は変更せず、調査結果のみ記録）。
- A5の真因は `New-Object ECDsaCng([ECCurve]::NamedCurves.nistP256)` が ECCurve を取る
  オーバーロードに解決されず、別オーバーロードでP-256以外の鍵を生成していたこと。
- B5の真因はC#側の設計（Agent切断待ちのEXIT送信）であり、Agent側のタイミング問題ではなかった。
- B6で判明: curlがプロキシのCONNECT拒否（非200応答）を受けると exit=56（CURLE_RECV_ERROR）を
  返す（exit=7は直結の接続失敗、CURLE_COULDNT_CONNECT）。
