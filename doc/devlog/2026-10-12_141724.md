## 目的

サイクル4（`f989d30`）の `/knowledge` は「検索箱に 1 問打つと、根拠カード＋AI 回答が同時に出る」
1 問 1 答だった。本サイクルで答えに続けて聞けるようにし（「それはいつ決まった？」「他の案件でも
同じことやった？」）、あわせて Claude Code 自身が MCP `ask_knowledge` で出典つきの答えを 1 回で
得られるようにした。

## §9 確認事項の調査結果（プラン段階で確定・判明済み事項を再検証した上で決定）

1. **`loadKnowledgeTurnTexts` の再取得・可視判定**: 既存関数は `(viewerUserId, {sourceId,
   sessionId}[]) → Map<sourceId, text>` で可視判定済みだったが、全文（`text`）しか返さない。
   会話の「既知の根拠」を再表示するには `title`/`projectName`/`ownerName`/`occurredAt`/`level`/
   `compartment`/`projectId`/`isOwn` も要るため、本体を `loadKnowledgeTurnDetails`
   （`KnowledgeTurnDetail` を返す）に実装し直し、`loadKnowledgeTurnTexts` はその薄いラッパに
   変更した（関数名・シグネチャは既存 wiring テストのピンのため維持）
2. **`buildKnowledgePrompt` のバイト一致テスト**: `items: []` のとき `result.user === '質問'`
   の 1 本だけがバイト一致固定。この分岐は抜粋ループの**前**で早期 return しているため、
   `history` は分岐の**外**（`system` 段落・`messages` 構成）で扱うことで、既存テストを
   1 つも壊さずに済んだ（実装後に確認: 省略時は `system`/`user` ともサイクル4と完全一致）
3. **MCP wiring テストの境界**: `search_knowledge` の直後・`get_knowledge_thread` の前に
   `ask_knowledge` を挿入すれば、既存 4 本（`knowledge-wiring`/`knowledge-admin-wiring`/
   `mcp-ask-source-guard`/`thread-reestablish`）の `indexOf`/`slice` 境界はいずれも
   `search_knowledge` 本体を含み続けるため無傷（実装後にフルスイートで確認済み）
4. **会話 UI の置き場所**: 新規コンポーネントは作らず `KnowledgeAnswerPanel.tsx` を拡張した。
   `components/knowledge/*.tsx` はディレクトリ走査で全件ガード対象になり、markdown 描画への
   接触は `ANSWER_PANEL_FILES`（2 ファイル）と**集合一致**で検査されるため、拡張であれば
   `knowledge-source-guards.test.mjs` を 1 行も変更せずに済んだ（実装後に確認済み）
5. **MCP `history`/`knownSources` の上限**: zod は型だけ受け、件数・文字数はサーバーの
   `normalizeHistory`/`normalizeKnownSources` に任せた（拒否ではなく切り詰め。Claude Code 側が
   history を積むたびにツールエラーになる事故を避けるため）

## ユーザー承認の追加要件（指示書 v2 の承認ノートで追加された 2 点）

- **(a) MCP `ask_knowledge` の `knownSources` 対応**: `history` だけでは追い質問のたびに番号が
  1 から振り直され、`history` 内の回答に書かれた `[n]` とズレてしまう。これを避けるため、
  `ask_knowledge` にも `knownSources?` を任意引数で受け、**戻り値の各 `sources[]` 要素に
  `sourceId`（`aiMessageId` のエイリアス）を追加**した。「前回の `sources[]` をそのまま
  `knownSources` に渡せば番号が会話で一意に続く」ことを `hint`・ツール説明文・
  `mcp/server.ts` の `SERVER_INSTRUCTIONS` の 3 箇所に明記した
- **(b) `evictForBudget` の「引用済み」判定をサーバー側で導出**: クライアント申告（例えば
  `knownSources` に「引用済みフラグ」を持たせる等）に頼らず、正規化済み `history[].answer`
  に実際に出現する `[n]` を `extractCitedRefs()` で抽出し、その結果だけを根拠に
  `evictForBudget` の `cited` を決める（クライアントが自己申告で「引用済み」を偽装しても
  予算の優先順位に影響しない）

## 実装中に発見し、先に直した問題（ユーザー承認の範囲内・方針変更ではなく実装精度の話）

- **カードクリック整合の崩壊リスク**: `mergeConversationSources`/`evictForBudget` の経路を
  会話でない最初の質問にも**常に**通す実装にすると、検索結果の `rank`（欠番がありうる）を
  会話一意の連番に詰め直してしまい、WebUI の `[n]` クリック→カードスクロールの対応が
  最初の質問からズレる。**会話でないとき（`history`/`knownSources` が両方空）は
  この経路を一切通さず、サイクル4と完全に同一のコードパス**（`rank` をそのまま使う）を
  通す分岐にして回避した。WebUI 側も `resolveCitationTarget` で `rank` 数値一致ではなく
  `(sessionId, aiMessageId)` の identity 一致に変更したため、最初の質問・会話継続後の
  いずれでも破綻しない
- **監査対象の取り逃し**: サイクル4の監査ロジックは `context.items` から
  `resultByMessageId.get(item.aiMessageId)?.ownerUserId` を引いていたが、会話の「既知の根拠」
  は `resultByMessageId`（今回の検索結果）に存在しないため、他人の既知根拠を含む追い質問で
  監査対象を取り逃す。`KnowledgeContextItem` に `ownerUserId`/`isOwn` を正式フィールドとして
  追加し、両経路（新ヒット／既知）で必ず埋めるように修正した上で、監査判定をそちらから
  行うようにした
- **`mergeConversationSources` の番号再利用バグ**: 実装直後のテストで、不可視になった既知の
  根拠（`ref=2`）が落ちた直後に新ヒットへ `ref=2` を再利用してしまう不具合を発見（続き番号の
  起点を「残った既知の最大 ref」から算出していたため）。起点を「クライアント申告の `known`
  **全体**（不可視で落ちた分も含む）の最大 ref」に変更し、番号の再利用を防いだ
