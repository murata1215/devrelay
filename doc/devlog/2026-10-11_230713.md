## 真因（実機ログで確認済み）

`isMachineBusy()`（`auto-updater.ts`）は (a) `progressTrackers`（session-manager.ts）の有無 と
(b) 直近 10 分の Message の有無のみで判定していた。`startProgressTracking` を呼ぶのは
`handleAiPrompt`・`handleExec`（`e`）・`handleAgreement`（`ag`）・MCP `submit_instruction`・
MCP `ask_project` の 5 経路だけで、**MCP `approve_implementation`（exec 本体）・crossquery/teamexec・
raw-completion は呼ばない**。本番ログで `busy (session running)` による skip は実測 **0 回**、
`⚠️ No tracker found for session …` が **1174 回**。該当機体は実際に 2 回 `🚀 [auto-update]` を
受けていた（`6ae9c8e→962dd96`、`962dd96→de1ec7a`）。

## 指示書に対する設計訂正（プラン段階で特定・ユーザー承認済み、C1〜C5）

- **C1（最重要）**: 指示書 D2 は Agent 側の実行中判定に `activeSessions.size` を使う設計だったが、
  これは誤り。`activeSessions`（`ai-runner.ts`）は「登録済み会話セッション」の台帳で、`.set` は
  `startAiSession()`（`session:start` 受信時、プロセス未起動）の 1 箇所のみ、`.delete` は
  `stopAiSession()`（`session:end`）の 1 箇所のみ。会話が続く限り残り続けるため、指示書どおり実装
  すると **Agent が永久に更新されなくなる**。正しいチョークポイントは `sendPromptToAi()`
  （SDK / PTY(terminalMode) / Devin・Codex・Gemini の spawn 経路・rawMode が全て通る唯一の入口）。
- **C2**: version-check の応答型は `agent:version-check:result` ではなく `agent:version:info`
  （リポジトリ全体で前者は 0 ヒット）。
- **C3**: D3「deferred は attempts に数えない」は *ロールバック* が必要。`autoUpdateAttempts` は
  **送信時**（`maybeAutoUpdate()`）に +1 済みなので、`deferred` 受信時に 1 戻さないと同一 commit で
  2 回 defer した時点で `evaluateAutoUpdateGates()` が `disable` を返し `autoUpdate` が false に落ちる
  （D3 が防ぎたい事故そのもの）。
- **C4**: D8 の `server:agent:restart` はチャットコマンドではなく REST（`POST /api/machines/:id/restart`）。
  409 を返せば既存の `machines.restart()` の `catch { alert(err.message) }` にそのまま表示されるため
  **`apps/web` は 0 行変更**で済む。
- **C5**: 指示書 Q1 の送信点リストに漏れがあった。`applyAgreement`（`ag`）も AI ターン開始点であり、
  4 番目のフック点として登録が必要。

## 実装

### サーバー側 D1: 実行中ターン台帳

新規 `services/in-flight-turns.ts`（`InFlightTurnRegistry`、外部 import ゼロ）。
`start(machineId, key, nowMs)` / `end()` / `clearMachine()` / `isBusy()` / `count()` /
`sweepStale()`（TTL 6 時間）。シングルトン `inFlightTurns` を台帳自身に置き、`agent-manager.ts` と
`auto-updater.ts` の両方から静的 import できるようにした（`agent-manager.ts` は既に
`auto-updater.ts` を動的 import して循環を避けている既存構造があるため、どちらの静的 import 先にも
しない設計）。

送信点 4 箇所すべてで送信直前に `start()`:
`sendPromptToAgent`（`server:ai:prompt`）・`execConversation`（`server:conversation:exec`）・
`sendRawPromptToAgent`（`server:raw:prompt`、`.finally()` で確実に解除）・
`applyAgreement`（`server:agreement:apply`、既に `startProgressTracking` 経由で busy 判定されているが
4 経路の形を揃えるため台帳にも登録）。

解除は 3 箇所: `handleAiOutput` の `isComplete` 分岐先頭（主経路）・`handleAiCancelled`（意図的に
楽観的 — `isComplete` を待たず解除する。キャンセル時に完了シグナルが届かない既知の事故クラスに
当たった場合、ユーザーが自分で止めたターンのせいで更新が TTL 6 時間ぶん止まるほうが明確に悪いため）・
`handleAgentDisconnect` の `clearMachine()`（取りこぼし経路の保険）。

`isMachineBusy()` は新設の `isMachineBusyWithReason()`（in-flight turn → session running →
recent activity の優先順位で理由文字列を返す。純関数 `resolveBusyReason()` に判定を委譲）に
委譲する薄いラッパへ変更。既存シグネチャ非破壊のため `capability-sweep.ts` の既存呼び出しは
0 行変更。`maybeAutoUpdate()` は `version.activeAiTurns`（Agent 自己申告、D2 連携）も busy 判定の
追加の安全網として利用する（新 Agent のみ、旧 Agent は無視して非退行）。

### サーバー側 D3: deferred 受信時のロールバック

`agent:update:status` に `'deferred'` を追加（`packages/shared/src/types.ts`）。
`handleUpdateStatus()` は `pendingUpdateNotify.has(machineId)` で手動/自動を振り分け、自動更新起点
（`pendingUpdateNotify` 無し）のときだけ新設 `recordAutoUpdateDeferred()`（`auto-updater.ts`）を
呼ぶ。この関数は `autoUpdateAttempts` を 1 戻し（0 未満にはしない）、`lastAutoUpdateStatus='deferred'`
に設定、`inProgress` から即座に削除する。クールダウンは `resolveCooldownMs()`（純関数）で
`lastAttemptStatus==='deferred'` のときだけ 10 分に短縮（通常 30 分）。未知 status は warn ログのみ
（attempts 不変、既存の暗黙の寛容動作を維持）。

### サーバー側 D4/D8: 手動操作への busy ガード

手動 `u`（1 回目・2 回目とも）: `handleUpdate()` 冒頭で `isMachineBusyWithReason()` を引き、
`decideManualUpdate({busy, force})` が `hold` なら `update.deferredBusy`（新規 i18n キー）を返し
`updateAgent()` を呼ばない。`pendingUpdate` の状態は変えない（busy のまま終了を待ち、終了後に
`u` を 1 回送るだけで続きから進められるようにする設計）。

`u force` / `u!`: `command-parser.ts` に個別パターン `/^u(?:pdate)?(?:\s+force|!)$/` を追加し
`{ type: 'update', force: true }` を返す。`natural-language-parser.ts` の `isTraditionalCommand()`
は既存の「2文字以上のキーのみ空白続きでマッチ」ガードに `u` が引っかからないため（`a`/`l`/`login` と
同じ理由）、個別パターンを 1 行追加。`UserCommand` の `update` バリアントに `force?: boolean` を追加。

`POST /api/machines/:id/restart`（D8）: 同じ `isMachineBusyWithReason()`/`decideManualUpdate()` を
通し、busy なら 409 を返す。`force` はリクエストボディ `{ force: true }` または
クエリ `?force=1`/`?force=true` で受け付ける。**`apps/web` は 0 行変更**（C4、既存の
`catch { alert(err.message) }` がそのまま表示する）。

`server:agent:update`（`updateAgent()`/`updateAgentAuto()`）の payload には `force` を含めない
（C5: Agent は現状サーバーから force を伝えられないため、常に安全側＝実行中ターンがあれば保留する）。

### Agent 側 D2（最後の砦、二重防御）

`agents/linux` と `agents/macos` の `ai-runner.ts` に `sendPromptToAi()` の実装本体を
`sendPromptToAiImpl()` へ分離し、`sendPromptToAi()` 自体は薄い `try/finally` ラッパへ変更
（`inFlightAiTurnStartedAt` Map に `sessionId` の開始時刻を記録・解除）。巨大な実装本体（約 1500 行、
複数の早期 return・ネストした `new Promise(...)` を持つ）には手を入れず、`await` した戻り値の
解決タイミングで安全に計測する設計（C1 の訂正を反映）。`getActiveAiTurnCount()` を新規 export。

新規 `update-guard-rules.ts`（`agents/linux`・`agents/macos` で byte-for-byte 同一、外部 import
ゼロ）: `decideAgentUpdateAction({activeAiTurns, pendingUpdate, force})` が `'start'|'defer'|'wait'`
を返す。`isTurnStale()` は TTL（6 時間）判定用。

`connection.ts` の `handleAgentUpdate()`: 既存の 60 秒二重更新防止・dev-repo 判定・restartCmd 検索の
**後**、`updateStartedAt = Date.now()` の**前**に busy 判定を挿入。`defer` なら
`pendingUpdate = true` を立てて `agent:update:status { status: 'deferred', activeAiTurns }` を送信し、
30 秒間隔の再確認タイマー（`armPendingUpdateRecheck()`）を起動して return。`wait`（既に保留中）は
無言で return（`deferred` を再送しない）。タイマーは 30 秒ごとに `handleAgentUpdate()` を再入させ、
`activeAiTurns===0` になれば `'start'` 判定で通常の更新処理へ進む（`clearPendingUpdateRecheck()` で
タイマー停止）。最大 2 時間で諦め、サーバーの次スイープに委ねる。`pendingUpdate` はプロセス寿命内
のみ（永続化しない）。

`handleVersionCheck()` の `agent:version:info` 成功 payload に `activeAiTurns: getActiveAiTurnCount()`
を追加（D2 連携）。

`agents/windows` は `server:agent:update` / `version-check` / `restart` のいずれも処理しないため
対象外（grep で 0 ヒットを確認、0 行変更）。
