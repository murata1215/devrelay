# 2026-09-23 18:07 JST ｜ サイクル2.2: DevRelay Sites Phase 1-B W4 Final Hosts Rollout

## 背景

W2（固定 21 host）・W3（特殊 9 host）で Sites logger 31 / health matcher 31 / host 31 まで
到達済み。残る未統合 host は `pixblog.net` と `ribbon-re.jp`（+ `www.ribbon-re.jp`）の 2 件のみで、
両者とも既存の独自 `log { }` ブロック（Sites 標準ではない）を持つため W3 では意図的に除外していた
（単純に snippet を足すと 1 host 2 logger になり不変条件違反）。本サイクルはこの最後の 3 host を
Sites 共有 snippet（`import sites_access_log`）へ統合する。

## 対象

- `pixblog.net`（Caddyfile 直書き、`reverse_proxy localhost:3002` + 独自 `log`
  `/var/log/caddy/pixblog.access.log`（50MiB/7）を保持）
- `ribbon-re.jp, www.ribbon-re.jp`（sites.d の 1 block が 2 host を担当、独自 `log`
  `/home/ribbon/sites/ribbon-re.jp/logs/access.log`（mode 0644）を保持）

host 数 34（33 block のうち 1 block が 2 host を担当するため、host 数と block/logger 数が
一致しない）。

## 実施方式（2 段構成）

Caddyfile 本体は sudoers NOPASSWD の対象外（`sites.d/*` の tee/rm のみ NOPASSWD）のため、
agent は自動書き込みできない。そのため:

1. **`--w4-stage`**: Caddyfile / sites.d は一切書き込まず、backup manifest を作成し
   `/tmp` ミラー上で W4 適用後の最終形（host 34 / block 33 / health matcher 33 / roll 1 種 /
   複数 logger host 0）を `caddy adapt` + `verifyAdaptedConfig()` で検証、PASS 後に human 向けの
   sudo コマンドを表示して停止
2. human が表示された sudo コマンドで Caddyfile / `sites.d/ribbon-re.jp` を実体へ配置
3. **`--w4-apply <batchId>`**: staging 済み内容と実ファイルの一致を確認 →
   実ファイルに対する `caddy adapt` + `verifyAdaptedConfig()` で PASS したときのみ reload を 1 回実行

batchId: `20260923T080236Z-7061195d`（`~/.devrelay/sites-backups/20260923T080236Z-7061195d/`、
内訳 `manifest.json` / `b0001.bak`（ribbon backup） / `Caddyfile.before` / `Caddyfile.new` /
`caddyfile-change.json`（sidecar） / `ribbon-re.jp.new`）。適用前に `/etc/caddy/Caddyfile` と
`sites.d/ribbon-re.jp` の sha256 を staging 時点の記録値と突合する drift 検出を実施し、
drift なしを確認した上で適用した。

## 適用結果

- reload: 今回 1 回（Phase 1-B 累計 **6 回目**）。`MainPID=790` / `NRestarts=0` は reload 前後で不変
- 到達値: **host 34 / Sites logger(block) 33 / health matcher 33**、1 host = 1 logger 違反 0 /
  dangling 0 / orphan 0、roll 設定 1 種のみ（`64MiB / roll_keep 12 / roll_keep_for 1440h / mode 0640`）
- `pixblog-custom`（catch-all `https://` block、`log { output file
  /var/log/caddy/pixblog-custom.access.log { roll_size 50MiB roll_keep 7 } }`）の
  default logger は**無変更のまま存置**
- ribbon legacy log（`/home/ribbon/sites/ribbon-re.jp/logs/access.log`、58MB + gz 4 本）は
  **削除せず存置**。適用後は追記が止まり最終行のタイムスタンプで固定される
- pixblog legacy log（`/var/log/caddy/pixblog.access.log`）も同様に削除せず存置、適用後は追記停止
- 秘匿ヘッダの除外は Sites 標準の `format filter`（`Cookie` / `Authorization` /
  `Proxy-Authorization` / `request>tls` / `resp_headers` を delete）に統一。W3 で `pixblog.net` /
  `ribbon-re.jp` 自体にクエリ経由の資格情報が乗る経路は無いため host 固有 `log_skip` は不要と判断
- regression: W2（21 host）/ W3（9 host）で作成した 31 host 分の logger はすべて保持。
  34 host 全件の health チェックで検出される 502/404 はいずれも backend 未 listen による既存障害
  （`game001.devrelay.io` 等）であり、Caddy 設定変更に起因する新規 regression ではないことを確認

## rollback readiness

`--rollback <batchId>` の dry-run で PASS。backup 実体（`b0001.bak` / `Caddyfile.before` /
`ribbon-re.jp.new`）/ manifest / sidecar は全て存置、drift なしを確認済み。

## 既知の残留事項（本サイクルでは対処しない）

`systemctl status caddy` の `Status:` 行に、過去（本 reload より前）に発生した失敗 reload の
残骸と見られる文字列（`setting up custom log 'log0': ... open
/var/log/caddy/pixblog.access.log: permission denied`）が残っている。ただし running config
（Admin API 実測）は W4 適用後の最終形そのもの（Sites logger 33 / host 34 / matcher 33 /
legacy logger なし）であり、`MainPID=790` / `NRestarts=0` は不変、`sites.access.log` には
34 host 分の行が現在も流入し続けている。実害は確認されないため、**この文字列を消すための
追加 reload は行わない**。journal は権限（`adm`/`systemd-journal` グループ未所属）の都合で
読めず、失敗発生時刻の特定はできていない。事実として記録するのみ。
