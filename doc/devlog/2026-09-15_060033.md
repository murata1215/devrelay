# サイクルS1: 一時通知の二重送信と progress 配信先の live 評価

## 背景

前サイクル（read-only 調査、commit `a581b59`、plan `cheeky-swimming-lecun`）で Flutter から報告された
2 件の観測 ——「`🤖 AI Status …` が AI 吹き出しとして 2 回出る」「`web:progress` だけ 2 回に 1 回届かない」——
の真因を確定し、`doc/flutter-thread-api-contract.md` §3.3.1 に記録した。本サイクルはその 2 件を
**server 側だけで根治**した。

- **C2**: Agent は `server:session:start` を受けるたびに無条件で `agent:ai:status` を返す（冪等でない）。
  `POST /api/threads` は新規スレッド作成時に `startAgentSession()` を呼ぶが Agent 再起動フラグを
  クリアしないため、直後の最初の送信で `handleAiPrompt()` が `isAgentRestarted()` を見て
  `session:start` を **もう一度**発行する。結果 1 ターン目だけ同一の一時通知が 2 通届く。
- **C4**: `web:progress` の配信先はターン開始時の 1 回だけ評価され、以降 8 秒周期の更新も
  そのスナップショットにしか送られない。`web:response` / `web:user_message` / `finalizeProgress()` は
  いずれも送信時 live 評価なので、progress だけが仕様上取り残されていた。

**スコープ**: `apps/server` + `doc` のみ。`agents/` / `packages/` / `prisma/` / `apps/web` は無変更。
反映は `pnpm build` → `pm2 restart devrelay-server` のみ。Agent の `u` 不要、DB マイグレーション不要。

## 調査結果の確認（実装前に静的解析で再確認）

`//connect`（`command-handler.ts:611-627` `handleProjectConnect()`）は、新規セッション作成時のみ
`startAgentSession()` を呼んだ直後 `clearAgentRestarted(project.machineId)`（:626）を**既に呼んでいた**
ため、C2 と同じ意図の対策が入っており変更不要と確認した。抜けがあったのは
`POST /api/threads`（`routes/api.ts:1797`）と MCP `submit_instruction`（`mcp/tools.ts:628` 付近）の 2 箇所。

ユーザー承認ノートで、当初プランでは「申し送り（次サイクル）」としていた MCP `submit_instruction` も
本サイクルのスコープに明示的に追加する指示があったため、両方を同時に修正した。

## 変更 C2: 新規セッション作成直後に Agent 再起動フラグをクリア

**`apps/server/src/routes/api.ts`**: import に `clearAgentRestarted` を追加し、`POST /api/threads` の
`startAgentSession()` 直後に `clearAgentRestarted(proj.machineId)` を追加。

**`apps/server/src/mcp/tools.ts`**: 同様に import を追加し、`submit_instruction` の新規セッション作成
（`startAgentSession()`）直後に `clearAgentRestarted(project.machineId)` を追加。

いずれも `clearAgentRestarted()` は `needsSessionRestart` Set からの `delete` のみの既存関数（無変更）。
`//connect` が既に同じクリアを行っているため、3 経路（`//connect` / `POST /api/threads` /
MCP `submit_instruction`）すべてで挙動が揃った。

## 変更 C4: `web:progress` を送信時 live 評価に変更

**新規 `apps/server/src/services/progress-recipients.ts`**（外部ランタイム import ゼロ、
`import type { Platform } from '@devrelay/shared'` のみ。`thread-reestablish.ts` と同じ流儀）。

`resolveProgressRecipients({ liveParticipants, trackerMessages })` は、`finalizeProgress()` が
既に採っている「live participants を回して tracker から messageId を引く」パターンと完全に同型にした:

1. `liveParticipants` の順序を保って走査（= 送信時点の live 評価）
2. `platform === 'web'` は常に含める。`messageId` は `trackerMessages` にあればそれ、無ければ `null`
   （`editWebMessage()` は `messageId` を実際には使わないため、ターン開始後に参加したタブでも
   messageId 無しで問題なく送れる）
3. `platform` が discord/telegram の場合は `trackerMessages` に該当 chatId の記録が **ある場合のみ**含める
   （編集対象のメッセージが存在しない chatId に対して 8 秒ごとに新規投稿することは絶対にしない）
4. `platform + chatId` の重複は初出優先で除去
5. `liveParticipants` に存在しない chatId は、`trackerMessages` に残っていても一切含めない
   （セッション参加を外れたら以降のフレームは届かなくなる。`finalizeProgress()` と同じ挙動に揃えるための
   意図的な変更）

**`apps/server/src/services/session-manager.ts`**: `updateProgressMessages()` のループ対象だけを
`resolveProgressRecipients()` の戻り値に差し替えた。頻度（8 秒固定）・payload・
`formatProgressMessage()`・タイムアウト系は一切変更していない。あわせて `elapsed` の冗長な二重計算
（従来コードが web 分岐内で `progressTrackers.get()` を引き直していた行）を外側の `elapsed` に統一した
（値は同一、DRY のみ）。

`startProgressTracking()` は無変更（`tracker.messages` の初期投入は Discord/Telegram の messageId 取得に
必須で、web 分が残っても新方式の規則 2 で無害）。WS 非 OPEN のタブは `editWebMessage()` が `false` を
返してスキップされる点も従来どおりだが、**次の 8 秒フレームで OPEN になっていれば届く**ようになった
（これが C4 の本体）。

### 副次的な挙動変化（意図的）

Discord/Telegram で「ターン途中にセッションから外れた chat」は progress 更新を受けなくなる。
`finalizeProgress()` は元々 live participants しか回していないため、その chat は現状でも
最終メッセージを受け取っておらず進捗表示が取り残されていた。今回の変更でむしろ整合する。

## テスト

**新規 `apps/server/tests/progress-recipients.test.mjs`**（`../dist/services/progress-recipients.js` を import）:

- 非退行: ターン開始時と同じ participants → 従来の `tracker.messages` 走査と同じ結果
- C4 本体: ターン開始後に参加した web タブが次フレームの宛先に含まれる（`messageId: null`）
- 参加を外れた web タブは宛先に含まれない（tracker に残っていても）

  旧スナップショット走査（`for (const [chatId, ...] of tracker.messages)`）を持たない
- 静的ガード: `progress-recipients.ts` は `import type` 以外の import を持たない

**既存 `apps/server/tests/thread-reestablish.test.mjs` へ追記**:

- `routes/api.ts` の `POST /api/threads` ハンドラで `startAgentSession(` の後に `clearAgentRestarted(`
  が現れる（順序込みの静的ガード）+ import 行に `clearAgentRestarted` が含まれる
- `mcp/tools.ts` の `submit_instruction` でも同様の静的ガード
- `command-handler.ts` の `clearAgentRestarted(` 出現回数が **5**（`handleProjectConnect`:626、
  `handleExec` 再確立ブロックの早期return+本体:978,1004、`handleAiPrompt` 再確立ブロックの
  早期return+本体:1795,1826）のまま変わっていないことを固定（`//connect` 側を壊していないことの証明。
  実装時、当初は 3 箇所と誤認してテストが落ちたため `handleExec` 分の 2 箇所を含めて 5 に訂正した）
