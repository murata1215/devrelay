# Flutter 向け確認: 一時ステータス通知の送信仕様と web:progress の配信先（read-only 調査 + 契約書追記）

## 背景

Flutter（iPhoneSE3、F3 版）で以下 2 件が観測された（2026-09-13）:

- 「🤖 AI Status: running / ⚠️ DevRelay Agreement 未対応」が AI メッセージの吹き出しとして **2 回** 出る。
  履歴 API には出ない（DB 非保存）。classic では 1 回しか見えない
- Flutter でスレッドを開いた直後に WebUI から送信すると、`web:user_message` と最終 `web:response` は届くのに
  `web:progress` だけ届かないことが 2 回中 1 回あった（再現条件未確定）

次サイクル（Flutter 表示磨き）の前提を確定するため、apps/server と apps/web を read-only で調査した。

## 調査結果の要点

1. **文言の組み立て**: `packages/shared/src/i18n.ts:243-247` の `aiStatus.running` + `agreement.*` を
   `\n` で連結した 1 本の `message`。`apps/server/src/services/agent-manager.ts:907-933` `handleAiStatus()`
   → `broadcastToSession(..., isComplete=false)` で送出
2. **実フレーム**: 専用 type ではなく **`web:response`**。`payload.messageId` は常に `undefined`
   （`apps/server/src/platforms/web.ts:332-343` `sendWebMessage()`）
3. **DB 非保存の理由**: `prisma.message.create({role:'ai'})` は `agent-manager.ts:691` の 1 箇所のみで、
   AI の最終応答（`isComplete===true`）でしか実行されない。一時通知はここを通らないため、DB 非保存は
   AI Status 固有の性質ではなく **`messageId` 無し `web:response` 全般**（全コマンド応答含む）の性質
4. **2 回届く経路**: Agent 側 `agents/{linux,macos,windows}/src/services/connection.ts` の
   `handleSessionStart()` は `server:session:start` を受けるたび無条件に `agent:ai:status` を返し冪等でない。
   サーバー側は Agent 再接続のたび `needsSessionRestart` フラグを立てる
   （`apps/server/src/services/agent-manager.ts:562-564`）が、`POST /api/threads`
   （`apps/server/src/routes/api.ts:1797`）はこのフラグをクリアしない。結果、
   「スレッド作成 → 直後の最初の送信」の 1 ターンに限り `server:session:start` が実質 2 回発行され、
   同一の一時通知が数秒差で 2 通届く
5. **classic が 1 回に見える理由**: `apps/web/src/pages/ChatPage.tsx:2331-2351` の内容ベース dedupe
   （role+content 完全一致・直近 5 件・30 秒以内）が 2 通目を捨てている。Flutter はこの dedupe を
   未実装と推定され、これが 2 回表示の直接原因
6. **`web:progress` の配信スコープ**: `web:response`/`web:user_message` は送信のたび
   `sessionParticipants` を live 評価するのに対し、`web:progress` は
   `startProgressTracking()`（`apps/server/src/services/session-manager.ts:442-508`）が
   **ターン開始時に 1 回だけ**評価したスナップショット（`tracker.messages`）にしか送らない。
   さらに `sendWebMessageWithId()`（`apps/server/src/platforms/web.ts:395-402`）は
   WS が OPEN でなければ `null` を返しキューにも積まないため、**ターン開始の瞬間に WS が
   OPEN でなかったクライアントは、そのターンの `web:progress` を 1 通も受け取れない**
   （`web:response` にはキュー救済があるが `web:progress` には無い）。これが観測 2 の構造的原因
7. **`web:progress` の頻度**: ツールイベント駆動ではなく、ターン開始時 + 以降 8 秒固定周期
   （`PROGRESS_UPDATE_INTERVAL = 8000`、env 不可）。1 分の `Bash sleep` 中は
   `output` 同一・`elapsed` だけ増える `web:progress` が約 8 回 + 最終 `web:response` 1 回
8. **§2.1 `labelFromAi`（`🔧`/`📊`/`📝` 除去）とは別集合**であることを確認
   （一時通知はそもそも `Message` に保存されないため対象外）

## 申し送り

- C2（`POST /api/threads` 直後の Agent 再起動フラグクリア）と C4（`web:progress` の live 評価化）が
  次サイクルの実装候補。C2 は 1 行修正で観測 1 の server 側原因を根治でき、C4 は観測 2 を根治できる

  本サイクルのスコープ外（Flutter アプリ側のコードは対象外のため）
