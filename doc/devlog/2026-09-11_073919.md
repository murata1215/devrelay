## 背景

`/lite`（Lite シェル）は L3 までで「読む」ことができるようになったが、入力欄は disabled のプレースホルダの
ままで送信できなかった。L4 のゴールは `/lite` から**送信できる**ようにすること。

## 報告事項（仕様と実コードの相違、承認済みの回避策）

プラン本文に詳細を記載済み（7 件、R1〜R8）。要点のみ:

- **R1**: `apps/server/src/platforms/web.ts` の `web:user_message` broadcast は送信者自身の chatId を
  除外するため、Lite タブは自分の発言を WS 経由で**永久に受け取らない**。楽観的表示は必須。
- **R2**: `mergeHistory('replace'|'refresh')` は history が空だと live 専用エントリを全滅させるため、
  素朴な `messages` への直接 push では create-then-send 直後に消える。
  → **新規純モジュール `apps/web/src/lib/lite-outbox.ts`**（外部 import ゼロ）を追加し、送信中の自分の
  発言を `messages` の外側に保持、`composeDisplayMessages()` でレンダー時に純粋合成する。
- **R3**: 「`web:command` を送らないこと」は字義どおりには実装不可能（classic の通常送信自体が
  `web:command` フレームであるため）。「コマンド文字列（u/w/x/e、`//connect`）を送らない」
  「フレームを自前組み立てしない（`useWebSocket` 内に閉じる）」と読み替え、静的走査テストを
  そのとおりに書き換えた（テスト内コメントに理由を明記）。
- **R4**: `LitePage.tsx` の JSDoc 自体が `//connect` という文字列を含むため、ガードは
  `stripComments()`（新規純関数、行/ブロックコメント除去）適用後の本文に対して検査する。
- **R5**: `ThreadList.tsx` に `onRequestCreate?` / `createInFlight?` を**純加算**し、Lite の
  「＋新規」は自前 tabId で作成する経路を通す。classic 側の `disabled` 真理値は
  `decideThreadCreateButton()` の真理値表テスト（8 パターン全数）で不変を固定。
- **R6**: markdown レンダラの共有化は不可能（`ChatPage.tsx` モジュールローカル関数、export すると
  diff 0 違反）。L3 の判断（素テキスト）を据え置き、**L5 候補**として記録（下記申し送り）。
- **R7**: `decideSendAction` は `machineOnline` でもブロックする（B1 の 3 条件の上位互換、既存仕様を採用）。
  人間承認条件 4 により、A2 のプレースホルダに専用の `'machine-offline'` 理由（「マシンがオフラインです」）を追加。

## 実装内容

### A. L3 手直し
- A1: `sortProjectSelectorOptions()`（マシン名→プロジェクト名の安定ソート、`buildProjectSelectorOptions`
  自体は既存テストの順序保持を守るため無変更のまま維持）
- A2: `resolveComposerPlaceholderReason()`（`connecting` / `machine-offline` / `no-project` / `ready`）
- A3: `decideProjectSelectorUrl()`（セレクタ変更で別プロジェクトなら session を URL から外す）+
  `shouldShowNewThreadNotice()`（`decideSendAction` の `needsNewThread` と同一条件であることをテストで固定）

### B. 送信
- B0: `lite-outbox.ts` 新規（`appendOutbox` / `removeOutbox` / `composeDisplayMessages`、`OUTBOX_MAX_ENTRIES=8`）。
  `composeDisplayMessages` は content 完全一致の貪欲 1:1 マッチングで dedupe し、`messages` を
  再ソートしない・空 outbox は同一参照を返す（不要な再レンダー防止）。
- B1: 入力欄は送信中も disabled にしない（B6）。Enter=送信/Shift+Enter=改行は classic と同一（IME
  判定なしも classic 同様に踏襲）。
- B2/B3: `decideSendAction()` の結果で分岐。B3（`create-then-send`）は `switchChainRef` で直列化し、
  `POST /api/threads` の 201 を同期点として URL 更新 → `switchThread`（冪等）→ outbox へ追記 →
  `sendCommand(text)`（**projectId ヒントは渡さない**、F1 の罠を回避）。
- F1 対策: 選択中スレッドの「実際の」プロジェクト ID を `threadProjectConfirmation` state で追跡し、
  情報源はサーバー確認済みの 2 つ（スレッド一覧クリックの `ThreadSummary.projectId` /
  `switchThread` 応答の `ThreadSwitchResult.projectId`）のみ。未確認時は `null` → `decideSendAction`
  が不一致側に倒れて fail-safe（不要な新規スレッド作成はあっても誤合流はしない）。
- B4: 「＋新規」ボタンは `ThreadList` の `onRequestCreate` 経由で `LitePage` の
  `buildThreadCreateRequest()`（tabId 必須の唯一 factory）を通し、作成のみ行う（送信はしない）。
  `createInFlight` state を新設し `ThreadList` に配線（作成中はボタンが `disabled` になる）。
- B-x: 描画ゲートを `historyLoading` 排他から `displayMessages.length === 0 && historyLoading` に変更。
  `historyLoadFailed` は上部バナーとして独立表示。セッション切替時は E3 で同期的に `setMessages([])`
  してから非同期取得を開始し、前スレッドの本文が一瞬混ざるのを防止。
- `useWebSocket.sendCommand` の戻り値を `void` → `boolean` に変更（純加算。`ChatPage.tsx` は戻り値を
  無視しているため無変更で動作）。`false`（WS 未接続で送信できなかった）のとき、outbox エントリを
  `removeOutbox` で撤回し composer 本文を復元する。

## E2E（人間側で実施 → 本 devlog に追記予定）

L3 の E2E も未実施のため合流して実施する。

| # | 内容 | 期待 |
|---|------|------|
| E2E-1 | classic と lite を別タブで同一スレッドに接続し、lite から送信 | 両タブに user メッセージ + AI 応答が出る |
| E2E-2 | 同一タブで `/` ↔ `/lite` を往復 | live WS が二重接続にならない（DevTools の WS が 1 本） |
| E2E-3 | lite でプロジェクトを切り替えて送信 | 新規スレッドが作られ URL の `session` が変わり、classic の一覧に現れる（F1 の回避確認） |
| E2E-4 | 「＋新規」を押す | 新規スレッドが作られ、そのまま送信できる（押した時点では送信は起きない） |
| E2E-5 | 自分の発言 + 応答（**楽観的表示 ↔ REST 履歴の照合を必ず確認**） | 二重表示されない。照合キーは **content + 時間窓**（`lite-outbox.ts` の `composeDisplayMessages` は content 完全一致の貪欲 1:1 マッチングで行い、`knownMessageIds` により送信前から表示済みだった同文面の過去メッセージとは誤マッチしない。L3 の dedupe（`lite-message-log.ts` の `mergeHistory`）と同じ「サーバー確定値が来たら差し替える」考え方に揃えている。手順: (1) lite で送信直後に自分の発言が即座に 1 件だけ表示される（楽観的表示）→ (2) AI 応答到着後、履歴取得（E3 の refresh）で自分の発言がサーバー確定値と差し替わり、依然 1 件のまま + AI 応答が追加される（合計 2 件）→ (3) 同一文面を連投しても各送信ごとに 1 件ずつ確定していくこと（貪欲マッチの確認） |
| E2E-6 | `pm2 restart devrelay-server` 後 | lite が自動再接続し送受信が復帰する |
| E2E-7 | ダーク / ライト両方でプロジェクトセレクタを確認 | 可読、マシン → プロジェクト順で並ぶ |

## L5 申し送り

- **承認カード（`web:tool:approval`）の応答経路**: `sendToolApprovalResponse` は L4 でも未使用のまま
  （静的走査テストで固定済み）。L5 で `LiteApprovalCard` から呼び出す経路を実装する必要がある。
  R5 fail-closed（`shouldShowApprovalCard`）の維持が前提。
- **質問（AskUserQuestion）の応答経路**: 未着手。承認カードと同様の経路を新設する必要がある。
- **F6: ハードコード日本語**: `lite-shell-rules.ts` / `LiteComposer.tsx` 等に残っている
  （i18n キー化は L5 以降の課題として先送り）。
- **`messageId` 付与のサーバー小サイクル**（L3 からの持ち越し、今回も未解消）:
  `web:user_message` の payload に `messageId` を付ける + 送信者自身にも配送する（R1 の根治）。
  これが入れば `lite-outbox.ts` の content 照合ヒューリスティックを id 照合に単純化できる
  （貪欲マッチングや `knownMessageIds` スナップショットが不要になる）。
- **本サイクルの負債**: R6（markdown レンダラ非共有、Lite は素テキスト表示のまま）、
  添付ファイル未対応（`sendCommand` の 2 引数目 `files` を渡していない）。
