# #358 MCP `submit_instruction` への添付ファイル対応（画像対応込み）

## 要求
プランモードで検討・承認済みの `elegant-snacking-kite.md` プラン「MCP `submit_instruction`
への添付対応（案A・画像対応込み）」を実装する。前サイクルの読み取り専用調査で、
`sendPromptToAgent()` の `files`（第5引数）は Agent 側まで完全に配線済みだが MCP
`submit_instruction` はそこに常に `undefined` を渡しているだけと判明していた。要件は
「配線を1本繋ぐ」ことと、その配線が開く新しい攻撃面（ファイル名がディスク書き込み先と
プロンプト平文の両方に流れる）をサーバー側で必須の検証として塞ぐこと。承認ノートにより
案1（Part A サーバー側必須 + Part B Agent 側多重防御の両方）を採用、Part A/B は分離可能な
形で実装し、Part B の反映（各マシンの `u`）は人間が行うことを明記する。

## 実行
### Part A（サーバー、`apps/server`）
1. 新規 `apps/server/src/services/attachment-validation.ts`（外部 import ゼロの純関数群、
   `human-text-fence.ts` の provenance 境界とは性質が異なる**セキュリティ境界**として拒否
   ベースで実装）。
   - `sanitizeAttachmentFilename()`: basename 化・制御文字除去・NUL/`.`/`..`/空/101文字超は
     拒否（切り詰めない）。
   - `decodeStrictBase64()`: 空白除去 → 正規表現 `^[A-Za-z0-9+/]*={0,2}$` + 長さ%4 検証 →
     デコード → 再エンコードして往復一致確認の3段。
   - `detectMimeFromMagicBytes()`: PNG/JPEG/GIF/WebP を実バイト列で判定（宣言 MIME を信用
     しない）。text/* は「画像シグネチャに一致しない」判定を UTF-8 妥当性チェックより**先に**
     行う（実装中にテストで発見: 逆順だと PNG バイト列が UTF-8 として不正になるため
     `mimeMismatch` ではなく `textInvalidUtf8` に埋もれて実体が画像であることが見えなくなる
     バグを踏んだため順序を確定）。
   - `validateAttachments()`: 件数10/単体5MB/合計10MB、サイズの権威はデコード後の実バイト長
     （クライアント申告 `size` は不使用）。
2. `apps/server/src/mcp/tools.ts`: zod スキーマに `attachments?` 追加、検証を `createSession`
   より前（状態変更ゼロの時点）で実行し `ok:false` ならツール `isError:true` で拒否理由・
   limits・failures を返す。成功時は WebUI 受け口（`command-handler.ts`）と同一形の
   `MessageFile` ネスト create（`Buffer.from(...,'base64')` で実バイト列保存、
   `direction:'input'`）+ `processMessageFilesEmbedding()` の fire-and-forget 呼び出し、
   `sendPromptToAgent()` の第5引数に検証済みファイルを渡す。`humanTextMeta`・ツール応答とも
   添付があるときだけ既存キー末尾にオブジェクトを追加する設計とし、無添付時は
   `undefined`/`{}`（スプレッド構文）でコード構造として現行と1バイトも変わらないことを担保。
3. `apps/server/src/mcp/server.ts`: `POST /mcp` に `bodyLimit: 16 * 1024 * 1024` を明示
   （Fastify 既定 1 MiB のままでは添付合計10MB→base64約13.34MBに届かない）+
   `SERVER_INSTRUCTIONS` に、bodyLimit 超過はツール呼び出し前の HTTP 413 として現れる旨を
   1文追記。
4. 新規テスト `apps/server/tests/attachment-validation.test.mjs`（39件）。

### Part B（Agent、3 OS、`agents/{linux,macos,windows}`）
5. `file-handler.ts` に純関数 `sanitizeSavedFilename()` を追加し、
   `join(filesDir, prefixedFilename)` の**前**に適用。サーバーとは異なり Agent 側は
   **拒否せず正規化**（basename 化・制御文字除去、空/`.`/`..` は `attachment` に
   フォールバック、120文字で切り詰め、変更時は `console.warn`）。加えて保存直前に
   `path.resolve()` による構造的な最終確認を追加し、サニタイズにすり抜けがあっても
   `filesDir` の外には書き込めないことを保証（違反時は該当ファイルのみスキップしバッチ
   全体は継続）。
6. linux で実装後、macos・windows へ展開。linux/macos は `diff` で byte-for-byte 同一を
   確認、windows は絵文字なし（`console.warn`/`console.log`）・英語プロンプト文言という
   既存の2つの差異のみ維持していることを `diff` で確認（差分行が期待どおり3行のみ）。
7. 新規テスト `agents/{linux,macos}/tests/file-handler.test.mjs`（19件、linux/macos
   byte-for-byte同一、`atomic-write.test.mjs` を先例に一時ディレクトリを使用）。

## 発見
- **既存 WebUI 経路でも今日成立していた穴**: Part B 導入前は `file-handler.ts` の
  ファイル名サニタイズが皆無で、`filename = "../../../etc/passwd"` のようなファイル名は
  `join(filesDir, "20260905_..._../../../etc/passwd")` が正規化され `.devrelay-files`
  はおろか `projectPath` の外にまで書き込める状態だった。これは本サイクルで新設した
  MCP 経路に限らず、**既存の WebUI（`web:command` フレーム）経由でも今日まで成立して
  いた脆弱性**であり、サーバー側の検証有無に関わらず Agent 側で塞ぐ必要がある根拠と
  なった。
- text/* の MIME 判定順序（画像シグネチャ判定を UTF-8 妥当性判定より先に行う）は
  実装中にテストで踏んだバグで、順序を誤ると偽装検知の理由が誤ってラベリングされる
  （`mimeMismatch` になるべきものが `textInvalidUtf8` になる）ことを確認済み。
- `/ws/web` に `checkIpAllowed`（#285 の組織 IP アクセス制限）が掛かっていない件は、
  本サイクルの調査過程で改めて存在を確認したが、**プラン記載どおり本サイクルでは
  修正しない**。既知のギャップとして本記録に残すのみ。
- Part A（サーバー）だけでも MCP 経由添付の要件は完全に満たされるが、Part B
  （Agent 側の多重防御）の反映には **各マシン（Linux/macOS/Windows）の `u` が必須**
  であり、これは人間が実施する。本サイクルでは commit + push のみ行い、
  `pm2 restart devrelay-server` およびフリートの `u` はいずれも実行していない。
