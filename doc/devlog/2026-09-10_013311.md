# スレッド管理 サイクル3（WebUI）: スレッド一覧パネル

## 背景
- サイクル1（`93b0e91`）で server、サイクル2（`b4b05b2`）で agent（scope-aware な会話クリア）が対応済み。
- 本サイクルはスコープを `apps/web` + `doc` に限定し、`doc/thread-management-spec.md` §5 §6 の設計を実装する。
- 起点確認: `git log -1 --oneline` = `b4b05b2`、`git status -sb` = `## main...origin/main`（差分なし = clean）。

## 現状調査で確定した事実（read-only）
- `apps/web` は「タブ＝プロジェクト 1:1」のまま。1 プロジェクトに複数スレッドがあっても UI 上は 1 本に潰れている。
- 履歴取得は `/api/projects/:id/messages`（プロジェクト横断）→ 別スレッドの発言が混ざる。
- server は `web:response` / `web:progress` の payload に `sessionId` を既に載せている（`apps/server/src/platforms/web.ts:279,342,356`）が、`apps/web/src/hooks/useWebSocket.ts:32-42` のローカル型 `ServerToWebMessage` が `sessionId` を定義しておらず**受信側で捨てている**。
- `web:session_info` には `title` / `agentScopeId` が既に付与されているが、クライアント側の型・ハンドラが未対応。
- DB の ALTER 3 本（`Session.title`/`lastActiveAt`/`agentScopeId`）は Prisma Client 生成済み・server dist に `/api/threads` 実装あり・pm2 稼働中で P2022 エラーなし → 適用済みと推定。

## 実装方針
1. **fail-open ルーティング**（`lib/thread-routing-client.ts`、外部importゼロの純関数 `shouldRouteToTab()`）: payload と tab の両方に sessionId があって不一致のときのみ drop。どちらか無ければ accept。`//connect` 応答・`web:user_message`・旧 server dist・タブ復元直後もすべて accept = 現行と同一挙動を保つ。
2. **履歴の後方互換**（`resolveHistorySource()`、同ファイル）: sessionId があれば `/api/sessions/:id/messages`、無ければ従来の `/api/projects/:id/messages` にフォールバック。
3. **ThreadList 表示ルール**（`lib/thread-list-rules.ts`）: §6 準拠（`lastActiveAt desc`、NULLは`startedAt`代替、既定スレッドは常に表示、firstUserMessage先頭40字フォールバック、相対時刻）。
4. テストは apps/web に既存テスト基盤が無いため、他5 workspace と同じ「`dist-test/` を `node --test` で読む」方式を新設（`tsconfig.test.json`、`references` には入れない、新規依存ゼロ）。

## 報告事項（スコープ外の穴・read-only 確認で確定）

### v1 の既知の制約（意図的な縮退、doc/changelog.md にも記載）
1. **`/api/sessions/:id/messages` は `sourceProjectName` を返さない**（`/api/projects/:id/messages` は返す）。履歴をスレッド限定にしたことで、クロスプロジェクトクエリの送信元バッジが `mode==='initial'`/`'replace'` 経路では表示されない。spec §5「クロスセッションスクロールバックは v1 で『スレッド内のみ』に縮退」の想定内の縮退として許容する。
2. **Plan / Issues / 承認履歴は projectId ベース**（`getLatestPlan()` / `readFile()` / `getApprovals()`）。同一プロジェクトの複数スレッドで同じプランが見える。#375 でプランは意図的にプロジェクトスコープに設計されており、**v1 では非対応**（spec §5 の「Plan / Exec カード、ツール承認カードは sessionId 紐づけのまま動く想定」を read-only で確認した結果、Plan カード自体は元々 projectId ベースであり本サイクルによる新規劣化ではない）。
3. **`packages/shared/src/types.ts` の `ServerToWebMessage` が stale**。spec §3.3 は「cycle3 で追従」を想定していたが、`apps/web` は独自のローカル型（`useWebSocket.ts` 内の `ServerToWebMessage`）を使っており実害はない。**spec からの意図的な逸脱**として本 devlog に明記する。`packages/shared` 側の型更新は本サイクルのスコープ外（`apps/server`/`agents` 側の実装が変わらない限り、shared 側だけを直しても実効性が無いため）。

### サイクル4 への引き継ぎ事項（read-only 確認のみ、本サイクルでは修正しない）
1. **ツール承認カードは sessionId を持っていない**。`apps/web/src/hooks/useWebSocket.ts:5-16` の `ToolApprovalPrompt` は `projectId`/`originProjectId` のみ保持。同一プロジェクトに 2 本のスレッドがあると、片方の承認カードがもう片方を表示中のタブにも出てしまう（承認自体は `requestId` で届くため誤動作＝誤承認は発生しない。表示だけの穴）。修正には `apps/server/src/platforms/web.ts:312` 付近の承認リクエスト payload に `sessionId` を追加する必要があり、**`apps/server` スコープのため本サイクルでは対応不可**。なお切断復元経路（`web.ts:100-103`, `:156-162`）は `getPendingToolApprovalsForSession(sessionId)` を使っており、こちらは正しく sessionId 単位で動作している。
2. **`web:user_message` に sessionId が載っていなかった問題は、サイクル1で `apps/server/src/platforms/web.ts` に既に追加されていることを確認済み**（本サイクルの調査時点で `useWebSocket.ts` の型定義側が追従していなかっただけ）。本サイクルの型追加（上記「変更ファイル」節）で解消済み。
3. **`decideConnectTarget().explicitSessionId`（`apps/server/src/services/thread-routing.ts:56-66`）が `//connect` 経路から未使用のデッドコード**。`handleProjectConnect`（`apps/server/src/services/command-handler.ts:501`）が呼び出し時に渡していないため、プロジェクトタブを離れて `//connect` で戻ると常に「最新スレッド」が選ばれ、ユーザーが選択していたスレッドから意図せず離脱する。修正は `apps/server` 側 1〜2 行の想定。**サイクル4の第一候補**（`apps/server` スコープのため本サイクルでは対応不可）。

## E2E 検証手順（人間側、spec §8 対応）

1. **新規スレッド作成**: ThreadList の「＋ 新規」をクリック → 一覧に新しい行が増え、`lastActiveAt desc` で先頭に入る。agent 側に `.devrelay/sessions/<id>/` が作られること（agent ログ or ファイルシステムで確認）。
2. **スレッド単位の会話分離**: スレッド A で「合言葉 X」を教える → 新規スレッド B を作成して「合言葉は？」と聞く → 知らないと返る（claude resume がスレッド単位で分離されていることの確認）→ A に切り替えて聞く → 正しく答える。
3. **fail-open ルーティングの drop 検証（唯一の drop パス）**: 2 タブ（または同一プロジェクトの2スレッド）で A / B を同時に開き、A に投げた指示の出力が B のタブに出ないことを確認する（`shouldRouteToTab` が両方の sessionId が既知で不一致のときのみ drop する設計の実地検証）。
4. **改名の永続化**: ペンアイコンで改名 → 一覧に即反映（楽観更新）→ ブラウザをリロード → 改名後のタイトルが保持されている（`PATCH /api/sessions/:id` が実際に効いていることの確認）。
5. **scope-aware な `x`（サイクル2の確認・非退行）**: scoped スレッド（`agentScopeId` 付き）で `x` を実行 → サイクル2の案内文がそのまま表示され、fail-closed のまま変わっていないこと（本サイクルは `x` の挙動を一切変更していない）。
6. **未 `u` の機体での既定スレッド非退行**: 既定スレッド（`isScoped:false`、「既定」バッジ表示）で通常のチャットが従来どおり動くこと。
7. **MCP `submit_instruction` の可視性**: MCP 経由で作成された Session が ThreadList の一覧に出て、`approve_implementation` 等の既存フローが壊れていないこと。
8. **`//connect` 互換**: 既存プロジェクトに `//connect` で入ると最新スレッドに入ること（**既知の制限**: 上記引き継ぎ事項#3 により、ユーザーが手動で選択していたスレッドから離脱していた場合でも常に「最新スレッド」に戻ってしまう。これは本サイクルで新規に発生した問題ではなくサイクル1由来の既存動作であり、サイクル4で対応予定）。
