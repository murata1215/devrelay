## 要求

サイクル1（commit `6ae9c8e`）の `search_knowledge` は `Session.userId = 自分` のみを検索するため、
部署で使うと「個人のメモ帳が 59 冊並ぶ」状態になる。**数字 1 本の機密度（0〜10）＋ 案件名の文字列
（compartment）** で「誰が何を見られるか」を決め、他人の会話が見えたときは既存の統制 v3 監査
（`SupervisionAuditLog`）に残す。あわせて、個人 OpenAI キーを持たない人の会話もベクトル化されるよう
組織共通 embedding キー（環境変数）を導入する。対象は `apps/server` のみ（agents/web/shared は 0 行変更）。

## 発見

- `UserClearance.compartments`（`String[]`）は本スキーマ初出の Postgres `text[]` 列。Prisma は scalar list
  に `NOT NULL` を付けない仕様のため、手書き DDL でも `NOT NULL` を省略して `prisma db push` と形を揃えた
  （`prisma migrate diff` で実測して確認）
- raw SQL に配列パラメータを渡す前例が無かったため、compartment の複数値照合は配列バインドではなく
  `IN ($n, $n+1, …)` への個別展開に統一した（`buildVisibilityPredicate` が採番込みで返す）
- `mcp-ask-source-guard.test.mjs` の `indexOf("server.tool(\n      'get_answer'")` 等はインデント込みの
  文字列一致のため、新規ツールは `ask_project`/`get_answer` の間を避けて挿入位置を選んだ
  （`search_knowledge` の直後・`approve_implementation` の直後）
