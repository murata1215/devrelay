# core#337: 実行中でも出る「5分無応答タイムアウト」誤検知の解消 (2026-08-31)

## 要求
ユーザー報告: 実装/調査が正常に走っている最中でも `⏱️ タイムアウト: エージェントから応答が
ありませんでした（5分経過）` が出る。しばらく待つと本当の結果が届くため実害は「誤報が混ざる」ことだが
毎回ノイズになる。前サイクル（read-only 調査 + core#335 実装）とは別の残プラン
（`vast-stargazing-marble.md` 下部、前サイクルで提出済み・未実行）を本サイクルで実装した。

## 実行
1. 新規 `apps/server/src/services/progress-timeout.ts`（外部 import ゼロの純粋関数
   `decideProgressTimeoutAction()`、`human-text-fence.ts` 等と同じ流儀）を作成。判定は
   「ハードタイムアウト超過→無条件finalize」「マシンonline→extend」「offline→finalize」
   「不明(null)→finalize（fail-safe）」の優先順位。
2. `packages/shared/src/i18n.ts` の `progress.timeout` を「（5分経過）」固定から `{min}` 埋め込みに変更。
3. `apps/server/src/services/session-manager.ts`:
   - `PROGRESS_TIMEOUT`/新設 `PROGRESS_HARD_TIMEOUT` を `DEVRELAY_PROGRESS_TIMEOUT_MS`/
     `DEVRELAY_PROGRESS_HARD_TIMEOUT_MS`（#321 の命名流儀）で調整可能に（既定 5分/60分）。
   - `ProgressTracker` に `machineId: string | null` を追加。`sessionMachineMap`（`sessionProjectMap` と
     同じ流儀）を新設し `createSession()`/`restoreSessionParticipants()`/
     `restoreSessionParticipantsForMachine()`/`startProgressTracking()` の4箇所で解決・キャッシュ
     （`startProgressTracking()` は既存の projectId 解決 DB クエリの `select` に `machineId` を足すだけで
     クエリ数は増やさない）。
   - `startProgressTracking()` と `appendSessionOutput()` に別々にコピーされていた同一の `setTimeout`
     ブロック（#304/#319 と同種の同期漏れ予備軍）を `armProgressTimeout(sessionId)` に一本化。
     `startProgressTracking()` 側は `progressTrackers.set()` の**後**に呼ぶよう順序を調整
     （`armProgressTimeout` は `progressTrackers.get()` でトラッカーを引くため）。
   - 満了ハンドラ `onProgressTimeout(sessionId)` を新設。`tracker.machineId` から
     `prisma.machine.findUnique({ select: { status: true } })` で生存確認し
     `decideProgressTimeoutAction()` に渡す。`extend` ならログのみでチャットには何も出さず再武装、
     `finalize` なら従来どおり `finalizeProgress()` を呼ぶ（`tChat(..., 'progress.timeout', { min })`）。
   - `session-manager.ts` は `agent-manager.ts` を import していないため、`Machine.status` を直接
     `prisma` 経由で読む方式にして循環 import を回避（プラン通り）。

## 発見
- 決定的な証拠は `~/.pm2/logs/devrelay-server-out.log` にあった: `ask-member` のクロスプロジェクト
  問い合わせ HTTP が `responseTime: 473368ms`（約7.9分）かかっており、その間呼び出し元セッションは
  `ask.sh` を実行する1個の Bash ツール内で待機中で出力ゼロだったため
  `⏱️ Progress timeout ... (300s since last output)` が誤発火していた（直近7日で17件、全件「無出力側」）。
- Devin（`ai-runner.ts`）・Codex・PTY 端末モードには元々30秒ハートビートが実装済みだったが、Claude SDK
  経路（`sendPromptToAiSdk`）にだけ無かった。今回は Agent 側にハートビートを追加するのではなく、
  サーバー側の判定軸を「出力が来たか」から「エージェントが生きているか」に変える設計を採用した
  （Agent 変更ゼロ・全マシン即日反映という利点があるため）。
- 副作用としてタイムアウト時に `progressTrackers` が削除され、以降の途中出力が
  `⚠️ No tracker found for session ...` として捨てられる挙動も実ログで確認済み（今回のソフト/ハード
  二段化により誤タイムアウト自体が減れば、この副作用の発生頻度も連動して下がる）。
- ハードタイムアウト（60分）はマシンが online のまま応答が返らない万一のケースの安全網として追加した。
  ソフトタイムアウトの再武装ループだけでは理論上無限に延長され得るため、ユーザーは `k`（kill）で
  いつでも中断できる旨をプランに明記していた。
