# core#334: ゲート①②③ 人間入力テキストの長さ上限・provenance fence・監査

## 要求

前サイクル（`vast-stargazing-marble.md` プラン）の経路調査（A. 経路一覧表）を受け、人間が以下を確定した:
実装対象は① `approve_implementation.note` / ② チャット `e,<指示>` / ③ `submit_instruction.instruction` の
3経路に限定（⑤ask/⑥teamexec/⑦AskUserQuestion回答はスコープ外）。上限値は①2,000/②4,000/③20,000
（`string.length`基準）で確定、超過時は切り詰めず400拒否、監査はDDL付き（メタのみでraw text復元不能な設計は
不可）、処理順序は「制御コマンド解析→payload抽出→長さ検証→fence」を全経路で統一し `w` を特例扱いしない。
fence は権限のセキュリティ境界ではなく provenance（由来）境界として設計・命名すること。
exec 承認後の追加要件（承認メッセージ）で、長さ検証は各経路のあらゆる状態変更より前に行うこと、長さの定義を
UTF-16 code unit数に統一しJSDoc+テストで明示すること、F3（teamexec転送時のfence未適用）は今回スコープ外の
まま残件記録すること、自己改変サイクルにつきpm2 restart/DDL適用は行わないことが明示された。

## 実行

新規 `apps/server/src/services/human-text-fence.ts`（外部import ゼロの純粋関数: `validateHumanTextLength`/
`neutralizeHumanInputTag`/`fenceHumanText`）を作成し、`approval-prompt.ts`（①）・`mcp/tools.ts`（①③）・
`command-handler.ts`（②）に適用。③は`createSession`より前、①は`Message.create({content:'exec'})`より前、
②は`handleExec()`冒頭（`lastRemoteProjectId`分岐より前）で長さ検証し、拒否時は状態変更が一切発生しない
配置であることをfile:lineで確認した（`mcp/tools.ts:475-489`/`:609-626`+`:644`、`command-handler.ts:697-710`
+`:713`）。②の`w`判定は`customPrompt?.startsWith(W_PROMPT_PREFIX_JA/EN)`という fence 後文字列依存の脆い
実装から、`command-parser.ts`が解析時点で付与する構造的な`promptOrigin`（`packages/shared/src/types.ts`の
`UserCommand`拡張）に置き換えた。監査は`Message.humanTextMeta String?`（新規DDL、`doc/migrations/
334_message_human_text_meta.md`に記載のみ、人間がpsql適用）に`rawRef`でraw text所在
（`message.content`/`session.approvalNote`）を明記するJSON文字列を保存する設計。`i18n.ts`に
`humanText.tooLong`（ja/en）を追加。

## 発見

- `mcp/tools.ts`の①は当初プランでは「Session.approvalNote保存より前」の検証を想定していたが、
  exec承認時の追加要件で「Message.create（'exec'固定文字列アンカー）より前」というさらに早い位置が
  明示され、それに合わせて実装した（get_build_statusのexecアンカー`content==='exec'`は無変更のまま
  humanTextMetaのみ同じ行に条件付きで付与）。
- スコープ外事項（次サイクル送り）: ⑤ask/⑥teamexec/⑦AskUserQuestion回答への長さ検証・fence適用、
  および`handleExec()`の`lastRemoteProjectId`（teamexec転送）分岐へのfence適用（F3、長さ検証自体は
  分岐より前に位置するため効いているがfence本体は未適用）。
- **DBマイグレーション適用（psql）+ `npx prisma generate` + server再起動が必要**（自己改変サイクルの
  ため本サイクルでは一切実行していない）。実チャットでの①②③超過拒否の実機確認は人間の反映後に別途必要。
