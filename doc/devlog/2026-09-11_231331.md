# スレッド管理 サイクル6: 送信が既定スレッドに入らず新規スレッドを作る + 空 ended セッション増殖の根治

日時: 2026-09-11 23:13 (JST)
プラン: `~/.claude/plans/eager-seeking-token.md`
スコープ: `apps/server` のみ。`apps/web` / `agents/*` / `packages/*` / `prisma/schema.prisma` は無変更、
DB マイグレーションなし（`git diff --stat` で確認）。

## 発端（read-only 調査の要約）

`FORKCAST_PoC` プロジェクトで報告された事象:

1. classic UI で既定スレッド（`cmtvf87l1...`）を開いた状態で送信したユーザーメッセージが、
   既定スレッドではなく新規作成された別スレッド（`cmtwf2e7j...`）にだけ保存された
2. 生成中の出力（生中継）は既定スレッドと新規スレッドの**両方**に表示された（Agent の実行は1回のみ）
3. 同じプロジェクトに `msgs=0 / status=ended / agentScopeId=self` の空スレッドが4件生成されていた

読み取り専用調査（サーバーログのフォレンジック + ソース精読）でファイル:行レベルの原因を確定した。

## 原因（3つとも「バグ」と判定）

### 事象1: `command-handler.ts` の Agent 再接続時セッション再確立

`agent-manager.ts` は Agent の WebSocket **再接続のたび**（Agent プロセス自体の再起動でなくても）
無条件に `needsSessionRestart` を立てていた（旧 `:548`）。これを受けて `command-handler.ts` の
`handleAiPrompt`（旧 `:1737-1795`）と `handleExec`（旧 `:915-961`）は、次のプロンプト/exec 送信時に
**新しい Session 行を `createSession()` で作成**し、`ChannelSession.currentSessionId` をそちらへ
差し替えていた。これが「送信が既定スレッドに入らず新規スレッドを作る」の直接原因だった。

新規 Session 作成は不要だった: Agent 側（`connection.ts`）は未知の sessionId を受け取ると
projectPath/aiTool から自動初期化する自己修復を既に持っており、同一 sessionId への
`session:start` 再送は Agent 側で冪等（`ai-runner.ts`）。

### 事象2: 生中継の二重表示（事象1の副作用）

再確立経路は `web:session_info` を一度も送っていなかったため、ブラウザの `tab.sessionId` が
旧セッションIDのまま取り残される一方、配送 payload には新セッションIDが載っていた。
`shouldRouteToTab`（web 側、fail-open）はこの不一致を許容して描画してしまい、かつ classic は
プロジェクトタブ単位で1本のメッセージバッファしか持たないため、両方のスレッドに同じ内容が
表示されているように見えていた。

### 事象3: 空 ended セッションの増殖

`//connect`（`handleProjectConnect`）の再利用候補クエリが `status:'active'` のみを見ており、
Agent オフライン中に `clearSessionsForMachine()` で全セッションが `ended` になった直後の
`//connect` は候補ゼロと判定して新規 `origin:'interactive'` セッションを作成していた。
Agent がまだオフラインのためその `startAgentSession` は無音で失敗し（`sendToAgent FAILED`）、
メッセージ0件のまま孤児化していた。

## 修正（Fix A / B / C。人間承認済みの3点を実装）

新規モジュール `apps/server/src/services/thread-reestablish.ts`（外部 import ゼロ、純関数3本。
`thread-routing.ts`/`thread-clear-guard.ts` と同じ流儀）:

- `decideSessionReactivation({ status })`: 再確立対象が `ended` なら `active`+`endedAt:null` に
  戻すべきと判定する（`ended` 以外は何もしない）
- `decideEndedRevival({ preferredThreadId, endedCandidateIds })`: `//connect` で active 候補が
  無い場合、`preferredThreadId`（`resolvePreferredThreadId()` の結果）に**ちょうど一致する**
  ended のみ復活させる。「最新の ended」を無条件に復活させることはしない
  （24h アイドルスイープの対象である無関係な古い ended スレッドを保護するため）
- `decideSessionInfoPush({ beforeSessionId, afterSessionId })`: 処理前後で `currentSessionId` が
  変わっていれば `web:session_info` を再送すべきと判定する

### Fix A（`command-handler.ts` の `handleAiPrompt`/`handleExec` 再確立ブロック）

`createSession()` 呼び出しを削除し、`context.currentSessionId` をそのまま再利用するよう書き換えた。
`decideSessionReactivation()` で `ended` なら `active` に戻し、`addParticipant()` は
（`clearSessionsForMachine` が participants を消している可能性があるため）必ず呼ぶ
（`addParticipant` 自体が重複追加を防ぐため冪等・無害）。`updateUserContext`・`context.currentSessionId`
の再代入・旧参加者マイグレーションループは不要になったため削除。exec 経路の冒頭にあった
`removeParticipant()`（旧セッションから一瞬でも参加者を外す処理）も、同一 ID を再利用する本実装
では不要かつ有害（その一瞬に届く配送を取りこぼす）なため削除。

### Fix B（`web.ts` の `web:command` ハンドラ）

`emitSessionInfoIfChanged()` を新設し、コマンド処理開始前の `currentSessionId` と処理後の値を
`decideSessionInfoPush()` で比較。変化があれば新セッションの全 web 参加者（他ブラウザタブ含む）に
`web:session_info` を再送する。`hintProjectId` フォールバック・`handleContinue` 経由の自動再接続
（`handleAiPrompt`/`handleExec` 内部）・Fix A 後も残りうる再確立経路の3つを、この1箇所の
前後比較で一括カバーする。既存の `//connect` 明示コマンド分岐は自前で送信して `break` するため
二重送信は発生しない。

### Fix C（`command-handler.ts` の `handleProjectConnect`）

active 候補が無い場合、`preferredThreadId` があれば同一ユーザー・同一プロジェクト・同一マシンの
`ended` セッション ID を取得し `decideEndedRevival()` に判定させる。復活の場合は該当セッションを
`active`+`endedAt:null` に更新して reuse 扱い（`isResumed=true`）にする。`startAgentSession` は
ここでは呼ばない（Agent 側自己修復、または次のプロンプト送信時の Fix A 再確立ブロックが
遅延初期化するため）。

## 発見・所感

- 真因は今回の調査対象日（2026-09-11）の変更ではなく、**スレッド管理サイクル1（`93b0e91`、
  2026-09-09）以前から存在していた「Session 行 = 1 回の AI 実行」という旧来の再確立コード**だった。
  サイクル1が「Session 行 = スレッド」と再定義したことで、この旧コードの新規 Session 作成が
  可視化された「スレッド分岐」バグに変わり、サイクル3のスレッド一覧 UI で人目に付いた。
  `440d14b`（本日の `orderBy`/`lastActiveAt` 修正）や Lite L3〜L4.1 は無関係（前者は表示クエリのみ、
  後者は `/lite` 専用ファイルのみで `ChatPage.tsx`/server/agents は無変更）。
- Fix D（Agent が per-process `instanceId` を申告し、真の再起動時のみ `needsSessionRestart` を
  立てる）は Agent 側の変更が必要なため次サイクル送り。現状は WS 再接続のたびに再確立ブロックが
  走るが、Fix A 適用後は同一 sessionId を再利用するだけになったため実害は無い（`startAgentSession`
  の無駄な再送が発生する程度）。
