## Requirements

B2-4（`doc/devlog/2026-09-23_133642.md`）で W2（21 host 一括適用）の設計判断は確定したが、
`sites-enable-access-log.ts` / `site-log-rules.ts` の安全性欠陥 6 件（A〜F）と retention 未確定（G）

G（`ROLLOUT_ROLL_CONFIG` への B2-4 確定値反映）。

## Execution

### 計画時の read-only 調査・`/tmp` ミラー実機検証（実装前）

本番 Caddy に一切触れず、`/tmp` ミラー上で `caddy adapt` を用いて以下を実測確認した:

- **N1**: 現行 snippet のまま同一 host へ `import` を 2 回入れると adapt は PASS し、
  `logger_names["tetris…"] = ["log3","log4"]` ＝ 1 host に 2 logger が生成される
  （B2-4 F3「1 request → 2 log line」の実測確認）
- **N2**: health matcher を snippet 内（`@drl_skip_health header User-Agent DevRelay-Sites/1.0` +
  `log_skip`）に置くと adapt PASS。二重 import 時は
  `Error: matcher is defined more than once: @drl_skip_health` で adapt FAIL
  （health matcher が二重適用の第 2 防衛線として機能することを確認）
- **N3**: `64MiB/12/1440h` は adapt 後 `roll_size_mb:64 / roll_keep:12 / roll_keep_days:60` に
  正しく展開される
- **N4**: W2 フルシミュレーション（ミラーに 21 host 適用）で adapt PASS。sites logger 数 22、
  1 host = 1 logger（複数持ち 0 件）、roll 設定 1 種類、health matcher 22 回
- **N5**: `sudo -l` 実測で NOPASSWD `/bin/rm /etc/caddy/sites.d/*` は 1 引数パターンのみ
  （`-f` を付けた 2 引数は対象外。`/bin/rm` と `/usr/bin/rm` は同一 inode）
- **N6**: 既存 backup は flat 2 ファイルのみ（manifest 無し。legacy 扱いに分類）

### 実装内容

1. **`src/services/sites/site-log-rules.ts`**（修正）
   - G: `ROLLOUT_ROLL_CONFIG` を `{ rollSize:'64MiB', rollKeep:12, rollKeepFor:'1440h', provisional:false }`
     に確定（B2-4 D3）。`resolveRollConfig()` は内部実装 `resolveRollConfigFrom(target, rolloutConfig)`
     に切り出し、`null` 時の fail-closed 挙動をテストで固定できるようにした（`PILOT_ROLL_CONFIG` は不変）
   - F: `HEALTH_CHECK_UA`（単一の真実）・`HEALTH_SKIP_MATCHER_NAME`（`@drl_skip_health`）・
     `renderHealthSkipDirectives()` を新設。`renderSnippet()` / `renderInlineLogBlock()` の
     冒頭に health skip（UA 完全一致 2 行）を追加。各 site ファイルは既存の `import` 1 行のまま
   - `allSkipRuleMatcherNames()` で予約 matcher 名との衝突を検査可能にした
   - `W2_TARGET_HOSTS`（B2-4 D4 確定 21 host）を定数化
2. **`src/services/sites/site-log-apply.ts`**（新規・純粋関数のみ）
   - `assertSitesDPath()`: `/etc/caddy/sites.d` 直下の安全なファイル名のみ許可（traversal・
     絶対パス以外・NUL 文字を拒否）
   - `detectAppliedState()` / `classifyHostForApply()`: 適用状態（none/snippet/inline/mixed）を検出し、
     **already-applied / inconsistent を eligibility 判定より先に**見る（F3 の穴を構造的に塞ぐ）
   - `applyLogConfig()`: 挿入後に自己検査（import ちょうど1・matcher 重複無し等）を行い、
     違反時は `sudo tee` 到達前に throw する
   - backup manifest 一式（`newBatchId` / `isValidBatchId` / `parseManifest` / `planRollback`）:
     backup 実体を `<batchId>/b0001.bak, …` の連番ファイルにし、`/`↔`_` の非可逆変換を廃止（C）。
     rollback は batchId 完全一致でのみ動作し timestamp 部分一致を廃止（D）。
     `action:'created'` で新規作成物（snippet 等）の rollback を一般化（E）。
     sha256 drift 検出により「適用後に別の変更が入っている」状態を fail-closed で検知
   - `verifyAdaptedConfig()`: `caddy adapt` 出力 JSON から 1host1logger・roll 設定 1 種・
     health matcher 数一致を構造的に検証する W2 前ゲート
3. **`scripts/sites-enable-access-log.ts`**（I/O シェルとして全面書き換え）
   - `listHostStates()` で host を eligible/already-applied/inconsistent/ineligible に分類。
     一括適用（`--only` なし）時は eligible 集合が `W2_TARGET_HOSTS` と完全一致しなければ中止
   - `sudoWriteFile()`: `cat | sudo tee` のシェル連結を廃止し `spawn('sudo',['tee',path])` +
     stdin 経由に変更（シェル非経由・interpolation リスクを排除）
   - `sudoRemoveFile()`: `-f` を外し `execFile('sudo',['rm',path])`（引数ちょうど 1 個で
     NOPASSWD パターンに一致）。`existsSync` で事前 no-op 化。呼び出し前に `assertSitesDPath()`
   - backup を batch manifest 方式に変更。`--rollback <batchId>` は既定 dry-run（対象一覧表示のみ）、
     `--apply` 併用で実行。drift 検出時は `--force` なしでは中止
   - `--list-backups`（batch 一覧 + legacy 表示）・`--verify-mirror`（`/tmp` ミラー構築 →
     `caddy adapt` → `verifyAdaptedConfig()`）を新設
4. **`src/services/sites/sites-rules.ts` / `health-checker.ts`**（小修正）
   - `OWN_HEALTH_CHECK_UA` / health-checker の `USER_AGENT` を `site-log-rules.ts` の
     `HEALTH_CHECK_UA` の re-export・import に置換（3 箇所が同一値であることをテストで固定）
5. **テスト**
   - `tests/sites-log-rules.test.mjs`: retention 確定値・`resolveRollConfigFrom` の null 分岐・
     health UA 完全一致・matcher 衝突なし・`W2_TARGET_HOSTS` の内容/重複なしを追加
   - `tests/sites-log-apply.test.mjs`（新規 34 テスト）: パス制約・適用冪等性・自己検査・
     manifest round-trip（アンダースコア含みパス）・exact batch matching・created-file rollback・
     drift 検出・`verifyAdaptedConfig` の PASS/FAIL を固定

## Findings

- 実装前の `/tmp` ミラー実測（N1・N2）により、修正前のコードでは「1 request → 2 log line」が
  adapt レベルで検知されずに本番へ到達し得ることを構造的に確認できた。今回の
  `classifyHostForApply()`（already-applied 判定を eligibility より先に見る設計）と
  `applyLogConfig()` の自己検査により、この経路は二重に塞がれている
  （host 側の冪等ガード + snippet 側の matcher 名衝突によるアプリ全体の adapt 失敗）
- health checker 除外を snippet 側 1 箇所に集約したことで、既に適用済みの dangou も
  次回 Caddy reload 時（W2 実施時）に自動で health 除外の恩恵を受ける
  （host ファイル側の追加編集は不要）。これは意図した設計だが、W2 実施サイクルの担当者は
  「dangou の host ファイル自体は今回変更していないのに health 除外が効くようになる」ことを
  reload 前に認識しておくこと
- 既存 backup 2 件（B2-1/B2-3 由来）は manifest 方式へ移行しておらず `--list-backups` で
  legacy 表示のみ・rollback 非対応のまま残した（削除・移行はしていない。要件に無い変更を避けた）
- `ROLLOUT_ROLL_CONFIG` が確定値になったことで `resolveRollConfig('rollout')` は例外を投げなくなった
  （fail-closed ガードは解除された）。W2 の実行可否は今後 `W2_TARGET_HOSTS` との完全一致チェック・
  `--verify-mirror` PASS・人間承認の 3 点で担保する
- **本サイクルでは W2 未実施・Caddy 本番設定変更なし・reload 0 回（Phase 1-B 累計 3 回のまま）・
  pm2 restart 未実施（`.ts` 変更のため案内のみ）・commit/push 未実施・DB 操作なし。**
  `.ts` ファイルを変更し `pnpm build` を実行したため、ユーザーに再起動コマンドを案内する
  （DB マイグレーションは対象外）
