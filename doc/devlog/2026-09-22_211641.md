# DevRelay Sites Phase 1-A — 公開 site 骨格（read-only discovery）

## 背景

前サイクルの調査（プラン `lovely-churning-blum.md`、`submissionId: cmucgddyg06ha1027c2qg51el`）で、
DevRelay が公開する Web サイト（Caddy 配下の testflight 等）の一覧化・監視の仕組み「DevRelay Sites」の
Phase 1 案が作られたが、Caddy access log 導入（reload・全サイトへの影響あり）まで含む一体の Plan だった。
公開環境への影響を最小化するため、人間の指示で **Phase 1-A（read-only 骨格）** と **Phase 1-B（access log
導入 + アクセス解析）** に分割し、別承認・別サイクルとした（修正版 Plan: `floating-wandering-melody.md`）。
本サイクルはそのうち **Phase 1-A のみ** を実装する。Caddy 設定・アクセスログ・DB schema には一切触れない。

## 実装内容

### サーバー（`apps/server/src/services/sites/`, 新規）

| ファイル | 役割 |
|---|---|

`routes/sites-api.ts`（新規）: `GET /api/sites`, `GET /api/sites/:host`, `POST /api/sites/:host/health-check`,
`GET /api/sites/_meta`。すべて `authenticate` + `requireSystemAdmin`（`#367` と同じ流儀）。`index.ts` に
1 行ずつ登録（`app.register(sitesApiRoutes)`, `startSiteHealthChecker()`）。

### 突合ルール

host（Caddy Admin API, 確定）→ LISTEN/uid/cgroup（`ss`, 確定）→ pid/cwd（自ユーザーのみ確定、他は ps args
で推測）→ TestflightService（`domain==host`、確定）→ Machine（`hostname/unixUser` の規約突合、条件付き）→
Project 候補（a. `path==cwd` 確定 > b. `path==TS.directory` 条件付き > c. 同マシンで name/host ラベル部分
一致 推測）→ Git（読める dir のみ）。directory は「登録上（`TestflightService.directory`）/ runtime 推定
（cwd or ps args）/ Project 候補一覧」を分離して持つ（1 つに断定しない設計）。

warnings: `BACKEND_NOT_LISTENING`(error) / `HTTP_5XX`(error) / `HTTP_4XX_ROOT` / `NO_TESTFLIGHT_ROW` /
`NO_PROJECT` / `DIRECTORY_MISMATCH` / `REGISTERED_DIR_IS_SHELL` / `STATUS_STALE` / `NO_ACCESS_LOG`
(info、「Phase 1-B で対応」) / `MACHINE_OFFLINE`。meta に orphans（Caddy host を持たない非 archived
TestflightService 行、DB 行も Caddy host も無い testflight ディレクトリ）。

### WebUI

`apps/web/src/pages/SitesPage.tsx`（新規）: `/sites` ルート、一覧テーブル（host/health/backend port/LISTEN/
Unix user/TestflightService/Project/directory/source/最終 check/警告）+ 詳細ドロワー（Caddy upstream・

`nav.sites`/`sites.*` キーを追加（en/ja）。

## 実機で発見した問題と対応

**Node の組み込み `fetch()`（undici）が Caddy Admin API に対して既定で空の `Origin:` ヘッダを送り、
`{"error":"client is not allowed to access from origin ''"}` として 403 で弾かれる**ことを実機の
スモークテストで発見（`curl`/Node の `http.get` は Origin ヘッダを送らないため通る）。調査時の Explore
エージェントは `curl` で確認していたためこの問題に気づいていなかった。`fetchCaddyInventory()` で明示的に
`headers: { Origin: 'http://127.0.0.1:2019' }` を付与して回避（`caddy-inventory.ts` にコメントで経緯を記載）。
これに気づかずリリースしていた場合、`/api/sites` は常に `caddyAdminReachable: false` で空一覧を返す
状態になっていた。

## 完了条件と残作業

DB マイグレーションなし。`apps/server` 変更のため **pm2 restart 要**。再起動後の E2E（`/api/sites` 実測、
WebUI `/sites` 表示、非管理者 403 確認等）はサーバー再起動後に別途実施が必要（本サイクルでは pm2 restart
を実行していないため、実機での API/WebUI 経由の動作確認は未実施。上記スモークはモジュール単体の直接呼び
出しによるもの）。Phase 1-B（Caddy access log 導入・PV/UU/Referer/UTM 集計）は本サイクルの対象外、
Phase 1-A の有用性を人間が確認した後に別サイクルで着手する。
