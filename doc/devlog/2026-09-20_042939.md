# raw-completion Phase 1.1 — スモークで判明した不具合の是正

2026-09-20 実施。前サイクル（#385調査 → commit `fae5174`「Phase 1: Claude」）で新設した
`POST /api/agent/raw-completion` を実機スモークにかけたところ「レスポンス本文が常に空」と判明。
本サイクルはその根治 + HTTP レスポンス契約の確定 + ツール拒否の可観測性確保 + Phase 0（Codex 調査）。

計画ファイル: `~/.claude/plans/unified-tumbling-ladybug.md`（本ファイル末尾に全文の要旨あり）。

## 真因（コードで確定・仮説ではない）

`agents/{linux,macos}/src/services/ai-runner.ts` の `sendPromptToAiSdk` は、assistant のテキストを
ストリーミングで `onOutput(block.text, false)` として流し、関数ローカルの `fullOutput` に連結する。
完了時のコールバックは常に **本文を渡さない**（出力ありなら `''`、無しなら `'(No response from AI)'`）。
連結は呼び出し元の責務のはずが、`handleRawPrompt`（`connection.ts`）は

```ts
if (!isComplete) return;
finalOutput = output;     // ← 常に '' になる
```

としていたため、出力があると空文字・無いと `'(No response from AI)'` という反転した結果を返していた。
これが空ボディの正体。あわせて ai-runner のエラー分岐（プロンプト長超過・未ログイン・OAuth 期限切れ・
SDK 例外）は `stopReason` 無しでエラー文言を `isComplete=true` で渡して早期 return するため、
旧 `handleRawPrompt` はそれを `stopReason:'success'` の正常応答として握りつぶしていた。

## 設計判断（プランからの意図的な逸脱 — ユーザー承認済み）

### 判断1: 本文の配線方式はチャンク連結ではなく `AiRunResult` 経由

指示は「`isComplete=false` のチャンクを蓄積」だったが、チャンク連結は採らなかった。理由:
- 同じコールバックには本文と区別不能な進捗ノイズ（ツール使用マーカー・auto-compact 通知・
  loop-guard 通知）が流れる可能性があり、4層防御が破れた瞬間にゲームの AI 応答へマーカーが
  混入する構造的な穴になる。連結ロジックを持たないことで構造的にこれを排除した。
- `deniedTools` 要件が既に `AiRunResult` チャネルを強制している（deny クロージャは
  `sendPromptToAiSdk` の内側にあり `onOutput` 経由では絶対に返せない）。

`AiRunResult` に `rawOutput?: string` / `rawDeniedTools?: string[]` を追加（どちらも optional）。
`handleRawPrompt` は `isComplete` の観測（`stopReason`/使用状況の記録）に徹し、本文は一切連結しない。
判定は純関数 `resolveRawCompletionResult()`（`raw-completion-mode.ts`、外部 import ゼロ）に閉じ込め、
3経路を明示的に区別する:

| 経路 | 条件 | 結果 |
|---|---|---|
| A | `rawOutput !== undefined` | 本文 = `rawOutput`。`stopReason` 空なら `success` に正規化。`error` は `ok:false`。`max_turns`/`aborted` は `ok:true` のまま部分出力と stopReason を保持 |
| B | `rawOutput` 無し + 完了シグナルあり | ai-runner のエラー早期 return 分岐。完了テキストは AI 回答ではなくエラー本文 → `ok:false` + `errorMessage`、`text` は空 |
| C | 完了シグナルも無し | `ok:false` + 明示文言（無言の success にしない） |

### 判断2: `mapRawUsage()` は削除（死コード）し、サーバー側に `summarizeRawUsage()` を新設

`mapRawUsage()`（agents 側、本番呼び出し0件・テストのみ）は完全な死コード。ai-runner の
`result.usageData` が既に同じ計算をして届いており raw 用の再マップに価値が無い。加えて
「`{input,output,cacheRead,cacheWrite}` 形式は HTTP レスポンスの表現であって Agent の関心ではない」
という単一責務判断により、agent 側の `mapRawUsage` + 型2つ + テスト4件を削除し、サーバー側
`apps/server/src/services/raw-completion-response.ts` に `summarizeRawUsage()` を新設して実経路
（`raw-completion-api.ts`）から呼ぶ形にした。

### 判断3: `pm2 restart` は自分では実行しない

`CLAUDE.md` の「サービスの再起動は実行しない」規則に加え、自分の WebSocket が切れて本レポート自体が
届かなくなるため。**本サイクルでは (a)〜(e) の再スモークは実施できない。**

  - `AiRunResult` に `rawOutput?: string` / `rawDeniedTools?: string[]` を追加。
  - raw モード分岐（`options.rawMode` ガード内）の `canUseTool` クロージャで deny したツール名を

  - 結果ハンドラ（正常完了）と自然終了フォールバックの両方に
    `if (options.rawMode) result.rawOutput = fullOutput;` を追加（連結済み本文の唯一の正）。
- `agents/{linux,macos}/src/services/raw-completion-mode.ts`: `mapRawUsage()` を削除し

- `agents/{linux,macos}/src/services/connection.ts` の `handleRawPrompt`: チャンク連結を廃止し、
  `isComplete` の観測のみ行う。`sendPromptToAi()` の戻り値（`AiRunResult`）から `rawOutput`/
  `rawDeniedTools` を取り出し `resolveRawCompletionResult()` に渡して結果を組み立てる。
  `agents/windows` は無変更（capability 未申告のため raw-completion に到達しない）。

### 要件2: HTTP レスポンス契約の確定

新規 `apps/server/src/services/raw-completion-response.ts`（外部 import ゼロ、`raw-completion-guard.ts`
と同じ流儀。ガード=「入口の防御」・レスポンス=「出口の整形」で単一責務分離）:

- `summarizeRawUsage(usageData)` → `{input, output, cacheRead, cacheWrite}`。SDK 実キー
  `input_tokens`/`output_tokens`/`cache_read_input_tokens`/`cache_creation_input_tokens` を写像。
  欠落・非数値・NaN・負値は0埋め（キーを落とさない）、小数は切り捨て、例外を投げない。
- `resolveRawModel(usageData, requestedModel)` → `usageData.model` → `modelUsage` 先頭キー →
  リクエスト指定 → `undefined` の優先順。
- `buildRawCompletionResponse(input)` → 新契約ボディを組み立て。`text`/`usage`/`deniedTools`/
  `stopReason`/`sessionId` は必ず存在する（`ok:false` でも同じ形の superset を返す）。

`apps/server/src/routes/raw-completion-api.ts` のレスポンス組み立てを `buildRawCompletionResponse()`
呼び出しに一本化。旧→新のキー対応表:

| 旧（Phase 1） | 新（Phase 1.1） |
|---|---|
| `output`（本文、実際は常に空文字だった） | `text`（正）。`output` は `text` と同値の `@deprecated` 別名として残す |
| （無し） | `model`（`usageData.model` → `modelUsage` 先頭 → リクエスト指定） |
| `usageData`（生の `AiUsageData`、形が不安定） | `usage: {input,output,cacheRead,cacheWrite}`（常に4キー） |
| （無し） | `deniedTools: string[]`（常に配列、重複除去済み） |
| `stopReason`（空のことがあった） | `stopReason`（`ok` に応じ `success`/`error` に正規化、`max_turns`等は保持） |
| （無し） | `error?: string`（`ok:false` 相当、または旧 Agent 検知時のみ） |

`Message.usageData` には従来どおり生の `AiUsageData` を保存（DB に原本を残す）。

### 要件3: `mapRawUsage()` の end state

agents 側から削除（死コード解消）。新テスト `raw-completion-mode.test.mjs` に
「`mapRawUsage` が export されていないことの表明」を追加し死コード復活を防止。
サーバー側 `summarizeRawUsage()`（実経路から呼ばれる）に新テスト21件を追加し
「テストが実経路を検証している」状態にした。

### 要件4: ツール拒否の可観測性

- Agent 側: `rawDeniedTools` を `AiRunResult` 経由でサーバーへ返す。`handleRawPrompt` は非空なら
  `console.warn`。
- サーバー側: `body.deniedTools` が非空なら `console.warn`（machineId/sessionId/seatKey 付き）+
  `role:'system'` の `Message` を作成（`agent.log` が読めない問題の恒久対策としてサーバーログ + DB
  の二重記録）。
- `text` が空で `error` も無い場合、および `error` がある場合も `console.warn` で `pm2 logs` 1行で
  切り分けられるようにした。
