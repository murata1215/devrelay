## Step1: `//connect` に explicitSessionId を配線

**変更ファイル**
- `apps/server/src/services/thread-routing.ts`: 純関数 `resolvePreferredThreadId()` を新規追加
  （`explicitSessionId` > `contextSessionId` > `null` の優先順位、前後空白のみの値は「指定なし」扱い）
- `apps/server/src/services/command-handler.ts`:
  - `handleProjectConnect(projectId, context, explicitSessionId?)` に第3引数を追加（省略可、既存呼び出しは無変更のまま動く）
  - `:501` 付近: `decideConnectTarget({ candidates, explicitSessionId })` に `resolvePreferredThreadId({ explicitSessionId, contextSessionId: context.currentSessionId })` の結果を渡すよう配線
  - `handleRecentConnect()`: `handleProjectConnect(session.projectId, context, sessionId)` として対象スレッドを明示指定（「最近使ったスレッドに戻る」の意図どおりに動くようになる）

**挙動**
- タブが直前に開いていたスレッド（`context.currentSessionId`）があり、かつそのプロジェクトの active スレッド候補に含まれていれば、そのスレッドへ接続する（`//connect` で最新スレッドへ強制的に切り替わらなくなる）
- `context.currentSessionId` が無い（新規タブ）、または候補に含まれない（別プロジェクトのセッション ID 等）場合は、従来どおり最新 active スレッドへフォールバックする（`decideConnectTarget()` の既存挙動、誤配送は発生しない）

## Step2: ツール承認カード payload に sessionId

**変更ファイル**
- 新規 `apps/server/src/services/tool-approval-payload.ts`: 外部 import ゼロの純関数 `buildToolApprovalPromptPayload()`
  （`thread-routing.ts` の `buildSessionInfoPayload` と同じ流儀。optional キーは値が無ければキー自体を省略し、
  `JSON.stringify` が undefined キーを落とす現行のワイヤ挙動と一致させる）
- `apps/server/src/services/agent-manager.ts`:
  - `handleToolApprovalRequest()` の `approvalPayload` 構築をビルダー経由に変更（`sessionId` を追加）
  - `getPendingToolApprovalsForSession()` の戻り値をビルダー経由に変更、戻り型を `ToolApprovalPromptPayloadWithSession[]` に変更

**設計判断（プラン記載どおり）**
- `packages/shared/src/types.ts` の `ToolApprovalPromptPayload` は変更しない（スコープ外）。ローカル拡張型
  `ToolApprovalPromptPayloadWithSession` を定義し、TypeScript の構造的型付け（変数経由の代入は超過プロパティ
  チェックの対象外）により、shared 側の型変更なしに `sessionId` を運べることを確認済み（`pnpm build` green で裏取り）
- `web:tool:approval:resolved` への `sessionId` 追加は見送り（`ServerToWebMessage` のリテラル型付けのため shared 側の型変更が必要になる）
- **表示の穴が実際に塞がるのは次サイクル**: 本サイクルは payload に `sessionId` を供給するところまで。
  `apps/web` 側（`useWebSocket.ts` の `ToolApprovalPrompt`）が `sessionId` を見て同一プロジェクトの
  別スレッドでは表示しないようにするゲート実装は次サイクルへ申し送り（下記参照）

## Step3: `web:user_message` に sessionId

**変更ファイル**
- `apps/server/src/platforms/web.ts:184` 付近: payload に `sessionId`（`context.currentSessionId ?? null`、既にスコープ内の変数）を追加

**挙動**
- `apps/web` は**無変更で即効く**: cycle3 で実装済みの `shouldRouteToTab()`（fail-open ゲート、payload と tab
  の両方に `sessionId` があって不一致のときのみ drop）が既に `useWebSocket.ts` 型定義上 `sessionId?: string` を
  受け入れているため、サーバー側が値を送るようになるだけで正しいタブにのみ配送されるようになる
- `//connect` 応答（`web.ts:134`）には意図的に `sessionId` を付けていない（承認済み方針どおり）:
  接続応答が届く時点でタブ側の `sessionId` はまだ古いままのため、付けると自分の接続応答が drop されてしまうため

## Step5: Lite シェル前提確認（報告のみ、コード変更なし）

`doc/thread-management-spec.md` §0（Lite シェル v2）が要求するデータについて、既存 API で全て満たされていることを実コードで確認した。

| spec §0 の要求 | 対応 API | 確認箇所 |
|---|---|---|
| スレッド一覧（プロジェクト横断、`lastActiveAt desc`、`projectName` バッジ付き） | `GET /api/threads`（`projectId` 省略可） | `apps/server/src/routes/api.ts:1538-1599`。`:1560` で `projectId` 省略時は全プロジェクト横断、`:1572` で `sortThreadsDesc()`、`:1586-1588` で `projectName`/`machineName`/`machineOnline` を返却済み |
| プロジェクト選択（machine / project、オンライン状態） | `GET /api/projects` | `apps/server/src/routes/api.ts:483-536`。`:488` で `deletedAt: null, machine: { userId }` の所有者フィルタ、`:523-528` で `machine.{id,name,displayName,online}` を返却済み |
| 所有者チェック | `evaluateProjectOwnership()` | `apps/server/src/services/thread-api-guard.ts:31-37`（非所有・存在しないプロジェクトはいずれも 404、情報漏洩防止） |
| `machineOnline` の単一情報源 | `getConnectedAgents()` | `apps/server/src/services/agent-manager.ts` の `connectedAgents` Map（WebSocket 接続ベース、DB カラムではない） |

**結論**: 専用の新規 GET は不要。既存 2 本（`GET /api/threads` / `GET /api/projects`）で Lite シェルの
「スレッド一覧」「プロジェクト選択（machine/project + オンライン状態）」の両方を満たせる。
