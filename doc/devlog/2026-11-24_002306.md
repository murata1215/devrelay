# 2026-11-24 00:23 JST ｜ サイクルSB-2.1: Sandbox の許可リスト（IP とポート）— 最小実装

## 要求

`doc/sandbox/SB-2.0_investigation.md` の推奨構成・決定事項（決定0〜8・追加1〜3）に従い、
`config.yaml` の `sandbox.allowDestinations` に `"ip:port"` を書くと次の Sandbox 実行開始時に
ファイアウォールへ反映され、その IP の TCP 許可ポートだけ届くようにする（他ポート・他 IP・
UDP は止まる）。行を消すと次の実行開始時に止まる。

承認時に人間から4点の追加指示があった:
1. ping（ICMPv4）のブロックルールは作らない（SB-1 実機確認で ICMP は OS が代行し身元単位では
   止まらないことが分かっている）。許可した IP 宛に塞ぐのは TCP の許可ポート以外と UDP のみ。
2. `state.json` も一時ファイル＋rename で書く。
3. `apply-allowlist.ps1` は専用フォルダ `allowlist-bin\` に置き、
   `SYSTEM:(F)` `Administrators:(F)` `<開発者>:(RX)` のみにする。
4. 完了時は commit/push・devlog 作成・実機確認手順の報告まで行う。

## 実行

Explore エージェント3体を並列起動し、(a) Agent 側 TypeScript の既存 Sandbox 実装一式
（config.ts の型、sandbox-allowlist.ts の純関数の流儀、sandbox-readiness.ts の判定順序・
拒否理由表、sandbox-preflight.ts の実行前確認の組み立て、ai-runner.ts の単一判定点）、
(b) `install-sandbox-host.ps1` / `uninstall-sandbox-host.ps1` の全体構造・ACL・FW ルール・
鍵生成・SID 解決、(c) 既存テストの書き方（表駆動・静的ガード）と devlog/コミットの流儀を
調査し、調査結果を踏まえて以下を実装した。

設計上の要点（投資資料からの発展）: Windows Firewall は Block が Allow に常に勝つため、
「許可先を通す」には install 時の静的な IPv4 Block ルール自体を狭める必要がある。これを
`install-sandbox-host.ps1` が固定リテラルで持ち続けると、apply スクリプトが後から足す
ルールは一切効かない（Block は OR される）。そこで **IPv4 Block ルールの所有権を
`apply-sandbox-allowlist.ps1` に一本化**し、install 側は内容が変わらない IPv6 Block・
loopback Allow の2本だけを作る設計に変更した。install はこの apply スクリプトを
（別プロセスとして。`&` 呼び出しだと子スクリプトの `exit` が installer まで終了させる
リスクがあるため）インストール完了直前に1回実行し、「未設定時は従来どおり全遮断」という
ブートストラップ世代を即座に作る（タスクが初めて起動するまでの無防備な間を作らない）。

- Agent（純関数、外部 import ゼロ）: `sandbox-allow-destinations.ts`（`/32` IPv4 のみの
  検証・正規化・canonical 文字列、未設定/空は空集合として受理＝ドメイン許可リストとは
  意図的に非対称）、`sandbox-allow-state.ts`（sha256 digest、`state.json` のパース、
  決定3の一致判定）
- Agent（I/O）: `sandbox-allow-apply.ts`（`request.json` を一時ファイル＋rename で書く→
  `schtasks /Run`→最大10秒ポーリングで `state.json` 再読込）、`config.ts` に
  `allowDestinations` フィールドとパスヘルパー2本、`sandbox-readiness.ts` に拒否理由2件
  （`allow_destinations_invalid`/`allow_destinations_not_applied`、判定順序は許可リスト
  妥当性の直後＝パイプ接続より前）、`sandbox-preflight.ts` の `runSandboxPreflightCheck()`
  に配線、`cli/commands/sandbox.ts` の `status`/`selftest` に新しい設定を渡し `status` に
  1節追加
- スクリプト（新規）: `scripts/apply-sandbox-allowlist.ps1`（ASCII のみ・トップレベル
  `param()` なし・IPv4 補集合を uint64 演算で計算し自己検査（全空間一致・許可先/loopback を
  含まない）・digest 付きルール名で新世代を全部作成→旧世代削除（緩む瞬間なし）・
  `state.json` を一時ファイル＋rename で書く・ICMPv4 ルールは作らない）
- スクリプト（改修）: `install-sandbox-host.ps1`（`-DeveloperAccount`/`-DenyDestination`
  引数追加、IPv4 Block ルール削除（apply 側へ移管）、IPv6/loopback の2本に `-Name`/`-Group`
  付与、`allowlist-request`/`-result`/`-deny`/`-bin` の4ディレクトリと ACL 作成
  （いずれもサービス SID には ACE を与えない）、apply スクリプトのコピー、タスク登録
  （`\DevRelay\apply-sandbox-allowlist`、ONSTART・SYSTEM・HIGHEST）、`Schedule.Service`
  COM での開発者アカウントへの実行権付与（try/catch、失敗時は ONSTART のみに縮退する旨を
  警告表示）、apply スクリプトを別プロセスとして1回実行してブートストラップ世代を作成）、
  `uninstall-sandbox-host.ps1`（タスク削除、`\DevRelay` フォルダの best-effort 削除、
  FW ルール削除を Group 併用に拡張）
- `doc/sandbox/SB-2.0_investigation.md` に決定1の訂正（追加4: ping は対象外）と
  追加5・追加6（state.json の atomic write、allowlist-bin フォルダ）を追記

## 発見

- 当初の Plan（SB-2.0 投資資料の記述を踏襲した「install 側は3本のまま、apply 側は別に
  追加するだけ」という想定）では、IPv4 Block ルールが Allow に対して常に勝つため許可先への
  通信が一切通らない構造的な問題があった。実装時に発見し、IPv4 Block ルールの所有権を
  apply スクリプト側へ完全に一本化する設計に変更した（上記「実行」参照）。
- 未検証（Windows 実機が必要）: タスクの非管理者起動権限付与（`Schedule.Service` COM の
  `SetSecurityDescriptor`、リポジトリに前例なし）、`New-NetFirewallRule` の `-RemotePort`
  配列指定の実際の受理、ファイアウォール反映の実効果全般。実機確認手順はチャット応答の
  本文側に記載。
