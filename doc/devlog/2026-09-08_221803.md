# 2026-09-08 22:18 JST ｜ core#377: SDK maxTurns 打ち切りの可視化と上限の設定可能化

## 要求

Claude Agent SDK が `maxTurns` 上限に到達して打ち切られても、DevRelay は「正常完了」として報告してしまう。
調査（submissionId `cmtskrvw4030m8waolltey4ha`）で以下を確認済み:

- `agents/linux/src/services/ai-runner.ts:941` で `maxTurns: 200` 固定。plan / exec 共通、env 上書き無し
- 同 `:1372` の result ハンドラが `m.subtype` を一切見ず、`error_max_turns` でも `isComplete=true` を送信
- `apps/server/src/services/agent-manager.ts:683` が無条件に BuildLog を作成し、
  `apps/server/src/mcp/tools.ts:365-381` が BuildLog の存在だけで `done: true` を返す
- 実測: 途中終了した2件は 228 / 209 ツール呼び出し（28.4 / 28.2 分）、正常完了2件は 84 / 28

本サイクルで打ち切りを `stopReason` として最後まで伝播させ、上限を env で調整可能にする。

## 事前調査で確定した根拠

### SDK result subtype（`@anthropic-ai/claude-agent-sdk@0.2.77` の sdk.d.ts:2120-2155）

```ts
export declare type SDKResultError = {
    type: 'result';
    subtype: 'error_during_execution' | 'error_max_turns' | 'error_max_budget_usd' | 'error_max_structured_output_retries';
    is_error: boolean;
    num_turns: number;
    ...
};
export declare type SDKResultMessage = SDKResultSuccess | SDKResultError;
// SDKResultSuccess: subtype: 'success'; is_error: boolean; num_turns: number; ...
```

**重要な発見（除外した2仮説）**:

1. 当初「`is_error` は失敗時のみ true」と想定していたが、実際は `SDKResultError` 型に `is_error: boolean`
   （bool型であり必ず true ではない）が定義されており、`error_max_turns` でも `is_error: true` になり得る。
   このため `ai-runner.ts:1410` の `if (m.is_error && options.resumeSessionId) { result.resumeFailed = true; }`
   が `error_max_turns` を「resume 失敗」と誤判定し、`:1418-1422` で `onOutput` を呼ばずに `return` していた
   （＝ exec 経路では打ち切り報告が構造的に発火しない）。**この仮説は実装レビューで実測コードにより確定**
   （当初「単に result ハンドラが subtype を見ていないだけ」という仮説を立てていたが、それだけでは説明できない
   `resumeFailed → composeFullPrompt(true) 再実行` という二次被害があることが判明し、修正範囲を拡大した）。
2. 「maxTurns 到達時は SDK が例外を投げてcatchブロックに落ちる」という仮説も検討したが、
   sdk.d.ts の型定義上 `error_max_turns` は正常な `result` メッセージの subtype として返る
   （例外ではない）ため棄却。result ハンドラ内で完結して処理する設計とした。

実測 228 / 209 ツール呼び出しの内訳は、上記の「maxTurns 到達 → resumeFailed 誤判定 → プロンプト全体再実行 →
再度 maxTurns 到達」という多重打ち切りを含む可能性が高い（本サイクルでは打ち切り自体の可視化が目的のため、
過去2件の内訳の遡及検証は行わない）。

### AiOutputPayload 現状（`packages/shared/src/types.ts:216-240`）

`machineId` / `sessionId` / `output` / `isComplete` / `files?` / `usageData?` / `isExec?` / `execPrompt?` /
`aiSessionId?` / `aiTool?` / `turnId?`（末尾3つは core#376 で追加）

### BuildLog カラム（`apps/server/prisma/schema.prisma`）

`id` / `buildNumber` / `projectName` / `projectId` / `machineId` / `sessionId` / `userId` / `summary` / `prompt?` / `createdAt`。
打ち切り理由を表現できる既存カラムが無いため `stopReason String?` を追加する（ALTER は `doc/migrations/377_*.md` に記載、
本サイクルでは未実行）。

### agents/macos との対比

`maxTurns: 200` は `agents/macos/src/services/ai-runner.ts:853`、result ハンドラの該当箇所は `:1313`/`:1340`
（linux `:1410`/`:1437` から59行ずれた同一構造）。`ai-runner.ts` 全体は端末モード等で約800行差があり
byte-for-byte 対象ではない。新規追加する `sdk-stop-reason.ts` とそのテストのみ byte-for-byte 同一にする
（`sdk-loop-guard.ts` / `running-code-stale.ts` と同じ流儀）。Windows agent は `maxTurns` を持たない CLI spawn
経路のためスコープ外（`stopReason` 未送信 → サーバー側で 'success' 扱い）。

### 稼働 agent の env 経路

稼働 agent は `~/.devrelay/agent/agents/linux/dist/index.js` を crontab `@reboot` + nohup で起動（pm2 管理外）。
`.env`/dotenv/`config.yaml` に env セクションは無く、env を渡す唯一の経路は crontab 行の `export`。
`sdk-loop-guard.ts:97-128` の `parseEnvInt()` + `resolveLoopGuardConfig()` の流儀（未設定/空文字/非数値/範囲外は
例外を投げず既定値へフォールバック）に合わせる。

## 発見

- 「resumeFailed 誤判定 → composeFullPrompt(true) 全プロンプト再実行」という既存の隠れた挙動が、
  調査時点で実測した打ち切り2件の 228 / 209 ツール呼び出しの主因である可能性が高いことが、
  実装前レビュー（sdk.d.ts の `is_error` 型定義の再確認）で判明した。本サイクルの唯一「挙動が変わる」修正は
  この誤判定の解消であり、`stopReason` の可視化そのものより実害是正としての価値が大きい
- `error_max_budget_usd` は本サイクルでは resume 失敗経路の除外対象にしていない（`max_turns` のみ除外）。
  予算上限到達時も同様の多重実行が起き得るため次サイクル候補として rules/project.md に明記した
- plan ターンは BuildLog を作らないため `get_plan` は打ち切られたプランを判別できない
  （`Message`/`Session` 側に stopReason 相当の列が必要＝別サイクル）
- Windows agent は `maxTurns` オプションを持たない CLI spawn 経路（`--max-turns` 等の概念が異なる）のため、
  本サイクルは意図的にスコープ外とした。`stopReason` は常に未送信でサーバー側 `normalizeStopReason()` が
  `'success'` にフォールバックするため、既存挙動（正常完了として表示）が維持される（後退なし）
