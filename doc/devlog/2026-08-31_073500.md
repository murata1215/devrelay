# 2026-08-31 #338: Claude OAuth トークン期限切れの生JSON表示バグ修正（#326 Phase1 の穴埋め）

## 要求
ユーザーから「トークン切れ対応って前依頼したけど実装やり切ったか覚えがない。いま pixblog で
トークン切れが起きている。どこまで対応したかを確認したい」とスクリーンショット付きで依頼。
スクリーンショットには `Failed to authenticate. API Error: 401
{"type":"error","error":{"type":"authentication_error","message":"OAuth access token has
expired. Re-authenticate to continue."},"request_id":null}` という生の JSON エラーがそのまま
チャットバブルに表示されている様子が写っていた。過去に「PTY でログイン切れ検出できるか」
「SDK でもっといい方法がある」という設計会話をした記憶があるとのこと。

## 調査
Explore エージェント（very thorough）で #326（2026-08-28）の実装状況を全項目棚卸し。
Phase1（15分ポーリング検知・DB永続化・WebUIバッジ・チャット通知・実行時エラー言い換え）は
commit `03c2c4c` で実装・push 済みで作業ツリーもクリーンと確認。Phase2（SDK control protocol
`Query.request({subtype:'claude_authenticate'})` によるリモート再ログイン中継本体）は全文検索で
コード上0件、未着手と確認（バックグラウンドタスクでの独立した全文検索でも同じ結論を再確認）。

DB を直接クエリしたところ `x220-158-18-103/pixblog`（ubuntu-prod/pixblog）の `claudeAuthOk` は
`true` のまま、報告時刻の約8.5時間前（同一ホストの全 Agent が再接続したタイミング、おそらく前回の
サーバー再起動由来）から更新が止まっていた。

コードを読み込み、根本原因を2点特定:
1. `checkClaudeAuth()`（15分ポーリング）が使う `claude auth status --json` はローカル資格情報の
   有無（`loggedIn`）しか見ておらず、資格情報自体は存在するがトークンがサーバー側で失効している
   ケース（今回の実際のケース）を検知できない構造的な限界がある。
2. `sendPromptToAiSdk()` の実行時エラー言い換え `formatAiErrorMessage()` は catch ブロック
   （JS例外）にしか配線されておらず、Claude Agent SDK はこの種の認証エラーを例外としてではなく
   通常の assistant テキストブロックとしてメッセージストリームに流すため、素通りして生の JSON
   エラーがそのまま `onOutput()` されていた（「Prompt is too long」「not logged in」の2パターンしか
   テキストブロック側に検出ロジックが無かった）。

DB上でこのプロジェクト（`terminalMode=false`）が SDK 経路（PTY 経由ではない）であることも確認し、
今回の実害がこの経路のバグで説明できることを裏付けた。

## 実行
`agents/linux/src/services/ai-runner.ts` と `agents/macos/src/services/ai-runner.ts` に
`isClaudeAuthExpiredMessage()` を切り出し、既存 `formatAiErrorMessage()` と assistant テキスト
ブロックのハンドラ（新設分岐）の両方から参照する単一情報源にした。テキストブロックで検出時は
`tChat(lang, 'claudeAuth.runtimeExpiredHint')`（#326 で追加済みだが未使用のまま残っていた
i18n キー）を出力し、生エラーの代わりに実行可能なヒントを見せる。

`agents/linux/src/services/connection.ts` と `agents/macos/src/services/connection.ts` に
`reportClaudeAuthExpiredFromRuntime()` を新設 export。実行時に実際の401を検知した瞬間、15分
ポーリングを待たず即座に `agent:claude:auth:status`（`ok:false`）をサーバーへ送る。
`checkAndReportClaudeAuth()` と同じ `lastReportedClaudeAuthOk` ガードを共有するため二重送信は
起きない。`ai-runner.ts` は既に `getServerSkipPermissions()` を `connection.ts` から import する
前例があったため、同じ向きの import として追加（新規の循環 import パターンではない）。

サーバー側（`agent-manager.ts`/DB スキーマ/WebUI バッジ/`notifySessionsForMachine()`）は #326 で
実装済みのロジックをそのまま利用でき無変更。15分ポーリング自体も別の失敗モード（完全ログアウト）
の検知に引き続き有効なため変更していない。

## 発見・スコープ外事項
- Windows（Electron GUI）は #326 時点で `claude-auth.ts` 自体が存在せず、今回も対象外のまま。
- `terminalMode`（PTY 経由）は raw ストリームのため同様の正規表現検知が困難で対象外
  （今回の実害のプロジェクトは `terminalMode=false` と確認済みのため無関係）。
- Phase2（リモート再ログイン中継本体）は依然未着手。今回は Phase1 の検知漏れの穴埋めのみ。
- `checkClaudeAuth()` 自体をより正確な生存確認に置き換える改修（CLI 側にトークン有効性を
  検証するオプションが無いため困難）は見送り、実行時検知で補う設計を採用。
- **各マシン（Linux/macOS）の `u` が必要**（commit/push 前提、Windows 対象外）。サーバー再起動は
  不要（Agent のみの変更）。実チャットでの実機確認（次回 OAuth 期限切れ発生時のヒント表示・
  WebUI バッジ即時反映）は `u` 反映後、実際にトークンが切れるタイミングでのみ検証可能なため
  本サイクルでは未実施。
