# Lite シェル L5: 承認カードの応答（web のみ）

日時: 2026-09-12 09:29 (JST)
プラン: `~/.claude/plans/prancy-jumping-kite.md`
スコープ: `apps/web` のみ（6 ファイル）。`apps/server` / `agents/*` / `packages/*` / `prisma/*` /
`ChatPage.tsx` / `useWebSocket.ts` / `tsconfig.test.json` は無変更（`git diff --stat` で確認済み）。

## 発端

`/lite` シェルは L4.1 までにスレッド選択・履歴表示・送信・新規スレッド作成ができるようになったが、
**ツール承認カードは表示専用**だった（`LiteApprovalCard.tsx` は 2 つのボタンを常に `disabled` で
描画し、本文は「classic UI から応答してください」と案内）。Lite だけを開いているユーザーはエージェント
を先へ進められず classic に戻る必要があった。加えて `approvalPrompt` が単数 state のため、承認要求が
同時に 2 件来ると 1 件目が消える問題もあった。

本サイクルで `web:tool:approval` に対する承認/拒否を Lite から返せるようにした。AskUserQuestion
（`isQuestion: true`）は L5.1、markdown 描画は L5.2 に分離しスコープ外のまま。

## 事前調査で確定した事実（実装前に実ファイルを確認）

- `useWebSocket` は既に `sendToolApprovalResponse(requestId, behavior, approveAll?, alwaysAllow?, answers?)`
  を返しており、フックは無変更で分割代入するだけで良い。
- `sendToolApprovalResponse` は **WS が OPEN でないと無言で `return` する**（戻り値なし。呼び出し側は
  失敗を検知できない）。
- サーバーは応答受理時（および 5 分タイムアウト時も）`web:tool:approval:resolved` をセッション参加者の
  全 web クライアントへ broadcast する。`LitePage` は既に `handleToolApprovalResolved` を持っており
  requestId 一致でカードを消す経路は実装済みだった（Map 化に合わせて `forgetApproval()` へ統合）。
- サーバーは WS 接続のたびに保留中の `web:tool:approval` を再送する（`platforms/web.ts`）。
- ガードテスト（`lite-source-guards.test.mjs:91-96`）が `LiteApprovalCard.tsx` は
  `hooks/useWebSocket` から `ToolApprovalPrompt` 型を import していることを要求しており、`prompt` の
  型を変更すると既存テストが壊れる。
- `tsconfig.app.json` は `noUnusedLocals`/`noUnusedParameters` を有効化しているため、未使用の
  分割代入はビルド失敗になる。

## 設計判断

### D1. 純モジュールは新規ファイルを作らず `lite-shell-rules.ts` に §16 を追記した

fail-closed の `shouldShowApprovalCard()`（§5）を複製せず再利用するため。新規ファイル（外部 import
ゼロ制約）だとセキュリティ述語を複製することになり、この repo で最もやってはいけない複製になる。
また `tsconfig.test.json` の include 追加・新規ガードファイルの配線が丸ごと不要になる。

### D2. 2000ms タイマーは採用しない

classic (`ChatPage.tsx`) の 2 秒 `setTimeout` は移植していない。happy path では `resolved` が
数ミリ秒で届き、2 秒タイマーは常に死にコードになる。逆にタイマーでカードを消すと、無言失敗
（サーバー未受理）と組み合わさって「送信できていないのにカードが消える → エージェントが 5 分
ハングする」という最悪の見え方になる。要件の「応答後にカードを閉じる」は `resolved` 受信
（実測ミリ秒）で満たし、無限に残る心配はサーバー側 5 分タイムアウトが保証する。

### D3. `connected` を応答可否の判定に含める（無言失敗の穴埋め）

`decideApprovalRespond()` に `connected` を渡し、切断中は `blocked: 'disconnected'` を返して
カードを pending のまま残す。`connectedRef` をレンダーごとに更新し WS コールバックから同期的に
読めるようにした。

### D4. 二重送信防止は ref（`entry.status` では足りない）

`markApprovalResponded` は `setState` なので、同一 tick の 2 回目クリックはレンダー時クロージャの
古い `status: 'pending'` を読んでしまう。`LitePage.tsx` に既にある `sendingRef`/`creatingThreadRef`
と同じ流儀で `respondedRef: useRef<Set<string>>` を使った。`entry.status` は表示専用の情報源に
とどめている。

### D5. サーバー再送は常に `pending` へ巻き戻す

「既存かつ非 pending なら無視」にすると次のデッドロックが起きる: (1) Lite が楽観的に `allow` に
する → 無言失敗でフレームが落ちる → (2) サーバーは未受理のまま再接続時に同じ requestId を再送 →
(3) 無視すると Lite からは二度と応答できずエージェントが 5 分ハングする。サーバーが再送する＝まだ
pending が権威、という判断で `upsertApproval()` は常に `status: 'pending'` で入れ直し、
`handleToolApproval` は同じハンドラ内で `respondedRef` からも削除する。`Map.set` は既存キーの挿入
位置を保つためカードの並びは動かない。

### D6. `LiteApprovalCard` は完全な受動コンポーネント（内部 state を持たない）

「クリック後 disabled」を内部 `useState` で持つと、D5 の巻き戻しが起きたとき（コンポーネントは
`key=requestId` で mount されたまま）内部 state を外から戻す手段がなく永久に disabled になる。
`status?: LiteApprovalStatus` prop で表現し、`LitePage` を唯一の真実とした。`prompt` の型は
`ToolApprovalPrompt` のまま変更していない（既存ガードテストの制約）。

### D7（要件 5 に対する追加対応。ユーザー承認を得て実施）

当初プランの既定は「sessionId ゲートは新設しない」だったが、レビューで「到着時ゲートしか効かず、
スレッド A を見ている間に届いたカードが B へ切り替えた後も残り続け、ボタンが生きると『見ていない
スレッドのツール実行を承認できる』穴になる」ことを申し送りとして明記していた。ユーザーの実行承認
メッセージで明示的に「**既存の `shouldShowApprovalCard()` をレンダー時にも適用して塞ぐこと。
新しいゲートは作らない**」という指示を受け、`selectVisibleApprovals()` を新設して対応した。この
関数は内部で既存の `shouldShowApprovalCard()` を呼ぶだけで、新しい判定ロジックは一切追加していない
（述語の適用箇所を到着時 1 箇所 → 到着時+描画時の 2 箇所に増やしただけ）。

### i18n

ボタン文言は既存の `lite.approvePlaceholder`/`lite.denyPlaceholder` をそのまま使う。本文用に
`lite.approvalRespondBody`/`lite.approvalResponded` の 2 キーだけ追加した。
