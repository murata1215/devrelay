# #345: Devin CLI が workspace trust で拒否される問題を解消 + `{tool}` 未置換 + `--agent-config` 誤判定の診断強化

## 要求
#344 を commit + push し当該 Windows CLI 機（`DESKTOP-1E6SDOQ/MURATA_K`）で `u` を実行したところ、
無内容な `(No response from AI)` は解消され devin 自身の実エラーが exit code + stderr 付きで表示される
ようになった。しかし実チャットで「まだだめみたい」と再報告があり、以下3件が判明した：

- ❶ `⚠️ この端末の Devin CLI は --agent-config に対応していないため...` という誤警告が依然として出る
- ❷ `❌ {tool} CLI が出力なしで終了しました（exit 1）。` の `{tool}` がプレースホルダのまま表示される
- ❸（本丸）stderr に `devin: error=Refusing to run in an untrusted workspace: d:\iap\eBuilder8\workspace\Lafit`
  が出て、Devin CLI が一切動かない

プラン `/home/devrelay/.claude/plans/vivid-waddling-boole.md` §39-45（新規サイクル #345）を exec モードで
実装した。

## 実行
read-only の実測（DB とソースのみ、推測ゼロ）から着手した。`probeDevinCapabilities()` の実際の戻り値を
DB のログ相当情報とコードパスから辿り、`ok:true`（probe 自体は成功）かつ `promptFile:true`・
`agentConfig:false` であることを確認。これはユーザーが手打ちした実機 `devin --help`（3000.1.27）とは
矛盾する結果であり、①正規表現のバグ、②自動リトライの未発火、のどちらでもないと切り分けた。残る可能性は
Agent プロセスが解決する `devin` 実体がユーザーの対話シェルとは別（H-A）か、devin config の差（H-B）の
どちらかだが、今のログでは判別できない。**推測で直すと外す**と判断し、❶は「次の1回のチャットで確定させる
観測性」の追加に留めた。

❸ については devin 3000.1.27 の `--help` に `--respect-workspace-trust [<RESPECT_WORKSPACE_TRUST>]`
（既定: 対話モード true、非対話/print モード false）という説明があることを確認。DevRelay は常に `-p`
で起動しているにもかかわらず拒否されており、拒否メッセージ自身が「config で
`respect_workspace_trust: false` を設定してください」と案内していることから、ユーザー側の devin config
が CLI の既定より優先されていると判断した。DevRelay はリモート実行のため対話の trust プロンプトを人間が
押せず構造的に詰んでいる。よって CLI 引数で devin 自身の print モード既定を明示的に指定する対応を選択
（権限拡大ではなく devin 自身の既定への回帰）。

実装は3 OS（`agents/linux`, `agents/macos`, `agents/windows`）+ `packages/shared` にまたがった：

1. `packages/shared/src/i18n.ts`: `tChat()` に `warnIfUnresolvedPlaceholder()` を追加（console.warn の
   みで戻り値は変更しない）。`devin.workspaceUntrusted`（新規、対処手順3点）と `devin.readonlyUnsupported`
   / `devin.execPermissionUnsupported` / `devin.probeFailed` への `{detail}` 追加。
2. `agents/{linux,macos,windows}/src/services/cli-failure.ts`: `isWorkspaceTrustError(stderr)` を
   `classifyCliFailure()` の**下に追加するのみ**（既存関数は1バイトも変更しない）。
3. `agents/{linux,macos,windows}/src/services/ai-runner.ts`: `ai.cliFailed` への `tool: aiTool` 追加、
   `probeDevinCapabilities()` に `respectWorkspaceTrust`/`version`/`helpBytes`/`ok`/`reason` を追加、
   `--respect-workspace-trust false` の条件付き付与、catch-all の `emptyNonZero` 分岐内での
   `isWorkspaceTrustError()` 判定と `devin.workspaceUntrusted` 表示、劣化通知3キーへの `{detail}` 付与。
4. テスト: `packages/shared/tests/i18n.test.mjs`（新規、4ケース）、
   `agents/{linux,macos}/tests/cli-failure.test.mjs`（拡張、workspace trust 4ケース追加、byte-identical
   維持）。

## 発見
- `probeDevinCapabilities()` の `ok:true` かつ `agentConfig:false` という組み合わせは、正規表現の実装
  ミスやリトライロジックの欠陥では説明できず、環境差（Agent プロセスが解決する devin 実体そのものが
  ユーザーの対話シェルと異なる可能性）を強く示唆する。これは #344 での「catch ブロックへの帰着」という
  診断とは異なる、より特定困難な部類のバグであり、今回は「直す」のではなく「次の1回で確定させる」ための
  診断行を追加するに留めた判断が妥当だったと考える。
- `--respect-workspace-trust false` の付与は `devinDroppedFlags`（#329 の自動リトライ安全網）に自動的に
  乗るため、当該フラグ自体を拒否する未知の旧 devin バージョンに対しても追加のコード変更なしに安全に
  動作する。安全網の設計が既に汎用的だったため、新しいフラグを追加するだけで済んだ。
- `{tool}` プレースホルダ欠落は #86→#90、#293→#304 に続き3回目の同クラスバグであり、今回初めて
  「個別修正」ではなく「仕組みでの検出」（`tChat()` の未置換プレースホルダ warn）を導入した。
