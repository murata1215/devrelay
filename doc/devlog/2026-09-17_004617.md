## 背景

P3-B で `agent-skills:standard` adapter が実機（DESKTOP-1E6SDOQ）E2E 合格したが、運用上の粗が 4 点残っていた:
空の `.devrelay-staging` が配布先に残置、skill を持たないプラグインが web で通常 present と区別不能、
診断文字列の接頭辞重複、役目を終えた `providers.devin` 型。調査中に **skill の update 経路が構造的に必ず
失敗する未発見バグ**（T1b）を発見したため、同一コード領域（staging/trash ライフサイクル）として同時に修正した。

## 実施内容

### T1: 同期後の空 `.devrelay-staging`/`.devrelay-trash` を削除
`skill-tree-io.ts` に `removeDirIfEmpty(dir)`（`readdir` 0 件のときだけ非再帰 `rmdir`、それ以外は fail-soft）と
`removeResidueDirsIfEmpty(skillsDir)` を追加。`agent-skills-adapter.ts` の `AgentSkillsDeps` に
`cleanupEmptyResidue` を追加し、`reconcileMachineWithDeps()` の cleanup-only 経路・通常経路の両 return 直前で呼ぶ。

### T1b（バグ修正）: `.devrelay-trash` 親ディレクトリ未作成による update の必発失敗
`installOrUpdateSkill()` は `trashDir = join(skillsDir, '.devrelay-trash', '<name>-<suffix>')` を渡すが、
**`.devrelay-trash` 親を作るコードがリポジトリ内に 1 箇所も無かった**（grep 全数確認）。`atomicSwapDir()` は
destDir 既存時（＝ update）に `rename(destDir, trashDir)` を行うため、**update 経路は必ず ENOENT で失敗していた**
（新規 install は trash を使わないため成功し、実機 E2E をすり抜けていた）。

修正: `atomicSwapDir()` の `destExisted===true` 分岐で rename 直前に `mkdir(dirname(trashDir), {recursive:true})`
を追加。dest 不在時（新規 install）は trash を触らないため mkdir もしない（空ディレクトリを作らない）。

**承認事項2の検証（(a)(b)(c)）**:
- (a) `skill-tree-io.test.mjs` に「trash の親 dir が存在しない状態で `atomicSwapDir` が成功する」回帰テストを追加。
  修正前コード（`mkdir` 行をコメントアウトした状態）でこのテストを実行すると `ENOENT: no such file or directory,
  rename '<staging>' -> '<trash>/...'` で失敗することを確認済み。
- (b) `agent-skills-adapter.test.mjs` に実 `fs/promises`（`skill-tree-io.ts` の実装をそのまま deps 注入する
  ハイブリッド構成。git/spawn 系だけを fake にし、copyTree/atomicSwap/removeManagedDir 等は実ファイル操作を使う）
  で「install → marketplace 側の skill 内容を書き換え → 2 回目 reconcile で `updated: 1`、同期後に
  `.devrelay-staging`/`.devrelay-trash` が残らない」を end-to-end 検証するテストを新設。既存の全テストは仮想
  ファイルシステム（Map/Set）で `copyTree`/`atomicSwap` をシミュレートしており実 `rename` を経由しないため
  T1b を検出できない、という構造的な穴をこのテストで埋めた。
- (c) `.devrelay-trash` へ rename する経路は `atomicSwapDir()`（`skill-tree-io.ts`）の 1 箇所のみ（grep 全数確認）。
  呼び出し元も `installOrUpdateSkill()`（`agent-skills-adapter.ts`）の 1 箇所のみ。他の `rename()` 呼び出し
  （`atomic-write.ts`／`approval-logger.ts`／`work-state-store.ts`／`git-guard.ts`）は skill trash と無関係の
  用途（設定ファイルのアトミック書き込み等）で、legacy 移行（`removeManagedDir()`）も trash を経由しない
  （legacy dir は読み取り＋削除専用、staging を作らない）ため対象外。

## 実機 E2E で update 経路を踏ませる手順（追加調査事項の回答）

**結論: 索引リポを変更せず DESKTOP 上の marker を書き換える方法は成立する。**

対象ファイル: 配布先スキル直下の `.devrelay-capability.json`（例 Windows:
`%USERPROFILE%\.agents\skills\<skillName>\.devrelay-capability.json`）。

書き換えが必要なキーは**2つとも**:
1. `sourceCommit`（または相当のコミット参照フィールド）を現在の索引 HEAD と異なる値に変更
   — `decideSkillActionFast()` の fast-path が indexCommit と marker のコミット一致で即 `'present'`
   に短絡するのを回避するため。
2. `contentHash` を実際の計算値と異なる値に変更
   — `decideSkillActionSlow()` が version 一致・contentHash 不一致の場合のみ `'update'` を返し、
   両方一致（またはバージョンのみ差異）だと `'refresh-marker'`（marker 更新のみで実ファイルは差し替えない）
   になるため。片方だけの書き換えでは `'present'` または `'refresh-marker'` に落ち、`installOrUpdateSkill()`
   （＝ T1b の修正対象コードパス）を通らない。

期待結果: Sync now 実行後、その skill が `updated: 1` として報告される。**T1b 修正前のコードでこの手順を
踏むと**、`decideSkillActionSlow()` が `'update'` を返した時点で `installOrUpdateSkill()` → `atomicSwapDir()`
に到達し、dest 既存（trash 経路）で ENOENT により `failed` に `swap-failed` 相当の reason が入る
（＝ 自動テストで再現した障害と同一コードパス）。
