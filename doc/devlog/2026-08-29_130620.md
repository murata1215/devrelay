# #331: MCP に `approve_implementation.note?` / `submit_instruction.council?` の受け口を追加

**要求**: 外部オーケストレーター（devrelay-manager）が既に送っている `approve_implementation` の `note?: string` と `submit_instruction` の `council?: boolean` が、core MCP のスキーマに定義が無いため zod に黙って strip されていた（実機 `tools/list` で確認済みとの報告）。受け口を追加し、`note` は実効化、`council` は受理・永続化まで行う（council 実行エンジンは別サイクル）。

**実行**: `note` は `apps/server/src/mcp/approval-prompt.ts`（外部 import ゼロの純粋関数 `buildApprovalExecPrompt`）を新設し、`approve_implementation` の exec プロンプト（`execConversation` の第5引数）に注入。`get_build_status` が exec 開始時刻のアンカーとして完全一致で参照する `Message.content === 'exec'` は一切変更せず、note は別途 `Session.approvalNote`（新規列）に監査目的で永続化。`council` は `submit_instruction` で `council === true` のときのみ `Session.councilMode`（新規列、既定 false）を更新する形にし、未指定時は更新自体を行わないことで「従来と完全同形」をコード構造で担保。返却 JSON は council 未指定時にキー自体を省略し、指定時のみ `status: 'accepted_not_implemented'` を明示（#325「静かなフォールバック禁止」)。DB 列は `prisma migrate dev` を使わず `psql` で直接 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` を適用し `npx prisma generate` で Client を再生成。

**検証**: `pnpm build` green（6 workspace 全て）。`node --test tests/`（新規 `apps/server/tests/approval-prompt.test.mjs`、Node 組み込み `node:test`、コンパイル済み dist を直接 import）で4ケース green（note 未指定/空白のみ→既定文と完全一致、note 指定→見出し付き追記、複数行 Markdown の改行保持）。`grep -c 'require(' apps/web/dist/assets/index-*.js` = 0。`content: 'exec'` の完全一致箇所（get_build_status の検索条件・approve_implementation の Message 書き込み）が編集前後で計2箇所のまま byte-for-byte 不変であることを git diff で確認。DB 列 `councilMode`/`approvalNote` の実在を `information_schema.columns` で確認（2行）。サーバー再起動・pm2 restart・プロセスkillは一切行っていない（自己改変サイクルの厳守事項）。

**発見**: council 機構自体は core に一切存在しない（`find -iname "*council*"` = 0件、実確認済み）。`rules/project.md`/changelog の「Council v1 の土台」は `ask --ai`（#325）のことで、批評ループ・収束判定・council-run.sh は未実装。今回はスキーマ受理とDB永続化までがスコープであり、council エンジン本体（claude=提案・修正、codex=批評、blocker/major ゼロで収束）は別サイクルで実装する必要がある。
