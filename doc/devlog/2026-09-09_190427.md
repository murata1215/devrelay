# 2026-09-09 19:04 JST ｜ サイクル: get_build_status summary「不明」+ 承認直後の誤報解消

## 要求
MCP `get_build_status` の `summary` が「不明」で返る事象（2026-09-09 に4回発生・再現性あり）と、
`approve_implementation` 直後の `get_build_status` が一時的に「承認が受理されていない」旨を返す
事象について read-only 調査を実施し、真因を確定してから修正する。プランファイル:
`quiet-sniffing-wirth.md`（`/home/devrelay/.claude/plans/`）。スコープは `apps/server` + `doc` のみ、
`agents/` 配下は触らない。

## 調査で確定した真因（実装前に判明）
- 「不明」は `build-summarizer.ts` の要約用システムプロンプトの指示どおりの AI の回答。
  `buildUserMessage()` が要約対象出力を**先頭 8000 文字**で切るため、進捗マーカー
  （`🔧 Editを使用中...` 等）で埋まった長いターンでは実装完了報告（末尾にある）が
  丸ごと切り捨てられ、AI が「不明確」と判断して文字通り「不明」を返す。DB 実値は
  null ではなく文字列 `"不明"`（サーバーログ `📋 BuildLog summary (openai): 不明` で確認、
  2026-09-09 分だけで #849/#57/#1/#2/#3 の5件）。
- "No approval received" という文字列は DevRelay コードベースに一切存在しない。
  `get_build_status` は `Session.approvedAt` を参照する設計になっておらず、未承認と
  承認直後（exec 開始直後）が同じ `phase:'queued'` 応答に潰れるため、呼び出し側モデルが
  誤って言い換えていると推定。同根ではなく別件。
- 副次発見: `approve_implementation` の exec 起動失敗時ロールバック（`tools.ts:821-830`）が
  `approvedAt` は null に戻すが、先に作成した `exec` Message を消していないため、
  失敗した submission が永久に「実行中」を返し続けるバグ。

## 実行

プラン（Fix A + Fix B）どおりに `apps/server` のみを変更。`agents/` は 1 行も触っていない。

### Fix A（「不明」の根治）
- **新規** `apps/server/src/services/progress-markers.ts`: `agents/linux/src/services/history-compaction.ts`
  の `PROGRESS_LINE_PATTERNS` / `isProgressMarkerLine()` / `stripProgressMarkers()` を外部 import ゼロで
  バイト単位コピー（server から agents は import できないため）。
- `apps/server/src/services/build-summarizer.ts`:
  - `buildUserMessage()` を「先頭 8000 文字」head 切りから「`stripProgressMarkers()` で進捗マーカー除去 →
    それでも 8000 文字超なら先頭 2000 文字（`OUTPUT_HEAD_LENGTH`）＋末尾 6000 文字（`OUTPUT_TAIL_LENGTH`）を
    `truncateOnLineBoundary()` で行境界安全に切り出し `[...omitted...]` で連結」に変更。完了報告は末尾に
    あることが多いため、これで構造的に失われなくなる。
  - `normalizeSummary()` に「不明」検疫を追加（`UNKNOWN_SUMMARY_VALUES = {'不明','「不明」','unknown'}`、
    trim 後・大小無視の完全一致のみ対象。「要件が不明瞭なため…」のような実質的な要約文は誤検疫しない）。
    検疫時は null を返し、`updateBuildLogSummaryAsync()` の `if (aiSummary)` ガードにより
    フォールバック要約を上書きしない。
  - テスト可能にするため `buildUserMessage` / `normalizeSummary` / `MAX_OUTPUT_LENGTH` /
    `OUTPUT_HEAD_LENGTH` / `OUTPUT_TAIL_LENGTH` / `MAX_SUMMARY_LENGTH` を export。
- `apps/server/src/services/agent-manager.ts` の `extractBuildSummary()`: `stripProgressMarkers()` を通し、
  先頭 200 文字ではなく `truncateOnLineBoundary(cleaned, 200, 'tail')` で**末尾** 200 文字を取るよう変更
  （意図的な挙動変更。AI 要約プロバイダー未設定ユーザーのフォールバックが「探索の書き出し」ではなく
  「完了報告の末尾」になる）。切り詰め時は先頭に `...` を付与。

承認時の指定どおり、「不明」検疫時のフォールバック順は
「（AI 要約なし or 検疫）→ `extractBuildSummary()` の末尾抜粋 → それも空なら `'Build completed'`」
（`get_build_status` の `buildLog.summary || 'Build completed'` で既に担保されている）。

### Fix B（承認状態の可視化 + rollback の穴埋め）
- `apps/server/src/mcp/tools.ts` の `get_build_status`:
  - 冒頭で `Session.approvedAt` を取得し、`null`（未承認 or submission 不存在）なら新設
    `phase:'plan'` を即返す（`approved:false`）。存在しない場合と未承認の場合でメッセージを分ける。
  - 承認済みの場合は以降の全分岐（`done`/`exec`/`queued`）に `approved:true` と `approvedAt`
    （ISO 文字列）を追加。
  - ツール description に「`approve_implementation` の return を待ってから呼ぶこと、並列呼び出し禁止」
    を明記。
  - これにより「未承認」と「承認直後・exec 開始直前」が同じ応答に潰れなくなり、
    呼び出し側モデルの「承認が受理されていない」という誤読を構造的に防止する。
- `apps/server/src/mcp/tools.ts` の `approve_implementation`: `execConversation()` 失敗時の catch 内で、
  claim 解放（`approvedAt` を null に戻す）に加えて先に作成した `exec` Message を削除するよう修正
  （`prisma.message.create()` の戻り値の `id` を保持し、catch で `prisma.message.delete()`。
  削除自体の失敗は claim 解放を妨げないよう握り潰す）。where 句は新設した純関数
  `buildExecMessageRollbackWhere(messageId)`（`submission-guard.ts`）経由。
