# サイクル SDK-0: claude-agent-sdk 0.3 系への移行調査（read-only）

## 概要

raw-completion Phase 1.3（`doc/devlog/2026-09-20_093326.md`）で停止条件4（同梱 `cli.js` の消滅）により
中止した SDK 0.2→0.3 移行の再挑戦に向けた、read-only の調査サイクル。
**コード・package.json・pnpm-lock.yaml・node_modules の変更はゼロ**。成果物は
`doc/sdk-0.3-migration-findings.md`（新規）とこの devlog のみ。

## Plan フェーズ（read-only 実測）

- 前サイクルの前提を3件訂正: (1) `agents/linux` の SDK は dangling ではなく実稼働は 0.2.80、
  (2) 0.3系は我々の node_modules 構成では `extractFromBunfs` が発火しない、
  (3) pnpm はプラットフォームパッケージを SDK 自身の private node_modules にしかリンクせず
  `createRequire(import.meta.url)` を Agent モジュール起点で使うと健全な環境でも必ず失敗する
  （解決済み sdk.mjs 起点で `createRequire` する必要がある）。
- SDK import 箇所（4ファイルのみ）と `query()` の使用 option 全面を洗い出し。
- `getClaudeExecutableFallback()` の判定ロジック・呼び出し元4箇所・`resolveSystemClaude()` との
  役割分担を確定。macOS は `claude-locator.ts`/`claude-path.ts` が未移植でインライン実装が残っていることを確認。
- 0.3.278 の実測（pnpm仮想ストアの残骸を read-only 走査）: `cli.js` 消滅、`bridge.mjs` 新設、
  `sdk.d.ts` が 141,640→479,793 bytes、`claudeCodeVersion` が `2.1.278`（`claude-fable-5-1` 要件を満たす）、
  8プラットフォームの `optionalDependencies` 完全固定、ネイティブバイナリ 234,119,480 bytes。
- `u`/サーバー Auto Update のフローとゲート（`Machine.autoUpdate`/bake time 120分/cooldown等）を確定。
  **`u` はこれらのゲートを一切通らない**ことが唯一のカナリアの穴と判明。
- SDK-1（実装サイクル）の方針・コミット分割・カナリア順序（uso8m→hp630g9→MacBook-Air→ubuntu-prod最後）・
  ロールバック手順を策定。

## Exec フェーズ（本サイクルで新規実施）

すべてリポジトリ外の一時ディレクトリ `/tmp/sdk03-1k0OuY`（`npm install @anthropic-ai/claude-agent-sdk@0.3.278`）で実施。
リポジトリの node_modules・lockfile には一切触れていない。

**Step 0（npm フラット解決の実測、新規）**: pnpm と対比するため npm でインストールし、
`createRequire(import.meta.url)` を「呼び出し元スクリプト起点」「解決済み sdk.mjs 起点」の両方で
`claude-agent-sdk-linux-x64` を解決できることを確認（npm では訂正3の問題は再現しない＝pnpm 固有と確定）。
バイナリサイズは 234,119,480 bytes で pnpm 実測値と完全一致。`package.json` の subpath resolve は
`ERR_PACKAGE_PATH_NOT_EXPORTED`（想定通り、`fs.readFileSync` で読む設計が正しいと再確認）。

**Step 1（型定義差分）**: Plan フェーズの実測（`sdk.d.ts` サイズ差分・`Options` キー拡張・peer import type）を
そのまま findings に転記。承認note指示により再実測は行っていない。

**Step 2（query() スモークテスト、新規）**: 既定モデルと `claude-fable-5-1` それぞれ1回ずつ実行。
両方とも `text` 非空・`is_error: false`・`num_turns: 1` で正常終了。所要時間は既定モデル 5399ms、
`claude-fable-5-1` 5442ms とほぼ同等。`system/init` の `model` フィールドで `claude-fable-5-1` が
正しくエコーされることを確認（拒否・フォールバック無し）。

**auto-memory キルスイッチの動的確認（新規、承認note必須項目）**: `query()` の `system/init` メッセージの
`memory_paths.auto` フィールドを実測して実際の参照先ディレクトリ（`~/.claude/projects/-tmp/memory/`）を特定
（cwd の完全エンコード `-tmp-sdk03-1k0OuY` とは異なり `-tmp` に短縮される副次発見あり、原因未特定・
SDK-1での注意点として記録）。この場所に sentinel を仕込み4パターンを実測:
- 対照区（`settingSources`未指定、kill switch無し）→ **漏洩する**
- `settingSources:[]`のみ（kill switch無し）→ **漏洩する**（重要な新知見：`settingSources:[]`単体では不十分）
- raw-completion 3層防御フル → **漏洩しない**
- env単体（`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`）→ **漏洩しない**

結論: **auto-memory キルスイッチは SDK 0.3.278 でも機能する**。Phase 1.3 の防御は移行後も有効。
sentinel 状態（`~/.claude/projects/-tmp/` と `~/.claude/projects/-tmp-sdk03-1k0OuY/`）は実測後すべて削除し、
残存が無いことを確認済み。一時ディレクトリ `/tmp/sdk03-1k0OuY` も削除済み。

## 結論

0.3.278 への移行で壊れる箇所は `getClaudeExecutableFallback()` の判定ロジックのみと特定。
pnpm 特有の `createRequire` 解決の罠は npm との対比実験で実証され、SDK-1 の設計
（解決済み sdk.mjs 起点で `createRequire`）が正しい対策であると裏付けられた。`query()` は
`claude-fable-5-1` を含め 0.3.278 で問題なく動作し、auto-memory の3層防御も機能することを実証した。
SDK-1（実装サイクル）に進むための技術的な障害は見当たらない。
