# プランモードの書き込みゲート穴（chat 経路）の根治

- 日時: 2026-09-12 11:05 JST
- プラン: `/home/devrelay/.claude/plans/eager-painting-sparrow.md`
- スコープ: `apps/server`（Layer 1）+ `agents/{linux,macos}`（Layer 2）+ `CLAUDE.md`/`rules/project.md`

## 背景・調査で確定した根本原因

2026-09-12 09:41 JST、test009（ubuntu-prod/devrelay）で「e.承認要求を出すために、TEST.TXTを作る作業をしてみてください」を送信したところ、**承認カードも deny も出ないまま Write が成功し TEST.TXT が作成された**。

読み取り専用フォレンジック（server log / agent.log の実測突合）により、単一の確定経路が判明した:

1. `command-parser.ts:152` の exec 判定はカンマ必須の正規表現 `/^(?:e|exec)\s*,\s*(.+)$/is` であり、`e.<本文>`（カンマなし）は exec ではなく**通常のチャットメッセージ**（`ai:prompt`）として扱われる。
2. server は `resolvePermissionPolicy('chat')` を呼び、従来はこれが `'interactive'` を返していた（`'mcp'` のみ `'strictReadonly'`）。
3. agent 側 `connection.ts` は `strictReadonly = permissionPolicy === 'strictReadonly' && usePlanMode` と解決するため、chat 経路では常に `strictReadonly = false` になる。
4. プランターンの `canUseTool`（`ai-runner.ts`）は `decidePlanPermission()` を呼ぶが、`plan-permission.ts` の実装は `if (!params.strictReadonly) return { behavior: 'allow' }` という**無条件 allow の早期 return**を write-tool チェックより先に置いていたため、Write/Edit/MultiEdit/NotebookEdit を含む全ツールが無審査で allow され、SDK 自身の `permissionMode:'plan'` を上書きしていた。
5. さらに `connection.ts` の `onAutoApproved` 配線は `if (!usePlanMode || strictReadonly)` の条件下でしか行われず、この経路の allow は WebUI の Approvals タブにも一切記録されない（完全に不可視）。これが長期間気付かれなかった理由。

Bash が別経路に見えたのは経路の違いではなくモード（plan/exec）の違いであり、同じ plan ターンなら Bash も Write も等しく無審査で素通りしていた。

`e,<本文>`/`e` 単体（exec）や、Claude Code 側の `~/.claude/settings*.json`（permissions/hooks なし、`settingSources` 未設定のため SDK が読まない）、`--dangerously-skip-permissions` 相当のフラグ（コード上どこにも存在しない）はいずれも原因ではないことも確認済み。

## 着手前の必須実測: Task サブエージェントの canUseTool バイパス有無

実装着手前に、`packages/shared/src/constants.ts:233` に残っていた「`Task` サブエージェントの canUseTool 経由有無は実機 E2E で要確認」という未検証コメントを解消するため、インストール済み Claude Agent SDK（`@anthropic-ai/claude-agent-sdk@0.2.77`）のソースを静的解析した。

`sdk.mjs` の `processControlRequest` メソッド（`can_use_tool` サブタイプの唯一のディスパッチ地点）を直接確認した結果:

```js
async processControlRequest(Q,X){
  if(Q.request.subtype==="can_use_tool"){
    if(!this.canUseTool) throw Error("canUseTool callback is not provided.");
    return {
      ...await this.canUseTool(Q.request.tool_name, Q.request.input, {
        signal:X, suggestions:Q.request.permission_suggestions,
        blockedPath:Q.request.blocked_path, decisionReason:Q.request.decision_reason,
        title:Q.request.title, displayName:Q.request.display_name,
        description:Q.request.description, toolUseID:Q.request.tool_use_id,
        agentID:Q.request.agent_id   // ← サブエージェント識別子。main thread では undefined
      }),
      toolUseID:Q.request.tool_use_id
    };
  } else if (...)
}
```

`cli.js` の zod スキーマ（PermissionRequest hook / `can_use_tool` control_request 双方）にも `agent_id: S.string().optional().describe("...Present only when the hook fires from within a subagent...")` という一致する定義があり、これを裏付ける。

**結論**: `Task` サブエージェント発のツール呼び出しであっても、トップレベルのツール呼び出しであっても、**同一の `this.canUseTool` コールバックに必ずルーティングされる**（区別は `agentID`/`agent_id` フィールドのみで、DevRelay の実装はこれを特別扱いしていない）。したがって `canUseTool` をバイパスする経路は存在せず、`PLAN_READONLY_TOOLS` に `'Task'` を含める現行実装のままで安全であることが確定した。**コード変更は不要**。この結果は `constants.ts:233` の未検証コメントの解消として `rules/project.md` にも記録した。

## 修正方針: 2 層構成

### 第 1 層（server のみ・`pm2 restart` で全機に即時反映・agent `u` 不要）

既存 agent は #332 で `'strictReadonly'` リテラルの処理を**既に持っている**ため、server が chat 経路でこの値を送るだけで更新済みの全 linux/macOS agent に即座にゲートが効く。新しいポリシー文字列は発明していない（未更新 agent での fail-open を避けるため）。

- `apps/server/src/services/permission-policy.ts`: `resolvePermissionPolicy(source, options?)` に `strictChatPlan` オプションを追加。`'mcp'`/`'chat'`(既定)/`'ask'`(新規) → `'strictReadonly'`。`'chat'` は `options.strictChatPlan === false` のときのみ `'interactive'` に戻る。`'exec'` は常に `'interactive'`（人間承認済みのフル権限は不変）。モジュール自体は `process.env` を読まない（外部 import ゼロの純関数を維持）。
- `apps/server/src/services/command-handler.ts:1889`: `resolvePermissionPolicy('chat', { strictChatPlan: process.env.DEVRELAY_PLAN_STRICT_CHAT !== '0' })` に変更。キルスイッチは `DEVRELAY_THREADS_SCOPE_INTERACTIVE !== '0'`（`session-manager.ts:278`）と同じ「既定オン・`0` でオプトアウト」パターン。
- `apps/server/src/services/agent-manager.ts`（`executeCrossProjectQuery` = ask/teamexec 経由のプロンプト投入）: `sendPromptToAgent(...)` に `permissionPolicy` が渡されておらず既定の `'interactive'` に落ちる同種の穴が存在したため、`resolvePermissionPolicy('ask')` を明示的に渡すよう修正。`PermissionPolicySource` に `'ask'` を追加。

**exec を壊さない根拠**: `usePlanMode` は agent 側で会話履歴から導出される値（server は plan/exec を知らない）。`connection.ts` の `strictReadonly = permissionPolicy === 'strictReadonly' && usePlanMode` が `&& usePlanMode` で AND されているため、chat 経路に無条件で `'strictReadonly'` を送っても **exec ターンでは必ず false に落ちる**。`permissionPolicy` を直接読む唯一の箇所（`connection.ts` の skip 判定）も `=== 'skip'` しか見ないため exec の `skipPermissions` 解決は不変。

### 第 2 層（agent・要 commit+push+各機 `u`）— ポリシー非依存の最終防衛線

- `agents/{linux,macos}/src/services/plan-permission.ts`: `decidePlanPermission()` 内の write-tool deny チェック（`(params.writeTools ?? []).includes(params.toolName)` → `planPolicy:writeTool`）を `!params.strictReadonly` の早期 return より**前**に移動（純粋な文の並べ替え、シグネチャ変更なし、`writeTools` 未指定時は `?? []` で従来どおり allow の後方互換を維持）。これにより `permissionPolicy` が届かない経路（キルスイッチ OFF・旧 server×新 agent 等）でも Write/Edit/MultiEdit/NotebookEdit は plan モードで必ず deny される。Bash はここでは扱わない（第 1 層の責務。ここで Bash まで deny すると未カバー経路への影響が大きすぎるため今回はスコープ外）。linux/macOS は完全に同一の編集（`diff` で確認済み、macOS 固有の JSDoc 1 行を除き差分なし）。
- `agents/{linux,macos}/src/services/connection.ts`: `onAutoApproved` の配線を `if (!usePlanMode || strictReadonly)` ガード付きから無条件配線に変更。09:41 の Write 無承認成功が Approvals タブにも一切残らなかった不可視性を解消する。
- `agents/{linux,macos}/src/services/ai-runner.ts`: plan モードの `canUseTool` が deny を返さない allow パス（strictReadonly=true の allowlist 内許可、strictReadonly=false の従来 allow の両方）で `options.onAutoApproved?.({ toolName, toolInput: input })` を呼ぶよう追加。`connection.ts` の無条件配線とセットで初めて「plan モードの全ツール呼び出しが監査行を残す」が成立する。

## 挙動が変わるもの（ユーザー影響）

chat のプランターンで Write/Edit/MultiEdit/NotebookEdit が deny になる（exec ターンは一切不変）。`AskUserQuestion`/`Read`/`Grep`/`Glob` 等の読み取り系ツールと Bash（第 2 層は write tool 限定のため）は引き続き plan モードの既存挙動（第 1 層が effective な機体では allowlist 判定、そうでない機体では従来どおり allow）に従う。摩擦が大きい場合は `DEVRELAY_PLAN_STRICT_CHAT=0` で即時ロールバック可能（chat のみに作用、mcp/exec には影響しない）。

## 本サイクルで塞がらない既知の穴（意図的にスコープ外）

- `find`/`curl` の argv0 のみでの分類（引数を見ないため `find -delete` 等が strictReadonly の allowlist を素通りする）
- gemini の `--approval-mode auto_edit` ハードコード（`usePlanMode` を見ていない）
- terminalMode（PTY）: `canUseTool` を使わないため `strictReadonly` が無効
- devin: `usePlanMode` を常に false に強制（git 自動復元ガードで別途担保）
- Windows agent: `plan-permission.ts` 自体が未移植（`canUseTool` も未設置のため CLI の `--permission-mode plan` がそのまま効き、元のバグ自体は出ない可能性が高いが未実測）
