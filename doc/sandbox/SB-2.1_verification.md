# SB-2.1 完了記録と実機検証（2026-11-24〜25、hp630g9）

## 1. 何ができるようになったか

- `config.yaml` の `sandbox.allowDestinations` に `"IP:ポート"` を書くと、Sandbox からその IP の
  その TCP ポートにだけ直接届くようになる（例 `"10.1.200.1:1521"`）。テスト DB など、中継プロキシ
  （ドメイン宛）では通せない直接通信を PC 単位で許可するための仕組み
- PC 単位（開発者が自分の `%APPDATA%\devrelay\config.yaml` に書く）、上限 20 件、開発者が自由に
  編集できる。Sandbox の身元からはこのファイルは読めない
- 既存の `sandbox.allowlist`（ドメイン宛・中継プロキシ 127.0.0.1:48711 経由）とは別物
- 書式の決まり: `/32` の IPv4 のみ、ポートは 1〜65535、ループバック等の禁止レンジは拒否、
  1 件でも不正なら全体を拒否（一部だけ適用することはしない）。未設定・空なら従来どおり何も通さない
- **ping（ICMP）とファイル共有（SMB）は対象外**。これらの通信は Windows 本体（OS / System）が
  代行するため、プロセスの身元単位のルールでは止まらない（SB-1 の実測で確認済み、§8 参照）

## 2. 仕組みの要約

- install スクリプトが登録する **SYSTEM** のタスク `\DevRelay\apply-sandbox-allowlist`
  （PC 起動時 `ONSTART` に加え、必要時に開発者本人が起動できる。定期実行はしない）が、
  開発者の要求ファイル（許可したい IP:ポートの一覧）を**自分で検証し直して**ファイアウォールへ
  反映し、結果をファイルに書き戻す。タスクが実行するのはリポジトリのスクリプトではなく、
  install がコピーした専用フォルダ内のコピー（開発者は実行のみ可能・書き換え不可）
- ファイアウォールのルールは 2 種類ある:
  - install が持つ「全遮断ルール」(`DevRelay-SandboxFailClosed-ipv4` 等) — 許可リストの状態に
    関わらず常に存在する大枠の遮断
  - apply が持つ「世代ルール」(`DevRelay-SandboxGen-<世代>-...`) — 許可リストの内容ごとに
    新しい世代として作られる、実際の許可を反映したルール
- 反映の順序は「**新しいルールを全部作ってから古いものを消す**」: 新世代のルールを全部作る →
  新鮮な問い合わせで全部実在することを確認する → ここで初めて古い世代を消す → 最後に全遮断ルールを
  消す。重なっている間は「新 ∪ 旧」で常に目標以上に厳しい状態になり、緩む瞬間が構造的に発生しない
- **失敗したら全遮断に倒れる**（fail-closed）: ルール作成の途中で失敗したら、その回で作った分だけ
  元に戻し、古い世代と全遮断ルールはそのまま残す。問い合わせ自体が失敗した場合も「無い」と同じ
  扱いにして、消さない側に倒す
- **Sandbox 実行開始時の突き合わせ**: 実行の直前に、開発者の設定ファイルから計算した値と、
  直前の反映結果を比較する。合っていなければタスクを 1 回起動し、最大 **60 秒**（タスクが動いて
  いると分かっている間は最大 **180 秒** まで延長）待つ。待っている間はチャットに
  `⏳ Sandbox の許可する接続先をファイアウォールへ反映中...（N秒経過）` が 30 秒おきに出る。
  それでも解消しなければ実行を拒否する（反映の方向が「厳しくなる」場合でも拒否する）

## 4. 実機確認の結果（hp630g9、2026-11-24〜25）

### Windows PowerShell 5.1 のテスト

`scripts/tests/test-apply-sandbox-allowlist.ps1` を実機（PowerShell 5.1）で実行した結果:

- **17 PASS / 0 FAIL / 1 SKIP**
- SKIP になったのは、要求ファイルをシンボリックリンクにするケースのみ。実行したアカウントが
  管理者ではなく、シンボリックリンクを作る権限が無かったため

### 接続確認

同じ LAN 上の宛先 4 つに対し、開発者本人の身元と、Sandbox の身元（許可リストの有無を切り替えて）
から接続を試みた結果:

| 宛先 | 開発者 | Sandbox（許可あり: 192.168.32.196:2222） | Sandbox（許可を消したあと） |
|---|---|---|---|
| 192.168.32.196:2222 | connected | connected | error |
| 192.168.32.196:2223 | connected | error | error |
| 192.168.32.1:80 | timeout | error | error |
| 1.1.1.1:443 | connected | error | error |

- 許可した宛先（192.168.32.196:2222）だけが Sandbox から届き、他は全て止まっている
- 許可リストを消した後は、Sandbox からは 4 宛先すべてが届かなくなった（全遮断に戻る）

### 確認方法の注意

- `BeginConnect` + `WaitOne` は「接続の試みが終わったか」しか見ないため、成功・失敗の区別には
  使えない。`ConnectAsync` を使い、結果を connected / timeout / error の 3 つに分けて判定する
- ファイアウォールで止められた場合は**即座に error** になる
- 相手側に届いたが応答が返らない（捨てられた）場合は **timeout** になる。表中、開発者の身元から
  192.168.32.1:80 への接続が timeout になっているのは、Linux 側（相手側）の ufw がそのポートを
  塞いでいたためで、Sandbox の仕組みとは無関係

## 5. Windows PowerShell 5.1 で踏んだ落とし穴

Linux 上の pwsh では再現しないものを含む。いずれも SB-2.1.1〜2.1.4 の実機確認で見つかった

- **`Stop` の下で外部コマンドの標準エラー出力が例外になる**（`2>$null` でも防げない） →
  `Invoke-NativeCommand` ヘルパーで外部コマンド呼び出しを経由させる（SB-2.1.1）
- **`List[object]` に `@()` を使うと ArgumentException** になる → `.ToArray()` を使う（SB-2.1.2）
- **整数の割り算が小数になり、`[uint64]` への変換が四捨五入される** → IP アドレスの文字列が
  壊れる（終了が開始より小さい範囲が生成される等） → 桁ごとに独立して計算し、生成した範囲
  文字列を往復パースして正しいか確認する自己検査を追加（SB-2.1.3）
- **NetSecurity（ファイアウォール操作）のコマンドは、呼び方によって `$ErrorActionPreference` を
  見ない** → `-ErrorAction Stop` を明示し、ルールを削除する前に実在を確認する（SB-2.1.3）
- **catch の中の `Write-Error` が例外になり、元のエラーを隠す** → `Write-Error` を使わない方針に
  した（SB-2.1.3）
- **ハッシュテーブルのキーは `Select-Object -ExpandProperty` / `Group-Object -Property` では
  読めない** → 素の `foreach` とメンバーの直接参照に書き換えた（SB-2.1.4）

## 6. 進め方の教訓

Linux で書いた PowerShell スクリプトを、PowerShell 5.1 で一度も動かさずに実機確認へ回すと、
1 回の実機確認で 1 つずつしか不具合が見つからない（SB-2.1.1〜2.1.5 がまさにこの繰り返しだった）。

ファイアウォール操作などのコマンドを記録専用の差し替えに置き換えたテストを、先に 5.1
（hp630g9 の非管理者アカウント）で全経路流してから実機確認に進む
（`scripts/tests/test-apply-sandbox-allowlist.ps1`、SB-2.1.4 で新設）。
